## Why this doc exists

Four RFCs currently carry a `Target: v0.3.x` line with no committed minor: [RFC 0023](rfcs/0023-llm-call-leasing.md) (LLM Call Leasing), [RFC 0024](rfcs/0024-event-driven-scheduling.md) (Event-Driven Agent Scheduling), [RFC 0026](rfcs/0026-declarative-facts-tier.md) (Declarative Facts Tier), and [RFC 0029](rfcs/0029-personal-society-storage-split.md) (Personal/Society Storage Split). Without an upfront sequencing call, three things go wrong:

1. **v0.3.0 scope creeps.** v0.3.0 is on the line — five RFCs (0008, 0009 P1–2, 0011 internal, 0020, 0021 P1) are mid-flight per the [v0.3.0 plan](v0.3.0-plan.md). Each new "could land in v0.3.0?" question that surfaces during review delays the cut. This doc explicitly takes the four candidates *off* v0.3.0.
2. **Cross-RFC sequencing slips.** RFC 0024 says "sequence after RFC 0023 lands at least Phase 1" ([RFC 0024 §Decision/Next Steps](rfcs/0024-event-driven-scheduling.md#decision--next-steps)); RFC 0026 lands its dementia-test improvements with no upstream dependency; RFC 0029 Phase 1 is a pure facade refactor that v0.4.0 needs ratified before RFC 0028 implementation begins. These constraints differ; ordering them once here is cheaper than re-litigating per-RFC.
3. **The "what user can do" line per patch is unclear.** [ROADMAP §Version Map](../ROADMAP.md#version-map) frames every release by what a developer gains. Patches are no exception — each v0.3.x release needs one sentence explaining the win.

Same shape as [v0.3.0-plan.md](v0.3.0-plan.md): a thin orchestration overlay across four RFCs that already own their internals. Owns "which patch, in what order, by what gate" — nothing else.

## Decision

Three v0.3.x patch releases. v0.3.0 itself is unchanged.

| Version | RFC scope | One-line story |
|---------|-----------|----------------|
| **v0.3.0** | (no change) — close on the [v0.3.0 plan](v0.3.0-plan.md) bundle: RFCs 0008, 0009 P1–2, 0011 internal, 0020, 0021 P1 | "Give agents a shared channel and watch them talk, negotiate, and form opinions over time" ([ROADMAP §Version Map](../ROADMAP.md#version-map)) |
| **v0.3.1 — Memory Quality** | [RFC 0026](rfcs/0026-declarative-facts-tier.md) Phases 1–3 (full RFC) **+** [RFC 0029](rfcs/0029-personal-society-storage-split.md) Phase 1 (`MemoryStore` facade refactor only — no Postgres) | The persona remembers stated facts about you (names, preferences, commitments) across interactions. The dementia test ([MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md)) flips green on the named-entity, preference, and self-consistency legs. |
| **v0.3.2 — Cost Gate** | [RFC 0023](rfcs/0023-llm-call-leasing.md) Phases 1–6 (full RFC, including Phase 6 channel-origin since RFC 0011 has shipped) | Every LLM call in the system — workflow, chat, autonomous tick, sub-agent, channel reply — passes through a wallet lease before issuing. The "chat bypasses BudgetEnforcer" line on the README known-limitations list comes off. |
| **v0.3.3 — Idle Truly Idle** | [RFC 0024](rfcs/0024-event-driven-scheduling.md) Phases 1–4 | A persona with no scheduled work and no inbound traffic stops paying any cost — no SQLite recall query, no `_inject_memory_context`, no provider-side activity. RFC 0017 §F empty-context guard is documented as vestigial (deletion deferred to Phase 5 in v0.4.0). |

### Why this order

**v0.3.1 first — memory quality is the user-visible win.** RFC 0026 is the highest-leverage fix for the [dementia test](memory-quality-roadmap.md#quality-bar--the-dementia-test). The roadmap explicitly calls it the §A deliverable from the [Memory Quality Roadmap](memory-quality-roadmap.md#a-promote-key_facts-to-a-declarative-fact-tier). Pairing it with RFC 0029 Phase 1 (MemoryStore facade) is the right shape because (a) facade promotion is a pure refactor — behaviour-identical, low risk; (b) RFC 0026 lands a new tier (`facts`), so promoting the facade *with* the tier addition keeps the migration to a single quarter rather than two. RFC 0029's [Phased Implementation Plan](rfcs/0029-personal-society-storage-split.md#phased-implementation-plan) explicitly notes Phase 1 is independent of RFC 0024, so this pairing does not block v0.3.3.

**v0.3.2 second — cost is the recurring failure class.** The [README cost warning](../README.md#%EF%B8%8F-cost-warning--read-before-running) documents a real $35 incident; v0.2.2 closed [one specific leak](rfcs/0017-persona-memory-injection-budget.md#f-empty-context-tick-short-circuit) and v0.2.3 still lists "chat traffic bypasses BudgetEnforcer" as a [known limitation](rfcs/0023-llm-call-leasing.md#motivation). RFC 0023 retires the class structurally. It ships before RFC 0024 because RFC 0024's Phase 3 salience-wake metric explicitly wants `wake.kind` as a lease attribute — that hook is cheapest to add the moment the wallet is the canonical cost surface.

**v0.3.3 third — idle truly idle.** RFC 0024 closes the polling-loop class once cost attribution is in place. Pairing the two structural cost fixes (lease + polling removal) across two patches rather than one keeps each PR set under the [BRANCHING.md](BRANCHING.md) review surface and gives one release of soak time on the wallet before the wake-source taxonomy lands on top of it.

## Per-version user-facing story

A version is ready when a developer can do something meaningful they could not do before ([ROADMAP §Version Map](../ROADMAP.md#version-map)).

### v0.3.1 — Memory Quality

> **Demo loop**: tell the persona "my daughter's name is Mira and she's allergic to peanuts," close the conversation, come back three days later, ask "what should I pack for Mira's school lunch?". v0.3.0 forgets Mira's name half the time and forgets the allergy almost always. v0.3.1 nails both because they live in the `facts` table indexed by subject = `Mira`, not embedded prose-side in the previous interaction summary.

Acceptance gates:
- [MT-MEMORY-005 — Dementia Test](manual-tests/MT-MEMORY-005-dementia-test.md) passes the named-entity leg (Leg 1), preference leg (Leg 2), and self-consistency leg (Leg 5) at >90% per [RFC 0026 §Phase 3](rfcs/0026-declarative-facts-tier.md#phase-3-reinforcement--retraction).
- `MemoryStore` facade is the only path callers reach `EpisodicMemory` / `RelationshipMemory` through; lint rule blocks new direct-aiosqlite imports outside `agents/memory/` ([RFC 0029 Phase 1](rfcs/0029-personal-society-storage-split.md#phased-implementation-plan)).
- No regression in tick-loop latency p99 ([RFC 0029 perf gate](rfcs/0029-personal-society-storage-split.md#test-strategy)).

### v0.3.2 — Cost Gate

> **Demo loop**: set `max_daily_usd: 0.50`, start a persona, run a chat session that costs $0.30, then start a workflow that estimates $0.40. v0.3.0 silently overspends because chat doesn't go through `BudgetEnforcer`. v0.3.1 already-shipped does not change that. v0.3.2 denies the workflow's *second* LLM call inside its task with a structured `LeaseDenied` and the README "chat bypasses BudgetEnforcer" line comes off.

Acceptance gates:
- All five LLM-call origins (workflow / chat / autonomous TICK / sub-agent / channel reply) acquire a lease before invoking the provider ([RFC 0023 Goals](rfcs/0023-llm-call-leasing.md#goals)).
- New manual tests `MT-COST-003` (chat budget exceed) and `MT-COST-004` (TICK budget exhaustion → idle) pass ([RFC 0023 Test Strategy](rfcs/0023-llm-call-leasing.md#test-strategy)).
- README known-limitations line on chat bypass deleted; CHANGELOG calls out the closed bypass.
- Wallet round-trip overhead measured at p99 ≤ 5 ms on loopback per [RFC 0023 Goal #6](rfcs/0023-llm-call-leasing.md#goals).

### v0.3.3 — Idle Truly Idle

> **Demo loop**: start a persona with `timers: []` and no inbound traffic, leave it running for 60 seconds. v0.3.2 ticks every 60 seconds and short-circuits via the §F guard — no LLM call, but does query SQLite and runs `_inject_memory_context`. v0.3.3 is structurally asleep on `queue.get()` — zero SQLite reads, zero allocator runs, zero provider activity, zero wallet leases requested.

Acceptance gates:
- "Bored persona" cost-regression CI gate from [RFC 0024 Test Strategy](rfcs/0024-event-driven-scheduling.md#test-strategy) passes (60 s observation, zero LLM calls, zero `_inject_memory_context` invocations, zero token spend at the wallet boundary).
- Channel-message dispatch goes through `event_loop.enqueue(InboundEventWake(event))` directly, not through `scheduler.wake()` ([RFC 0024 Phase 4](rfcs/0024-event-driven-scheduling.md#phased-implementation-plan)).
- RFC 0017 §F guard remains in place but is documented as vestigial; deletion deferred to RFC 0024 Phase 5 in v0.4.0.

## Dependency chain

```
v0.3.0 close (in-flight: RFCs 0008, 0009 P1–2, 0011 internal, 0020, 0021 P1)
    │
    ├── RFC 0026 (Declarative Facts Tier — full)
    │       ├── depends on RFC 0020 (closed) for interaction-close hook
    │       └── ships with RFC 0029 Phase 1 (facade refactor — independent)
    │            │
    │            └─→  v0.3.1 — Memory Quality
    │
    ├── RFC 0023 (LLM Call Leasing — Phases 1–6)
    │       ├── Phase 0 blockers: transport choice, tokeniser parity (per RFC 0023 §Open Questions #1, #5)
    │       └── Phase 6 (channel origin) lands in-window because RFC 0011 has shipped
    │            │
    │            └─→  v0.3.2 — Cost Gate
    │
    └── RFC 0024 (Event-Driven Scheduling — Phases 1–4)
            ├── soft-depends on RFC 0023 Phase 1 (wake.kind as lease attribute)
            └── soft-depends on SA-1 (RFC 0029) for timer persistence — but Phase 2 ships SQLite
                table now and migrates if/when SA-1 lands a society partition
                 │
                 └─→  v0.3.3 — Idle Truly Idle
```

The chain is sequential by version but the RFCs themselves can begin work in parallel — RFC 0026 implementation starts the moment v0.3.0 cuts; RFC 0023 can begin Phase 0 blocker resolution and Phase 1 (proto + skeleton) while v0.3.1 stabilises.

## Out of scope for v0.3.x

These are explicit non-goals so they don't surface as "could we slip this in?" pressure on the four scoped patches.

- **RFC 0023 Phase 7+** (per-cause budget policies, distributed wallet) — RFC 0006 mesh territory, v0.6+.
- **RFC 0024 Phase 5** (deprecation warning) — v0.4.0 per [RFC 0024 §Phased Implementation Plan](rfcs/0024-event-driven-scheduling.md#phased-implementation-plan).
- **RFC 0024 Phase 6** (`tick_interval_seconds` removal, §F guard deletion, `EventType.TICK` removal) — v0.5+ per same plan, gated on the [Phase 6 entrance criteria](rfcs/0024-event-driven-scheduling.md#phased-implementation-plan).
- **RFC 0026 cross-agent fact sharing** — v0.4.0 per [RFC 0026 §Open Questions #4](rfcs/0026-declarative-facts-tier.md#open-questions); pairs with [RFC 0008 §H](rfcs/0008-agent-memory-context-optimization.md).
- **RFC 0029 Phases 2–6** (capability tokens, Postgres backend, migration tool, society-tier RFC consumers, conditional file-split) — v0.4.0 per [RFC 0029 Phased Implementation Plan](rfcs/0029-personal-society-storage-split.md#phased-implementation-plan); gates RFC 0028 implementation.
- **RFC 0027** (Reflection-Driven Consolidation) — v0.4.0 per [ROADMAP RFC Master Index](../ROADMAP.md#rfc-master-index); supersedes draft 0025.
- **Memory Quality Roadmap MQ-2 / MQ-3 / MQ-7 / MQ-11 / MQ-12** — tracked in the [v0.3.0 plan §Memory Quality Follow-Ups](v0.3.0-plan.md#memory-quality-follow-ups-v03x-and-beyond); each is a small docs/PR follow-up that rides whichever v0.3.x patch is open at the time. They do not anchor a release on their own.
- **The narrowed [RFC 0023 spec — JSON summary schema only](memory-quality-roadmap.md)** is a different scope than this doc's RFC 0023 (LLM Call Leasing). The `0023` file in `docs/rfcs/` is the leasing RFC; the narrowed memory-quality scope is reserved per [ROADMAP RFC Master Index](../ROADMAP.md#rfc-master-index) row 0023 and ships independently as a memory-quality follow-up — does not affect this sequencing.
- **The deferred [RFC 0024 spec — Episodic Vector Recall](memory-quality-roadmap.md)**, gated on [MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md) Leg 4 ([v0.3.0 plan MQ-8](v0.3.0-plan.md#memory-quality-follow-ups-v03x-and-beyond)), is reserved at [ROADMAP](../ROADMAP.md#rfc-master-index) row 0024 — different scope from this doc's RFC 0024 (Event-Driven Agent Scheduling). Same slot-reuse pattern as the 0023 footnote above; revisited only if v0.3.1 dementia data shows recall (not representation) is the bottleneck.

| [MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md) telemetry needs per-turn tier provenance to diagnose leg failures. MQ-11 in [v0.3.0 plan](v0.3.0-plan.md#memory-quality-follow-ups-v03x-and-beyond) and step 3 of [RFC 0026 §Phase 3](rfcs/0026-declarative-facts-tier.md#phase-3-reinforcement--retraction) name the same `MemoryBudget`-allocator instrumentation. ## Open questions

1. **Should v0.3.1 fold MQ-1 (outcome-tagged importance, [RFC 0020 OQ #6](rfcs/0020-interaction-lifecycle.md#open-questions)) alongside RFC 0026?** MQ-1 is a small carve-out of `0020-pr-plan.md` and unblocks MQ-7 (salience reinforcement, [RFC 0008 calibration review](rfcs/0008-calibration-review.md)). Lean toward yes — it is one extractor-prompt patch and lands cleanly with the facts extractor that RFC 0026 Phase 1 introduces. Decide at `0026-pr-plan.md` authoring time.
2. **Does v0.3.2 need a separate "RFC 0023 follow-up: chat reply caching"?** [RFC 0023 §Open Questions #6](rfcs/0023-llm-call-leasing.md#open-questions) flags the response-cache placement when chat or channel-reply paths gain caching. Out of scope for v0.3.2; track as a tracked-issue follow-up on RFC 0023 PR 4 if it surfaces.
3. **Should v0.3.3 ship a calibration step for the salience threshold ([RFC 0024 §Open Questions #2](rfcs/0024-event-driven-scheduling.md#open-questions))?** Default keeps salience wakes off; calibration needs a week of production reflection-score data. v0.3.3 ships with the default disabled and a tracked-issue follow-up to flip it after a soak.
4. **Bundle v0.3.3 into v0.4.0 if RFC 0024's PR count is small enough?** Phases 1–4 are ~6–8 PRs; below the v0.3.0 bundle's volume. If v0.4.0 master plan opens before v0.3.3 cuts, reassess — but the default is to ship the cost-attribution win independently so the bored-persona regression gate has its own release boundary. Tradeoff with [§Risks row 4](#risks): bundling violates the per-version user-story contract — this only stays open if v0.3.3's "idle" story reads as a half-deliverable of the v0.3.2 cost gate.

## Amendment 2026-05-12 — re-sequence after RFCs 0030 and 0031 and post-v0.3.0 data

The original 2026-05-10 decision predates three events that landed on or before v0.3.0 cut. The active decision is updated below; the body above is preserved verbatim for context.

### What changed since 2026-05-10

1. **v0.3.0 shipped (2026-05-12).** [MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md) Leg 1 confirmed the dementia-gap signature; [release checklist §6](v0.3.0-release-checklist.md#6-known-gaps-to-document-in-release-notes) pins RFC 0026 as the v0.3.1 fix path. That promise is now public.
2. **[RFC 0031](rfcs/0031-per-session-namespacing-channels.md) filed 2026-05-12.** F-3 root-cause fix. [OQ #4](rfcs/0031-per-session-namespacing-channels.md#open-questions) is load-bearing: *"the cheaper sequencing is this RFC's Phase 1 lands before RFC 0029 Phase 1 freezes the facade."* Shipping 0029 P1 in v0.3.1 without 0031 forces a non-additive facade back-extension when 0031 lands later.
3. **[RFC 0030](rfcs/0030-multi-agent-conversation-governance.md) filed 2026-05-11.** [Layer 1 is gated on RFC 0023 Phase 1](rfcs/0030-multi-agent-conversation-governance.md#phased-implementation-plan); shipping before v0.3.2 leaves it wire-reserved.

Risk and mitigation detail lives in [v0.3.1-plan.md §Risk and mitigations](v0.3.1-plan.md#risk-and-mitigations) — not duplicated here.
