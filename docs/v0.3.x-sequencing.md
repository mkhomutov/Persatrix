## Why this doc exists

Four RFCs currently carry a `Target: v0.3.x` line with no committed minor: [RFC 0023](rfcs/0023-llm-call-leasing.md) (LLM Call Leasing), [RFC 0024](rfcs/0024-event-driven-scheduling.md) (Event-Driven Agent Scheduling), [RFC 0026](rfcs/0026-declarative-facts-tier.md) (Declarative Facts Tier), and [RFC 0029](rfcs/0029-personal-society-storage-split.md) (Personal/Society Storage Split). Without an upfront sequencing call, three things go wrong:

1. **v0.3.0 scope creeps.** v0.3.0 is on the line — five RFCs (0008, 0009 P1–2, 0011 internal, 0020, 0021 P1) are mid-flight per the [v0.3.0 plan](v0.3.0-plan.md). Each new "could land in v0.3.0?" question that surfaces during review delays the cut. This doc explicitly takes the four candidates *off* v0.3.0.
2. **Cross-RFC sequencing slips.** RFC 0024 says "sequence after RFC 0023 lands at least Phase 1" ([RFC 0024 §Decision/Next Steps](rfcs/0024-event-driven-scheduling.md#decision--next-steps)); RFC 0026 lands its dementia-test improvements with no upstream dependency; RFC 0029 Phase 1 is a pure facade refactor that v0.4.0 needs ratified before RFC 0028 implementation begins. These constraints differ; ordering them once here is cheaper than re-litigating per-RFC.
3. **The "what user can do" line per patch is unclear.** [ROADMAP §Version Map](../ROADMAP.md#version-map) frames every release by what a developer gains. Patches are no exception — each v0.3.x release needs one sentence explaining the win.

Same shape as [v0.3.0-plan.md](v0.3.0-plan.md): a thin orchestration overlay across four RFCs that already own their internals. Owns "which patch, in what order, by what gate" — nothing else.

## Decision

Three v0.3.x patch releases. v0.3.0 itself is unchanged.

| Version | RFC scope | One-line story |
|---------|-----------|----------------|
| **v0.3.0** | (no change) — close on the [v0.3.0 plan](v0.3.0-plan.md) bundle: RFCs 0008, 0009 P1–2, 0011 internal, 0020, 0021 P1 | "Give agents a shared channel and watch them talk, negotiate, and form opinions over time" ([ROADMAP §Version Map](../ROADMAP.md#version-map)) |
| **v0.3.1 — Memory Quality** | [RFC 0026](rfcs/0026-declarative-facts-tier.md) Phases 1–3 (full RFC) **+** [RFC 0029](rfcs/0029-personal-society-storage-split.md) Phase 1 (`MemoryStore` facade refactor only — no Postgres) | The persona remembers stated facts about you (names, preferences, commitments) across interactions. The dementia test ([MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md)) flips green on the named-entity, preference, and self-consistency legs. |
| **v0.3.2 — Cost Gate** | [RFC 0023](rfcs/0023-llm-call-leasing.md) Phases 1–6 (full RFC, including Phase 6 channel-origin since RFC 0011 has shipped) | Every LLM call in the system — workflow, chat, autonomous tick, sub-agent, channel reply — passes through a wallet lease before issuing. The "chat bypasses BudgetEnforcer" line on the README known-limitations list comes off. |
| **v0.3.3 — Idle Truly Idle** | [RFC 0024](rfcs/0024-event-driven-scheduling.md) Phases 1–4 | A persona with no scheduled work and no inbound traffic stops paying any cost — no SQLite recall query, no `_inject_memory_context`, no provider-side activity. RFC 0017 §F empty-context guard is documented as vestigial (deletion deferred to Phase 5 in v0.4.0). |

### Why this order

**v0.3.1 first — memory quality is the user-visible win.** RFC 0026 is the highest-leverage fix for the [dementia test](memory-quality-roadmap.md#quality-bar--the-dementia-test). The roadmap explicitly calls it the §A deliverable from the [Memory Quality Roadmap](memory-quality-roadmap.md#a-promote-key_facts-to-a-declarative-fact-tier). Pairing it with RFC 0029 Phase 1 (MemoryStore facade) is the right shape because (a) facade promotion is a pure refactor — behaviour-identical, low risk; (b) RFC 0026 lands a new tier (`facts`), so promoting the facade *with* the tier addition keeps the migration to a single quarter rather than two. RFC 0029's [Phased Implementation Plan](rfcs/0029-personal-society-storage-split.md#phased-implementation-plan) explicitly notes Phase 1 is independent of RFC 0024, so this pairing does not block v0.3.3.

**v0.3.2 second — cost is the recurring failure class.** The [README cost warning](../README.md#-cost-warning) documents a real $35 incident; v0.2.2 closed [one specific leak](rfcs/0017-persona-memory-injection-budget.md#f-empty-context-tick-short-circuit) and v0.2.3 still lists "chat traffic bypasses BudgetEnforcer" as a [known limitation](rfcs/0023-llm-call-leasing.md#motivation). RFC 0023 retires the class structurally. It ships before RFC 0024 because RFC 0024's Phase 3 salience-wake metric explicitly wants `wake.kind` as a lease attribute — that hook is cheapest to add the moment the wallet is the canonical cost surface.

**v0.3.3 third — idle truly idle.** RFC 0024 closes the polling-loop class once cost attribution is in place. Pairing the two structural cost fixes (lease + polling removal) across two patches rather than one keeps each PR set under the [BRANCHING.md](BRANCHING.md) review surface and gives one release of soak time on the wallet before the wake-source taxonomy lands on top of it.

## Per-version user-facing story

A version is ready when a developer can do something meaningful they could not do before ([ROADMAP §Version Map](../ROADMAP.md#version-map)).

### v0.3.1 — Memory Quality

> **Demo loop**: tell the persona "my daughter's name is Mira and she's allergic to peanuts," close the conversation, come back three days later, ask "what should I pack for Mira's school lunch?". v0.3.0 forgets Mira's name half the time and forgets the allergy almost always. v0.3.1 nails both because they live in the `facts` table indexed by subject = `Mira`, not embedded prose-side in the previous interaction summary.

Acceptance gates:
- [MT-MEMORY-005 — Dementia Test](manual-tests/MT-MEMORY-005-dementia-test.md) passes the named-entity leg (Leg 1), preference leg (Leg 2), and self-consistency leg (Leg 5) at >90% per [RFC 0026 §Phase 3](rfcs/0026-declarative-facts-tier.md#phase-3-reinforcement--retraction).
- `MemoryStore` facade is the only path callers reach `EpisodicMemory` / `RelationshipMemory` through; lint rule blocks new direct-aiosqlite imports outside `agents/memory/` ([RFC 0029 Phase 1](rfcs/0029-personal-society-storage-split.md#phased-implementation-plan)).
- No regression in tick-loop latency p99 ([RFC 0029 perf gate](rfcs/0029-personal-society-storage-split.md#test-strategy)).

### v0.3.2 — Cost Gate

> **Demo loop**: set `max_daily_usd: 0.50`, start a persona, run a chat session that costs $0.30, then start a workflow that estimates $0.40. v0.3.0 silently overspends because chat doesn't go through `BudgetEnforcer`. v0.3.1 already-shipped does not change that. v0.3.2 denies the workflow's *second* LLM call inside its task with a structured `LeaseDenied` and the README "chat bypasses BudgetEnforcer" line comes off.

Acceptance gates:
- All five LLM-call origins (workflow / chat / autonomous TICK / sub-agent / channel reply) acquire a lease before invoking the provider ([RFC 0023 Goals](rfcs/0023-llm-call-leasing.md#goals)).
- New manual tests `MT-COST-003` (chat budget exceed) and `MT-COST-004` (TICK budget exhaustion → idle) pass ([RFC 0023 Test Strategy](rfcs/0023-llm-call-leasing.md#test-strategy)).
- README known-limitations line on chat bypass deleted; CHANGELOG calls out the closed bypass.
- Wallet round-trip overhead measured at p99 ≤ 5 ms on loopback per [RFC 0023 Goal #6](rfcs/0023-llm-call-leasing.md#goals).

### v0.3.3 — Idle Truly Idle

> **Demo loop**: start a persona with `timers: []` and no inbound traffic, leave it running for 60 seconds. v0.3.2 ticks every 60 seconds and short-circuits via the §F guard — no LLM call, but does query SQLite and runs `_inject_memory_context`. v0.3.3 is structurally asleep on `queue.get()` — zero SQLite reads, zero allocator runs, zero provider activity, zero wallet leases requested.

Acceptance gates:
- "Bored persona" cost-regression CI gate from [RFC 0024 Test Strategy](rfcs/0024-event-driven-scheduling.md#test-strategy) passes (60 s observation, zero LLM calls, zero `_inject_memory_context` invocations, zero token spend at the wallet boundary).
- Channel-message dispatch goes through `event_loop.enqueue(InboundEventWake(event))` directly, not through `scheduler.wake()` ([RFC 0024 Phase 4](rfcs/0024-event-driven-scheduling.md#phased-implementation-plan)).
- RFC 0017 §F guard remains in place but is documented as vestigial; deletion deferred to RFC 0024 Phase 5 in v0.4.0.

## Dependency chain

```
v0.3.0 close (in-flight: RFCs 0008, 0009 P1–2, 0011 internal, 0020, 0021 P1)
    │
    ├── RFC 0026 (Declarative Facts Tier — full)
    │       ├── depends on RFC 0020 (closed) for interaction-close hook
    │       └── ships with RFC 0029 Phase 1 (facade refactor — independent)
    │            │
    │            └─→  v0.3.1 — Memory Quality
    │
    ├── RFC 0023 (LLM Call Leasing — Phases 1–6)
    │       ├── Phase 0 blockers: transport choice, tokeniser parity (per RFC 0023 §Open Questions #1, #5)
    │       └── Phase 6 (channel origin) lands in-window because RFC 0011 has shipped
    │            │
    │            └─→  v0.3.2 — Cost Gate
    │
    └── RFC 0024 (Event-Driven Scheduling — Phases 1–4)
            ├── soft-depends on RFC 0023 Phase 1 (wake.kind as lease attribute)
            └── soft-depends on SA-1 (RFC 0029) for timer persistence — but Phase 2 ships SQLite
                table now and migrates if/when SA-1 lands a society partition
                 │
                 └─→  v0.3.3 — Idle Truly Idle
```

The chain is sequential by version but the RFCs themselves can begin work in parallel — RFC 0026 implementation starts the moment v0.3.0 cuts; RFC 0023 can begin Phase 0 blocker resolution and Phase 1 (proto + skeleton) while v0.3.1 stabilises.

- **RFC 0024 Phase 5** (deprecation warning) — v0.4.0 per [RFC 0024 §Phased Implementation Plan](rfcs/0024-event-driven-scheduling.md#phased-implementation-plan).

- **RFC 0026 cross-agent fact sharing** — v0.4.0 per [RFC 0026 §Open Questions #4](rfcs/0026-declarative-facts-tier.md#open-questions); pairs with [RFC 0008 §H](rfcs/0008-agent-memory-context-optimization.md).
- **RFC 0029 Phases 2–6** (capability tokens, Postgres backend, migration tool, society-tier RFC consumers, conditional file-split) — v0.4.0 per [RFC 0029 Phased Implementation Plan](rfcs/0029-personal-society-storage-split.md#phased-implementation-plan); gates RFC 0028 implementation.
- **RFC 0027** (Reflection-Driven Consolidation) — v0.4.0 per [ROADMAP RFC Master Index](../ROADMAP.md#rfc-master-index); supersedes draft 0025.
- **Memory Quality Roadmap MQ-2 / MQ-3 / MQ-7 / MQ-11 / MQ-12** — tracked in the [v0.3.0 plan §Memory Quality Follow-Ups](v0.3.0-plan.md#memory-quality-follow-ups-v03x-and-beyond); each is a small docs/PR follow-up that rides whichever v0.3.x patch is open at the time. ## Risks

| Risk | Mitigation |
|------|------------|
| v0.3.1 pairs RFC 0026 with RFC 0029 Phase 1; if the facade refactor finds unexpected coupling, it slips and drags 0026 with it. | Phase 1 of RFC 0029 is explicitly a pure refactor with behaviour-identical tests ([RFC 0029 Test Strategy](rfcs/0029-personal-society-storage-split.md#test-strategy)). If risk materialises, ship 0026 alone in v0.3.1 and slip RFC 0029 Phase 1 to a v0.3.1.x point release; the RFCs are independent. |
| RFC 0023 Phase 0 blockers (transport choice, tokeniser parity) delay v0.3.2 start. | Phase 0 is doc-only review. Open the resolution PRs immediately on v0.3.1 cut so the Phase 0 calls are settled before v0.3.1 ships. | RFC 0024 Phase 2's per-agent SQLite `scheduled_wakes` table couples to a backend SA-1 (RFC 0029) may re-shape. | Acknowledged in [RFC 0024 §Open Questions #1](rfcs/0024-event-driven-scheduling.md#open-questions): table is a derived cache, source of truth is `agents.yaml`. | Three patches in sequence is more release-prep overhead than one bundled v0.4.0. | Each patch carries one user-facing story per the [ROADMAP version-map definition](../ROADMAP.md#version-map). Bundling all four RFCs into a single release violates that contract — the user can't tell what they gained. Three small releases also give three measurement points for the dementia test, the cost-leak rate, and the idle-cost regression. |
| [MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md) telemetry needs per-turn tier provenance to diagnose leg failures. MQ-11 in [v0.3.0 plan](v0.3.0-plan.md#memory-quality-follow-ups-v03x-and-beyond) and step 3 of [RFC 0026 §Phase 3](rfcs/0026-declarative-facts-tier.md#phase-3-reinforcement--retraction) name the same `MemoryBudget`-allocator instrumentation. | "Cost Gate" in v0.3.2 changes a code-review-able invariant ("does this path acquire a lease?") that downstream RFCs must respect. New v0.4.0 RFCs (0010 sub-agents, 0028 decision policy) need to know about it. | Cross-link from each v0.4.0 RFC to RFC 0023's [§B Lease Lifecycle](rfcs/0023-llm-call-leasing.md#b-lease-lifecycle) at the time their PR plans are authored. Add a checklist line to [RFC review template](rfcs/RFC_TEMPLATE.md): "Does this RFC introduce a new LLM-call origin? If yes, name its `Cause` enum." |

## Open questions

1. **Should v0.3.1 fold MQ-1 (outcome-tagged importance, [RFC 0020 OQ #6](rfcs/0020-interaction-lifecycle.md#open-questions)) alongside RFC 0026?** MQ-1 is a small carve-out of `0020-pr-plan.md` and unblocks MQ-7 (salience reinforcement, [RFC 0008 calibration review](rfcs/0008-calibration-review.md)). Lean toward yes — it is one extractor-prompt patch and lands cleanly with the facts extractor that RFC 0026 Phase 1 introduces. Decide at `0026-pr-plan.md` authoring time.
2. **Does v0.3.2 need a separate "RFC 0023 follow-up: chat reply caching"?** [RFC 0023 §Open Questions #6](rfcs/0023-llm-call-leasing.md#open-questions) flags the response-cache placement when chat or channel-reply paths gain caching. Out of scope for v0.3.2; track as a tracked-issue follow-up on RFC 0023 PR 4 if it surfaces.
3. **Should v0.3.3 ship a calibration step for the salience threshold ([RFC 0024 §Open Questions #2](rfcs/0024-event-driven-scheduling.md#open-questions))?** Default keeps salience wakes off; calibration needs a week of production reflection-score data. v0.3.3 ships with the default disabled and a tracked-issue follow-up to flip it after a soak.
4. **Bundle v0.3.3 into v0.4.0 if RFC 0024's PR count is small enough?** Phases 1–4 are ~6–8 PRs; below the v0.3.0 bundle's volume. If v0.4.0 master plan opens before v0.3.3 cuts, reassess — but the default is to ship the cost-attribution win independently so the bored-persona regression gate has its own release boundary. Tradeoff with [§Risks row 4](#risks): bundling violates the per-version user-story contract — this only stays open if v0.3.3's "idle" story reads as a half-deliverable of the v0.3.2 cost gate.

## Amendment 2026-06-04 — re-sequence the v0.3.x tail for conversation realism & usefulness ahead of v0.4.0

The prior amendments sequenced the v0.3.x tail by *org-readiness* (confidentiality, membership, identity — the substrate v0.4.0 organizations need). This amendment re-sequences it by **adoption pull**. The active decision is the table below; everything above is preserved as historical record.

### Why this changes

The driving goal is now explicit: **to attract users, the multi-persona conversation must read as realistic and be useful — and that must land before v0.4.0 (organizations).** Measured against that goal, the org-readiness ordering was wrong:

1. **The confidentiality / membership / identity substrate is invisible to a prospective user.** Whether a leadership channel leaks into a public one, or a membership-interval ledger scopes recall, is *correctness-for-organizations* — and organizations are v0.4.0. A newcomer evaluating Persatrix sees only whether the agents *talk like people* and *produce something worth reading*.
2. **The realism + usefulness story is a tight, already-half-built cluster — RFC 0030 + RFC 0034 + a prompt change** — that barely touches the confidentiality stack. Manual testing of the v0.3.6 group channels surfaced the gap directly: personas talk like assistants, answer questions aimed at someone else, pile on, and never converge. See the [RFC 0030 relevance-gated-response amendment](rfcs/0030-amendment-relevance-gated-response.md) for the response-gate analysis.
3. **The org substrate can ride the v0.4.0 on-ramp.** It is required *before* organizations, not before adoption — so it slips to just ahead of v0.4.0 rather than anchoring v0.3.x patches.

The "useful" target is staged. Minimal usefulness is a productive **brainstorm**; full usefulness is **reasoning toward a decision**:

| Structured meeting / negotiation | convene → propose → deliberate → decide → ratify | v0.5.0 ([RFC 0012](rfcs/0012-protocols-organizations.md) Phase 4) |

v0.3.x delivers realism + brainstorm-level usefulness; reasoning is a v0.4.x stage on top.

## Amendment 2026-06-23 — add v0.3.10 (Reasoning Before Posting) as the next realism rung

The [Amendment 2026-06-04](#amendment-2026-06-04--re-sequence-the-v03x-tail-for-conversation-realism--usefulness-ahead-of-v040) re-sequenced the v0.3.x tail by **adoption pull** and ran it through v0.3.9 (*Conversations you can mine*), closing the realism-and-usefulness arc and pointing at v0.4.0 (organizations). This amendment adds **one more v0.3.x rung before v0.4.0** — and it is squarely on the same adoption-pull axis, not an org-substrate detour.

### Why this changes

v0.3.9 closed the *brainstorm* rung of the [usefulness ladder](#the-usefulness-ladder): conversations converge, terminate, and can be mined. But manual testing of the v0.3.6+ group channels surfaced a realism gap the relevance gate only *partly* closed — personas still **post reflexively**: they answer questions aimed at someone else, restate a peer, pile on with "I agree" turns, and compose the first thing the model produces rather than the most useful thing. The v0.3.8 Tier-B salience gate attacked *eligibility* (a numeric score with a bias-to-silence threshold) but a numeric threshold can neither articulate "I'd only be agreeing" nor rescue a low-scored turn that would add real substance, and once admitted a persona composes in a single unconsidered pass.

[RFC 0051 — Reasoning Before Posting](rfcs/0051-reasoning-before-posting.md) is the realism lever that closes it: a private per-turn deliberation that generalizes the shipped RFC 0030 Tier-B bid into a structured `{ should_post, plan }` verdict — **semantic silence** (decide "nothing to add" *with a reason*, before the expensive compose) and **considered posts** (compose under a private plan). It is a v0.3.x-sized realism patch with **no v0.4.0 dependency** (it reuses the shipped RFC 0030 Tier-B seam, the RFC 0050 config surface, and the RFC 0023 lease), and it is the natural next rung after "conversations that converge" — **conversations worth posting into**.

## Amendment 2026-06-28 — add the autonomous agent-only channel as the v0.3.x realism capstone

The [Amendment 2026-06-04](#amendment-2026-06-04--re-sequence-the-v03x-tail-for-conversation-realism--usefulness-ahead-of-v040) re-framed the v0.3.x tail by **adoption pull** and ran the realism arc through v0.3.9; the [Amendment 2026-06-23](#amendment-2026-06-23--add-v0310-reasoning-before-posting-as-the-next-realism-rung) added v0.3.10 (reasoning before posting) as the next rung. This amendment adds **one more rung on the same adoption-pull axis**, and it is the one that closes the arc honestly: the **autonomous agent-only channel** — a channel where personas discuss a topic with *no human in the loop*. The active decision is the table below; everything above is preserved as historical record.

### Why this changes

Every rung of the realism arc (v0.3.7→v0.3.10) was validated **with a human in the loop** — a human seeds the topic, watches, and implicitly keeps the discussion alive and on track. That leaves a gap measured against the adoption goal:

1. **The arc is only demonstrated with a human in the chair.** A prospective user evaluating Persatrix sees good conversation *because a human is steering it*. The honest proof that the realism work stands on its own is to remove the human — convene a roster on a topic and watch it discuss, converge, and synthesize untouched. That "watch it run by itself" moment is also the **single best adoption demo** the project can ship before v0.4.0.
2. **The substrate is almost entirely shipped** — agent-to-agent channels with no human participant already work at the session layer ([memory-scope-axes.md](memory-scope-axes.md) "channel with no human participant" case), agent posts wake each other (RFC 0024 `InboundEventWake`), and floor control / chair / end-of-interaction / reasoning-before-posting are all in. This is **assembly (self-convening) plus three new mechanisms (§C–§E)** — each *extends a shipped governance invariant rather than re-tuning it globally* (see [RFC 0052 §C–§E](rfcs/0052-autonomous-agent-channels.md#c-the-central-tension--anti-collapse-cadence)) — not a new subsystem: a v0.3.x-sized lever, no v0.4.0/org dependency. (One of the three — the wallet synthesis reserve — is new core wallet accounting with no shipped analog, not a tuning knob; size it as such.)
3. **There is a real design tension worth naming** (below) — which is exactly why it deserves its own rung rather than being folded silently into v0.4.0.

### The central tension this rung resolves

The realism arc deliberately installed **bias-to-silence and converge-then-terminate** pressure: RFC 0051 semantic silence is **on by default**, and the RFC 0030 chair stall-escalation forces one chair turn — and, crucially, **at most one per interaction** (the CE5 loop guard) whose job is to synthesize-and-close or hand off. With a human present these are correct. **With no human they compose into premature death** — everyone reasons "the others can cover this," all stay silent, the single escalation fires, its handoff also draws silence (CE5 is spent), and an unattended channel converges to a near-empty transcript. The new rung's design content is the **anti-collapse cadence** that supplies counter-pressure — concretely, *generalizing CE5's one-escalation-per-interaction ration to a per-agenda-item one* (a chair that advances the *agenda* on a stall, with the per-item loop guard preserved, plus a best-effort liveness target — not an enforceable floor, since semantic silence cannot be compelled), **scoped strictly to autonomous channels** so the human-channel defaults are untouched. Plus a **mandatory cost cap with a reserved synthesis allowance and a new deterministic bounded close** — there is no human circuit-breaker on an unattended channel, and because the shipped wallet fails leases closed and a chair cannot close an interaction (RFC 0030 CE4/CE6), neither the close nor its synthesis is free reuse. Full design in [RFC 0052](rfcs/0052-autonomous-agent-channels.md).

### Usefulness-ladder placement

This rung stays on the **brainstorm** rung of the [usefulness ladder](#the-usefulness-ladder) — discuss → converge → synthesize — with the human removed from every step. The **reason-toward-a-decision** version (the roster weighs tradeoffs and emits an auditable recommendation) remains gated on the [RFC 0028 decision engine](rfcs/0028-agent-decision-policy-engine.md) and stays **v0.4.x**. So the scope line is: *human-free brainstorm now; human-free deliberation when the v0.4.x decision engine lands on top.*

## Amendment 2026-08-19 — v0.3.15 + v0.3.16: attribution and audience before the v0.4.0 train

The [Amendment 2026-08-02](#amendment-2026-08-02--v0313--v0314-the-two-release-tail-to-v040) shipped as v0.3.13 (2026-08-05) and v0.3.14 (2026-08-19). Both landed their headline promise, and both closed by naming residuals rather than by clearing the board. This amendment ratifies **two** further patch releases before the v0.4.0 train opens, derived not from the residual list alone but from a sweep of the conversational **topologies** the product claims to serve. The active decision is the table below; everything above is preserved as historical record.

### Why this changes

1. **The v0.3.14 close already assigns three items to v0.3.15.** [ISSUE-0082](issues/ISSUE-0082-orchestrator-per-request-session-principal-emission.md) **R-1** (per-speaker interaction scope — the room-scoped close record aggregates every speaker's turns and extracts facts from the aggregate under whichever principal closed) and **R-2** (the orchestrator hop drops the tenant, so every cascade descending from a persona's reply writes to the shared `local` principal), plus [ISSUE-0130](issues/ISSUE-0130-catchup-replay-rederives-memory-under-default-principal.md) shape **(b)** (persist `principal_id` on `messages`, channel store v11 → v12). Their designs, the group-channel MT that can observe them live, and the workstream plan are in draft [#822](https://github.com/mkhomutov/Persatrix/pull/822), whose Phase 0 gate measures against the v0.3.14 tag — so the work starts now and not before.
2. **A topology sweep found one gap of the same class that no issue covered.** R-1 splits the close record by PRINCIPAL, and only authenticated humans have one: emission is `auth.mode: enabled`-only and a persona's outbound publish re-enters unauthenticated, so the whole fleet shares `local`. Derived memory therefore records *what* was said and *where*, never *who said it* — a `Fact` carries `subject` (who it is ABOUT) and no speaker, and the interaction it is extracted from resolves to `group:<channel_id>` in the topology that matters (a DM already keys its scope on `sender_id`; a shared room is where the speakers collapse). Filed as [ISSUE-0131](issues/ISSUE-0131-derived-memory-has-no-speaker-attribution.md). It rides v0.3.15 because it shares R-1's **record-shape decision** — the key-vs-column question the #822 Phase 0 gate exists to answer — and deferring it means re-opening that decision after R-1 has already built on one answer. It does **not** share 0130(b)'s migration: `principal_id` on `messages` is a Go channel-store change (v11 → v12), while the speaker axis lands on the derived rows in the Python persona-memory store (migration 17 → 18). Two stores, two migrations, one shared decision.
3. **One operational failure voids the live verification every one of these releases depends on.** [ISSUE-0125](issues/ISSUE-0125-agents-never-reregister-after-orchestrator-restart.md) — the agent registry is in-memory, agents self-register exactly once, and an orchestrator restart leaves the fleet permanently mute while `/healthz` stays green and publishes return 201. It has been a recorded quirk since v0.3.0, it voided an MT arc on a paid provider, and it has accreted a documentation debt of its own ([ISSUE-0126](issues/ISSUE-0126-mt-orchestrator-restart-registry-note-missing.md): eight manual tests prescribe a restart and none warns about it — a ninth, [MT-MEMORY-MULTIUSER-001](manual-tests/MT-MEMORY-MULTIUSER-001.md), carries the one warning PR #823 wrote). Every release in this doc is gated on a live MT; v0.4.0 multiplies dispatch targets. Fix it before the train, and then take ISSUE-0126's option 1: **delete that one warning** and confirm the eight restart steps are safe as written — rather than writing the eight notes that were never written.
4. **The human→persona→human boundary is asserted at channel granularity, not at person granularity.** The RFC 0037 §D gate ranks each entry's `protection_level` against the acting CHANNEL's classification; who is in the room is not an input. With the §A stamping default `internal` for both a DM and an ordinary channel, and facts cross-room by default since RFC 0049 Phase 1, a fact learned from one person in a DM is admissible in a room where a different person is present. The coarse control (raise the DM's classification) works and costs the feature everywhere else. Filed as [ISSUE-0132](issues/ISSUE-0132-memory-egress-gate-blind-to-room-audience.md) and slotted **v0.3.16**, because it needs the ISSUE-0131 attribution to reason against, and because RFC 0012 clearance builds directly on this gate.
