### 3.1 Required Upgrade Notes

| Notable change | Detail |
|----------------|--------|
| **[No migrations — drop-in upgrade]** | **No store migrations this cycle.** The channel store stays v11 and persona-memory at migration 17, both already at the v0.3.12 tag. Nothing to run, and — unlike v0.3.12 — **no downgrade caution**. |
| **[Behaviour — the fix, not a regression]** tool recalls now obey the run scopes | An agent-initiated memory-**tool** recall no longer returns rows outside the request's epoch/session. **The v0.3.12 `--epoch`/`--session` Known-Gap caveat is retired** ([ISSUE-0118](issues/ISSUE-0118-tool-recall-bypasses-epoch-session-scopes.md)). A tool recall that previously surfaced foreign-epoch rows now excludes them: that is the fix working. Operators who unknowingly *depended* on the leak (e.g. a probe run under a throwaway epoch that still saw live history) will see empty results — the release notes say this in as many words, and quote the Leg 4 provenance line as the closing evidence. |
| **[New capability]** per-channel `max_cascade_depth` | Declare it in `channels.yaml` or edit it live (`PATCH /api/v1/channels/{id}/config`, the web console's Channel settings panel, or `persatrix channel config set <ch> max_cascade_depth=N`). Zero/absent inherits the fleet cap; it can never be config-disabled. **Raising one channel past the fleet default means raising the fleet cap — and the aligned `agents/dispatch.py` pin — first**: the Python dispatcher's defense-in-depth cap is a per-process global, so an above-fleet per-channel value is unreachable. The YAML loader rejects it; a live edit applies with a loud server-side warning rather than a reject, so a running channel is never bricked into a restart. |
| **[Behaviour — render only]** bounded facts-header subject | The `Known facts about <subject>:` block header renders the subject through a bounded template (4 words / 48 chars, then `…`). Sized off the legitimate subject population, so in-bounds subjects render **byte-identically**; storage, the fact rows, grouping and recall matching are unchanged ([ISSUE-0116](issues/ISSUE-0116-fact-subject-renders-unquarantined.md)). |
| **[Wire]** no protobuf changes | No new or changed proto fields this cycle. The REST surface gains only the additive per-channel knob on `PATCH …/config`; old clients are unaffected. |
| **[Dependencies]** | **No new direct dependencies in any ecosystem.** `make notices` is expected to produce no delta. |
