## Why this plan exists

Three reasons v0.3.3 deserves an umbrella rather than a bare RFC 0024 PR plan:

1. **One RFC, multiple cross-RFC commitments.** Phase 1's [`SyncDispatchHandle`](rfcs/0024-event-driven-scheduling.md#b1-synchronous-dispatch-callers-under-the-queue-model) preserves the dispatch return-value and await-serialisation contracts; Phase 3 introduces a write-side `salience` field and a `source_span_id` attribute, neither of which exists today (per [§F failure-mode row 3](rfcs/0024-event-driven-scheduling.md#f-failure-modes)); Phase 4 reshapes the channel-message dispatch path RFC 0011 shipped in v0.3.0. The umbrella promotes these to plan-level gates rather than burying them in PR scope.
2. **`wake.kind` is the v0.3.2 → v0.3.3 hand-off.** [RFC 0023](rfcs/0023-llm-call-leasing.md) shipped lease wiring in v0.3.2 with `wake.kind` reserved as a lease-request attribute; RFC 0024 Phase 1 is when the attachment point actually carries a value other than `"tick"`. The cost-attribution surface v0.3.2 ratified must not silently regress when the wake taxonomy expands.
3. **The "bored persona costs nothing" promise needs a build-gated regression test.** [RFC 0024 §Test Strategy](rfcs/0024-event-driven-scheduling.md#test-strategy) defines a 60-second cost-regression CI gate — *the* v0.3.3 acceptance. The umbrella makes it a release-blocker, not a per-PR convention.

Single RFC, so no inter-RFC sequencing tension — only Phase-internal ordering, which RFC 0024's own [§Phased Implementation Plan](rfcs/0024-event-driven-scheduling.md#phased-implementation-plan) owns.

## Decision on the uncommitted v0.3.x rows

The [v0.3.x-sequencing.md §Updated decision](v0.3.x-sequencing.md#updated-decision) table still lists *"v0.3.x — uncommitted: RFC 0030 Phase 1; RFC 0031 Phases 2–4"* — flagged at v0.3.2 plan opening as **"Deferred to v0.3.3 plan opening or a dedicated v0.3.x plan"**. This plan is that opening; the decision:

- **RFC 0031 Phases 2–4 are re-homed to a dedicated v0.3.4 patch.** Per the recall-filtering / [ISSUE-0051](issues/ISSUE-0051-per-session-memory-namespacing-channels.md) closeout, Phases 2–4 carry the F-3 fix as their own user-facing story. Bundling into v0.3.3 dilutes the idle-cost contract; the v0.3.4 plan will open after v0.3.3 cuts and will name `docs/rfcs/0031-phase2-pr-plan.md` (drafted in [#383](https://github.com/mkhomutov/Persatrix/pull/383)) as its Phase 1 input.
- **RFC 0030 Phase 1 is not absorbed into v0.3.3.** Layer 1 is unblocked (RFC 0023 Phase 1 shipped), but absorbing gives v0.3.3 two stories. Re-homed to a dedicated v0.3.x plan or v0.4.0, whichever opens first.

Both rows stay `v0.3.x — uncommitted` in the sequencing doc until their absorbing plans open.

## Acceptance for v0.3.3

The user-facing promise — *"a persona with no scheduled work and no inbound traffic costs nothing — no SQLite recall query, no `_inject_memory_context`, no provider activity, no wallet lease requested"* — is met when:

- The "bored persona" cost-regression CI gate from [RFC 0024 §Test Strategy](rfcs/0024-event-driven-scheduling.md#test-strategy) is green and wired to run on PRs touching the wake-path file set named there.
- Channel-message dispatch goes through `event_loop.enqueue(InboundEventWake(event))` directly, not through `scheduler.wake()` ([RFC 0024 Phase 4](rfcs/0024-event-driven-scheduling.md#phased-implementation-plan)).
- [RFC 0017 §F](rfcs/0017-persona-memory-injection-budget.md#f-empty-context-tick-short-circuit) guard remains in place but is documented as vestigial; cross-link naming RFC 0024 Phase 5/6 as the deletion path added to the RFC 0017 file.
- [`SyncDispatchHandle`](rfcs/0024-event-driven-scheduling.md#b1-synchronous-dispatch-callers-under-the-queue-model) preserves the `list[AgentAction]` return contract for `SendChatMessage` and the await-serialisation contract for `ActionExecutor.dispatch.wait_for`; existing chat and cascading-dispatch tests pass unchanged.
- `wake.kind` is emitted as a metric attribute on `agent.wake.{inbound,scheduled,salience,dropped}` and as a lease-request attribute at the [RFC 0023](rfcs/0023-llm-call-leasing.md) wallet boundary.
- New manual test `MT-IDLE-001` ships green; existing `MT-COST-004` still passes under the event-driven model.
- `agents/event_loop.py` exists; `TickScheduler` is a thin adapter synthesising `ScheduledWake(timer_id="legacy_tick")`.
- Phase-3 prerequisite `source_span_id` attribute lands on memory writes (or the coarser fallback from [§F row 3](rfcs/0024-event-driven-scheduling.md#f-failure-modes) ships in its place) before `SalienceWake` is enqueued.
- Phase-3 `salience_threshold` default set above conservative scores per [§D](rfcs/0024-event-driven-scheduling.md#d-salience-triggered-wakes) — observable but disabled by default until calibrated.

Out of acceptance: Phase 5 deprecation warning; Phase 6 guard deletion; RFC 0030 Phase 1; RFC 0031 Phases 2–4; RFC 0033; RFC 0034 Phases 2–3.

Source of truth lives in [v0.3.x-sequencing.md §New dependency chain](v0.3.x-sequencing.md#new-dependency-chain). This is the v0.3.3 slice:

```
v0.3.2 complete (✅ released 2026-05-20)
    │
    └── RFC 0024 (Event-Driven Agent Scheduling — Phases 1–4)
            ├── depends on RFC 0005 (closed), RFC 0011 (closed), RFC 0017 (closed)
            ├── consumes RFC 0023 (shipped v0.3.2) — `wake.kind` lights up as a lease attribute
            ├── Phase 1 — EventLoop + WakeEvent + SyncDispatchHandle (preserves dispatch contracts)
            ├── Phase 2 — autonomy.timers config + per-agent SQLite scheduled_wakes table
            │              (timer registry; OQ §1 resolved-before-Phase-2 to per-agent SQLite,

            ├── Phase 3 — write-side salience + SalienceWake + source_span_id loop-back guard
            │              (threshold default keeps salience wakes off until calibrated)
            └── Phase 4 — channel-message dispatch routed through event_loop.enqueue
                 │
                 →  v0.3.3 — Idle Truly Idle
```

**Ordering**: RFC 0024 is the only workstream. Phase 1 → 2 → 3 → 4 is sequential per the RFC's own phase boundaries; the PR plan owns sub-phase ordering.

## Risk and mitigations

| Risk | Mitigation |
|------|------------|
| Phase 1's `SyncDispatchHandle` is subtle — three contracts ride on `EventDispatcher.dispatch()` (return-value, await-serialisation, queue-mediated ordering). A naïve "enqueue and park" silently breaks chat and timeout accounting. | Contract analysis recorded in [RFC 0024 §B.1](rfcs/0024-event-driven-scheduling.md#b1-synchronous-dispatch-callers-under-the-queue-model). The Phase 1 PR's `test_event_loop.py` asserts the handle resolves for chat-style callers and stays unresolved for fire-and-forget callers. |
| Phase 3 introduces two new memory-write attributes (`salience`, `source_span_id`) that don't exist today. Coupling them in one phase increases partial-landing risk. | [§F row 3](rfcs/0024-event-driven-scheduling.md#f-failure-modes) commits to either shipping `source_span_id` with `SalienceWake` or the coarser fallback. The Phase 1 PR plan names which path Phase 3 takes. |
| Phase 4's channel-dispatch rewrite touches the v0.3.0 channels surface (stable since 2026-05-12). Regression surfaces as channel-message latency spike or message loss. | Phase 4 keeps `scheduler.wake()` working for non-channel callers; the change is mechanical at the call site. The cost-regression CI gate already triggers on `agents/server_servicers.py`. |
| 60-second bored-persona CI gate is non-trivial CI time per PR. Risk of being skipped or moved to nightly. | The gate's trigger set ([§Test Strategy](rfcs/0024-event-driven-scheduling.md#test-strategy)) covers every file that could re-introduce the polling-cost class. Moving to nightly defeats it; the Phase 1 PR plan documents the PR-trigger shape as a release-blocker invariant. |
| RFC 0030 Phase 1 becomes shippable mid-flight (unblocked since v0.3.2) and pressure builds to absorb. | [§Decision on the uncommitted v0.3.x rows](#decision-on-the-uncommitted-v03x-rows) is the arbiter — re-homed elsewhere. Absorbing makes v0.3.3 two-story and dilutes the idle-cost regression-gate framing. |
| `tick_interval_seconds` legacy config keeps working through Phase 5, but a persona relying on polling cadence as implicit heartbeat would silently change behaviour if the synthesised `ScheduledWake(timer_id="legacy_tick")` doesn't reproduce the previous cadence exactly. | Phase 1 includes a config-compat test asserting unmodified `agents.yaml` (`tick_interval_seconds: 60`) produces the same observable wake cadence as `timers: [{id: "legacy_tick", interval_seconds: 60}]`. |
| Master plan rots as Phase 2 progresses. | Status updates are part of every step PR's checklist (see [ROADMAP hygiene](#roadmap-hygiene)). Reviewers reject step PRs that flip RFC status without touching the per-RFC plan's progress table. |
