## Schema / migration state

**Four migrations across two separately-versioned stores** — so the checklist cannot reuse v0.3.14's no-migration statement.

| Store | Migration | What it does | Consumer |
|---|---|---|---|
| Channel (Go) | **v11 → v12** | `principal_id` on `messages`, stamped server-side at publish | B2's replay seed |
| Channel (Go) | **v12 → v13** | *Repair.* v12's backfill was inverted `'local'` → `''` at the B2 review, and editing an applied migration reaches only stores that never ran it | ships **with** its consumer |
| Persona-memory (Python) | **17 → 18** | `speaker_id` on the derived tiers, landed dormant at A3 | A4's projection |
| Persona-memory (Python) | **19** | An index on the re-keyed close predicate | no new reader |

Two are not the ordinary "migration ahead of its consumer" shape, and the checklist states each rather than letting the count imply uniformity:

> **v13 is a repair that ships *with* its consumer, not after it.** `applyMigration` dispatches on `user_version`, so a store already at v12 keeps the inverted backfill forever — and its first post-upgrade catch-up derives an authenticated person's content into the shared `'local'` tenant, which B2's guard would then make **permanent**. v13 detects an affected store exactly (the column's recorded DEFAULT reads `'local'` there, `''` elsewhere) and rewrites those rows.

> **19 has no reader to be ahead of.** It adds no column and changes no read *result* — only the plan. Both its consumers (`update_episode_summary`, and the shape-(b) guard) already existed.

The scope lock's "two stores, two migrations" says the stores are **disjoint**, not that there is a budget of two — as the [master plan's acceptance](v0.3.15-plan.md#acceptance-for-v0315) states.

**Downgrade caution — new this cycle.** v0.3.14 was drop-in both ways; v0.3.15 is not. A store carried forward to channel v13 or persona-memory 19 and then run under a v0.3.14 binary meets a `user_version` from the future. The checklist states forward as supported and backward as unsupported, rather than repeating v0.3.13's "drop-in" line.

## Wire-compatibility state

**No protobuf changes this cycle** — A1/A2 moved orchestrator-internal state and the `persatrix-principal` header shipped in v0.3.14. PR 4 confirms with `make proto && git diff --exit-code` under the CI-pinned protoc rather than assuming it. The REST surface gains one **additive** field: `principal_id` on `channelMessageResponse` (B1), which a v0.3.14 client ignores.

Two deliberate **behaviour** changes ride the release, both release-note obligations:

1. **Group-room memory fragments per speaker per tenant** — the promise applied *inside* a room, the trade v0.3.14 made per person. Room continuity is untouched: transcript and verbatim history are not principal-scoped.
2. **`agent.interactions.closed.by_<reason>` changes shape**, because a room-wide close now fans across records rather than closing one.

Under `auth.mode: disabled` the principal axis stays **byte-identical** — and the speaker axis deliberately does **not**, which is the point of Leg 8.

## Manual test state

[MT-MEMORY-GROUP-TENANT-001](manual-tests/MT-MEMORY-GROUP-TENANT-001.md) is at **v1.1** — widened by B2 with the Leg 9 restart leg and the Leg 4 triples, and **never run against the post-fix column**. That debt is the release gate. Ten legs (0–9): Alice authenticated; the disclosure + cascade; R-2's relayed write; the persona-publish close; R-1's derived write; the travel; the other close trigger; Bob's absence bar; `disabled` mode; the replayed write across a restart.

**Live-run guidance** (carried forward, one item now retired):

- **Machine-pace the whole arc in one script** — governance windows race idle operators.
- **The manual agent restart is no longer required**: C1 makes the fleet self-heal, and Leg 9 is where that is *proved*. Both ISSUE-0126 warnings are already deleted from the MT, so the run cannot fall back to the workaround by accident. Drive the restart on a transition that is **not** `TRANSIENT_FAILURE` — an `IDLE` cycle — or the leg passes without exercising the watcher.
- Run with `PERSATRIX_MEMORY_PROVENANCE=1` but do **not** treat it as the evidence: the `relationship` tier emits no admission line ([ISSUE-0122](issues/ISSUE-0122-relationship-tier-emits-no-provenance.md)), so the `memory.db` columns are authoritative.
- sqlite queries ride the agent runtime's `python3` — the image ships no `sqlite3` CLI.

## Dependency notices state

**No new direct dependencies** — but unlike v0.3.14, the graph is **not** byte-unchanged since the tag, so PR 4 should expect a `make notices` delta rather than treat one as a red flag.
