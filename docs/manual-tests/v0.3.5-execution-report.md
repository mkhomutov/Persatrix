by an automated counterpart that **was** run green here, so the release gate is
not weakened — only the *live-operator* confirmation of these specific legs is

## MT-SESSION-003 — F-3 recall isolation (live + gate)

Live on the OpenAI stack with ember-owl. The **write contract** was scoped at the
persona boot (`PERSATRIX_SESSION_ID`), and the **recall filter** was exercised on
the resulting persisted rows.

| Step | Expected | Observed | Result |
|------|----------|----------|--------|
| dispatch | chat→persona→reply live | `ember-owl: "Got it, Alex. Enjoy your time with Mira later!"` (OpenAI). | ✅ |
| write-tag | episode tagged `arc-one` | Persona booted under `PERSATRIX_SESSION_ID=arc-one` → after interaction close, `episodes` row `session_id='arc-one'` lands, coexisting with a `legacy` row (`episodes by session: [('arc-one', 2), ('legacy', 1)]`). | ✅ |
| **recall isolation** | fresh session excludes prior | Default-recall predicate (`session_id IN (active,'legacy')`) on the live rows: under `arc-one` → `{arc-one, legacy}`; under **`arc-two` → `{legacy}` only — the arc-one episode is EXCLUDED**. The F-3 promise, on persisted rows. | ✅ |
| legacy carve-out | always visible | `legacy` rows are in `arc-two`'s default-recall set; `arc-one`'s are not. | ✅ |
| within-session continuity + LLM-reasoning | persona acts on recalled fact | Carried by [`test_session_continuity.py`](../../tests/integration/test_session_continuity.py) `TestSingleSessionArcContinuity::test_arc_reads_back_through_every_tier` + `TestMultiSessionDefaultIsolation::test_arc_2_default_recall_excludes_arc_1` (green). | ✅ (gate) |

**Finding (recipe corrected).** The DM-chat episode is written at *interaction
close* in the persona's background loop, tagged with the session the
persona-runtime **snapshotted at boot** — a per-CLI-invocation `--session` /
`PERSATRIX_SESSION_ID` governs the *recall query* and channel-binding for that
call but does **not** retag the asynchronous close-path write in a long-running
persona. The recipe now scopes an arc at the persona's boot (the MT-SESSION-001
contract / the dementia-test Setup), not per invocation. Also: `--session`
resolves against the registry first (an ad-hoc id 404s — use `PERSATRIX_SESSION_ID`
or `session new` first).

**MT-SESSION-003: ✅ Pass.** Cross-session recall isolation verified live on
persisted rows; the within-session continuity + multi-session no-bleed behaviour
is the green continuity bridge.

## Follow-ups

- **F-1 — DM-chat close-path write follows the persona's *boot* session/epoch, not a per-CLI-invocation override** (new this run; severity: low — operator-documentation, **not** an isolation defect). The asynchronous interaction-close write is tagged with the session/epoch the persona-runtime snapshotted at boot; `--session`/`--epoch` on a single `chat` call governs the recall query + channel-binding but does not retag that write in a long-running persona. The new MT recipes (MT-SESSION-003 / MT-EPOCH-001) now scope arcs at the persona boot (the MT-SESSION-001 contract). The structural isolation itself is intact (proven by the gates). Worth a one-line note in the [sessions guide §4](../guides/sessions.md) operator path during [release-prep PR 2](../v0.3.5-release-prep-plan.md#pr-2--readme--roadmap--sessionsepochs-guide-verification--release-checklist).
- **F-2 — epoch switch on a reused `(agent,user,room)` can append to the prior interaction** (new this run; severity: low). A turn issued right after an epoch reboot can join an interaction opened under the prior epoch, so its close-path episode keeps the prior `epoch_id` (observed: an episode `live` while the relationship row took `trial-7`). Start a fresh interaction when switching epochs; recipe notes this. Not a recall-filter defect.
- **F-3 — Go-only gates not runnable on this host** (environment; severity: none — carried). The alias cost-attribution gate + the Go suites + `test_session_operator_surface.py` need a Go toolchain; carried by CI + the Python counterparts. [Release-prep PR 4](../v0.3.5-release-prep-plan.md#pr-4--final-pre-tag-verification--release-notes) re-confirms on the post-bump tip.
- **F-4 — configured Anthropic key invalid; ran on OpenAI** (environment; severity: none). The v0.3.5 surface is provider-independent; the live legs ran on the valid OpenAI peer (config-driven, RFC 0033).
