## Live provider cost

⬜ Pending. **Capture before `docker compose down -v`** — the v0.3.14 arc lost its figure to teardown and reported cost as *not measured*.

**P-1 (pre-run finding) — the v0.3.14 checklist's cost workaround does not work as written.** [Checklist §1.1](../v0.3.14-release-checklist.md) instructs `docker compose logs orchestrator | grep '"op":"settle"'` and says it "yields lease finalization carrying `actualUSD`". Verified against the code during this PR's prep, both halves are wrong:

- `"op":"settle"` matches `wallet: lease finalized` (`internal/wallet/wallet.go`), which carries `actual_input_tokens` / `actual_output_tokens` — **no USD figure at all**.
- `actualUSD` is on a *different* line with no `op` field: `provisional charge reconciled` (`internal/cost/cost.go`), carrying `estimatedUSD` and `actualUSD`.

Both are `Debug`. The compose stack does emit them — it runs the orchestrator `--env development`, and `loggerLevel` returns `DebugLevel` there — but a `production` deployment logs neither, so cost is not recoverable from logs at all in that configuration. `persatrix cost` remains unimplemented.

`scripts/manual_tests/mt_group_tenant_evidence.py::collect_cost` reads the correct line and sums it. **Carry this correction into the v0.3.15 checklist at PR 2** so the instruction that failed once does not ship a third time.

| | Value |
|---|---|
| Reconciled leases | **13** (Legs 0–4, including the re-runs) |
| Total `actualUSD` | **$0.0689** |

Measured, not estimated — the bar the v0.3.14 arc missed. Read live before teardown via `collect_cost()`.

### P-1 — the cost-capture workaround is wrong as documented — **prep finding, fixed; correction carried to PR 2**

Recorded above. Found during prep by verifying the instruction against the code rather than following it, and **confirmed live**: `collect_cost()` read $0.0689 off the correct line during this run. The v0.3.14 checklist row stays unchecked until PR 2 rewrites it.

### F-1 — the auth gate passed on a comment, and the arc read as an R-2 failure — **tooling defect, fixed in this PR**

The first clean-looking Leg 2 reported **5 dispatches, 5 tenant-less** — the exact signature of R-2 being broken. It was not. `config/security.yaml` had `auth.mode: disabled`, so every request resolved to the anonymous `local` identity: messages stamped `principal_id='local'`, dispatches carried no `principal.id`, and the arc completed green while proving nothing.

The preflight's auth gate tested `"mode: enabled" in text` and matched a **comment** eleven lines above the real setting, which reads *"a typo in `mode: enabled` must not silently boot an unauthenticated…"*. The gate that exists to stop a leg passing vacuously was itself passing vacuously.

Caught only by checking storage instead of trusting the artifact — Alice's own message read `principal='local'`, which no correct run produces. Two fixes: the file gate now **parses YAML**, and a second **live** gate probes a `policyAuthenticated` route and requires `401`, because the file and the running process disagree whenever the stack booted before the edit.

**The general lesson for Legs 5–9**: an artifact that looks like a finding is not one until the storage side agrees.

### F-2 — the persona fleet gets `401` on the roster fetch under `auth.mode: enabled` — **product finding, unslated**

All three agents logged `channels: roster fetch http://orchestrator:8080/api/v1/agents returned HTTP 401` once at startup. `GET /api/v1/agents` is `policyAuthenticated` ([`internal/server/auth_policy.go`](../../internal/server/auth_policy.go)) and the personas are unauthenticated callers by design — the whole fleet resolves `local`.

They degrade rather than crash, so the arc was unaffected, but the roster feeds `--mention-all` resolution and the RFC 0030 Tier B `salience_max_channel_members` gating. "Auth on ⇒ the fleet cannot read the roster" is a real interaction between RFC 0039 and the channel layer that no gate covers. **Worth its own issue at PR 2.**

### F-3 — `channel config unset` falls back to the *fleet* default, not the channel's YAML — **product finding, behaviour-as-designed but sharp**

Restoring `interaction_idle_timeout_seconds` with `channel config unset` resolved it to **600 `[default]`**, not the `1800` declared for `planning` in `config/channels.yaml`. Once a channel carries store overrides the store is canonical, and `unset` clears to the fleet inherit rather than re-reading the declaration — the RFC 0050 export-first foot-gun, hit live. Restored by `set`ting 1800 explicitly. An operator "undoing" a temporary override this way silently lands on a *different* value than the one they started from.

### F-4 — Leg 3's end-vote quorum never formed; the close was forced by idle — **recorded deviation**

Leg 3 asks for a close driven to an **end-vote quorum** (K=2 within W=3). It did not happen, twice:

- After the wrap prompt, `iron-fox` and `nova-sparrow` both deliberated and returned `should_post: False, reason_code: 'nothing_to_add'` — RFC 0051 silence, working correctly. A persona that says nothing casts no vote.
- After a second, direct prompt naming both, only `nova-sparrow` posted (and did say *"let's close it out"*). K=2 needs **two distinct** voters; `iron-fox` stayed silent again. No `end_vote` or `interaction_closed` line appears anywhere in the orchestrator logs.

**The close was then forced** by lowering `interaction_idle_timeout_seconds` to 30 via `channel config set`, waiting past the window, and sending one cheap bridge turn to trigger the lazy retirement (there is no background sweeper — `ChannelActivity` prunes as it reads). All three personas derived immediately.

**Why this is acceptable evidence for Leg 4, and where it is not.** Leg 4 asserts the *shape* of the derived record — one principal, one speaker, no mixing — and that shape is a property of the record key, not of the trigger. Post-fix the trigger is explicitly supposed to be irrelevant, which is Leg 6's whole claim. What this run therefore does **not** establish is Leg 3's own assertion (that a persona-origin close carries the right tenant) — **Leg 6 must still be run**, and it now carries more weight than planned.

**The MT should not assume emergent behaviour.** Leg 3 is written as "the natural continuation of Leg 1 usually reaches it" — it did not, on a stock roster with a live provider, in two attempts. MT correction 7 records the deterministic fallback.

## MT corrections — seven defects in the procedure itself

Every one of these stopped or silently corrupted the arc. They are fixed in [MT-MEMORY-GROUP-TENANT-001](MT-MEMORY-GROUP-TENANT-001.md) v1.2 and in the driver; recorded here because the *pattern* matters — the MT was authored against a host orchestrator and never executed, so its setup steps had never met a compose deployment.

| # | Defect | Symptom if run as written |
|---|---|---|
| 1 | **Bootstrap path.** `bin/persatrix-server account bootstrap` defaults to `data/accounts.db`; the containerised orchestrator runs `--accounts-db /var/lib/persatrix/accounts.db` on a named volume, and `./data` is not mounted into it. | Leg 0 creates an account the orchestrator never reads. Every later leg authenticates as nobody — and looks fine doing it. |
| 2 | **`-wal`/`-shm` sidecars.** The MT says a bare `rm -f data/accounts.db` at Legs 0 and 7. | The next bootstrap dies `accounts: read user_version: disk I/O error (522)`. This is v0.3.14's F-4; MT-MEMORY-MULTIUSER-001 absorbed it at v1.1, this MT never did. |
| 3 | **Membership must be declared, not joined.** Publishing is membership-gated, but `persatrix channel join` writes only the channel **store** — and `ReconcileConfig` treats a store/config membership divergence as a **FATAL** at startup (RFC 0011 §B, a deliberate loud failure). | `join` + the next restart = an orchestrator **crash loop**. This MT restarts at Legs 0, 7 and 8. The check is symmetric, so both humans must be declared together — declaring alice and joining bob at Leg 7 fails the same way in the other direction. |
| 4 | **`--as` is mandatory on every send.** Its default is the **OS username**, normalized — not the authenticated principal. | `403 … sender is not a member`. Worse if the operator's OS username *is* a member: the arc runs green with turns attributed to a speaker who never spoke, and ISSUE-0131's axis is read off `sender_id`. |
| 5 | **Leg 1's episodes check cannot pass at Leg 1.** It asks for an `alice-person` **episodes** row, but episodes are close-derived and the close is Leg 3. | The stop-and-diagnose gate — the one guarding every later leg — is unevaluable exactly where it is needed. The *live* check that works is the message row's `principal_id` (B1's stamp), available immediately. |
| 6 | **Leg 4's `turn_count > 1` filter is a pre-fix lens.** It was written to catch the merged multi-speaker aggregate. Post-fix, an agent that speaks once owns a **one-turn** record. | The filter hides exactly the rows ISSUE-0131 creates. Observed: every store reported "1 row" and the speaker split was invisible. |
| 7 | **Leg 3 assumes an end-vote quorum forms.** It does not, on a stock roster — see F-4. | The arc stalls with nothing derived. The deterministic fallback (lower the idle timeout, bridge turn to trigger lazy retirement) must be written down, with its consequence for Leg 6 stated. |

**Preconditions the MT should also state**: rebuild the **host** binaries (`--build` refreshes only the containerised orchestrator), and `make reset` before the arc — the volumes otherwise carry the previous release's rows, and Leg 4's assertion is a *count*.
