## Findings & follow-ups

- **F-1 — the per-channel `max_cascade_depth` knob had no CLI surface, and the lockstep guard that exists to catch that was silently blind. FIXED in this PR.** ISSUE-0114 shipped the knob on the server merge switch and the web console's Channel settings panel, but never added it to the CLI's flat-knob registry: `persatrix channel config set planning max_cascade_depth=3` failed client-side with `unknown config knob`, and `config get` omitted the row — the one governance knob an operator most plausibly tunes per channel was **web-only in practice**, in the very release that shipped it. Underneath it, `cli_knob_set_matches_server_merge_switch` parses the flat knobs out of the Go source, and [#810](https://github.com/mkhomutov/Persatrix/pull/810) moved `mergeConfigPatch` into a new `channel_config_merge.go` at the 500-line-cap split — so the parse returned **zero** flat knobs while the existing `!server.is_empty()` assert stayed satisfied on the nested `reasoning.*`/`autonomous.*` knobs alone. Net: the guard degraded to nested-only coverage *and* failed, and the drift it was built to catch shipped anyway. Fix: the knob added to `CONFIG_KNOBS` / the typed view (`#[serde(default)]` for pre-v0.3.13 payloads) / `config_rows`; the guard re-pointed at the moved file **and** taught to assert the flat parse is non-empty, so a future move fails loudly instead of going quiet. Re-verified live on the running stack: `config set … max_cascade_depth=3` now applies and `config get` renders `max_cascade_depth 3 [channel]`.
- **F-2 — CI never ran the Rust test suite. FIXED in this PR.** The `rust` job was `cargo build` + `cargo clippy` only, so all 293 Rust tests — including both CLI↔server lockstep guards — were left to the manual pre-tag sweep. That is precisely why F-1 could merge green and sit on `main` for a full PR. `cargo test` is now a step in the same job (the job **name** is deliberately unchanged so an existing required-status-check rule keeps matching). This is the v0.3.12 F-2 shape repeating in a different blind spot: a gate that exists but no automation runs.
- **F-3 — `MT-MEMORY-CROSSROOM-001` Leg 2b had two procedural gaps, both found by executing it. FIXED in this PR (MT doc).** (a) The leg as written is run in `group:planning` *after* Leg 2, but a natural Leg 2 reply addresses the asker by name, and that reply is then in the room's RFC 0034 conversation window — so the leg cannot distinguish memory-recognition from transcript-reading. The MT now requires an untainted room (ask before Leg 2, or use a fresh channel) and carries the clean-room commands; this is the identity-tier twin of the fresh-channel lesson Leg 4 learned in v0.3.12. (b) The diagnosis note told the operator to read the injected identity line out of `PERSATRIX_MEMORY_PROVENANCE=1`, but the `relationship` tier **does not call** `MemoryBudget.record_admission` (a documented gap in `memory_budget.py`), so no `tier_admitted` line for identity is ever emitted — zero admissions on a Leg 2b turn is the *expected* reading, not evidence of a recall miss. The note now says so and points the triage at the `relationships` query and the delivered `sender_participant_type` instead.

**Triage note.** F-1 is a wiring regression introduced by a v0.3.13 PR, in a surface the [release checklist](../v0.3.13-release-prep-plan.md#pr-2--docs--release-checklist) names as a gate ("knob parity across CLI/web") — so it was fixed in-release rather than deferred, per the [amendment's](../v0.3.x-sequencing.md#amendment-2026-08-02--v0313--v0314-the-two-release-tail-to-v040) pre-authorisation. No MT leg went red, so no in-release fix PR was needed for the arc itself.
