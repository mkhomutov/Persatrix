**Channel**: `group:mt-recall-001`. **Verdict: ✅ Pass** (one non-blocking finding — F-1 / [ISSUE-0107](../issues/ISSUE-0107-recall-channel-id-narrowing-not-canonicalized.md)).

**The load-bearing data-exposure gates pass.** The removal-gap message is unreachable both deterministically (Step 3, `POST …/recall`) and through the real persona (Step 5b — the persona's own un-narrowed query textually matched the gap message yet the membership `EXISTS` clause excluded it, and the persona did not fabricate the secret). A FAIL here would have been a data-exposure defect blocking the cut; neither path leaked.

**Finding F-1 ([ISSUE-0107](../issues/ISSUE-0107-recall-channel-id-narrowing-not-canonicalized.md), medium, non-blocking).** The recall endpoint forwards the body `channel_id` *narrowing* parameter to the store unmodified ([`persona_recall_handlers.go:90`](../../internal/server/persona_recall_handlers.go)), with no `group:` canonicalization — so narrowing by the bare, human-facing channel name silently returns empty (`mt-recall-001` → 0 vs `group:mt-recall-001` → 7 vs un-narrowed → 7, confirmed deterministically). Observed live: `ember-owl`'s own tool call narrowed by the bare name and got nothing, then fell back honestly to its transcript. **Not** a data-exposure / scope-widening risk — narrowing can only reduce the result set past the membership filter; the un-narrowed and canonical paths both work. Triaged as a fast follow, out of scope for this execution-only PR.

**Out of scope (deterministic-only by design).** The §OQ-6 `epoch_id` hard filter is **not** a live MT lever — the production channel store is single-epoch (`live`) and a cross-epoch message cannot be produced through the real publish path; it is pinned by `TestRecallEndpoint_RealPublishPath_ExplicitEpochUnreachable` + `TestRecallMessages_Epoch_HardFilter` (both green above). The cross-session span is pinned by `TestRecallMessages_SpansSessions`; live Step 7 demonstrated it. These are recorded as deterministic-only rather than faked through the publish path.

## Findings & Follow-ups

- **F-1 — recall `channel_id` narrowing parameter is not canonicalized** ([ISSUE-0107](../issues/ISSUE-0107-recall-channel-id-narrowing-not-canonicalized.md), medium, **non-blocking**). `POST …/recall` forwards the body `channel_id` narrower to the store unmodified ([`persona_recall_handlers.go:90`](../../internal/server/persona_recall_handlers.go)) — no `group:` canonicalization, unlike the channel REST paths. Narrowing by the bare channel name silently returns empty (`mt-recall-001` → 0 vs `group:mt-recall-001` → 7 vs un-narrowed → 7). Observed live: `ember-owl`'s own tool call narrowed by the bare name and got nothing, then fell back honestly to its transcript. **Not** a data-exposure / scope-widening risk — narrowing can only reduce the set past the membership filter. Filed as a fast follow; out of scope for this execution-only PR. The data-exposure gate (gap unreachable) is unaffected and passes both deterministically and live.
- **Additive-defaults proof.** Structurally pinned: a persona without `channels:recall` is denied the tool (`test_denied_without_channels_recall`, `test_memory_read_does_not_grant_recall`, `test_wired_tool_enforces_the_persona_gate`), so its prompt is unchanged from v0.3.8; the `?as_participant` window filter is a no-op for a current single-stint member (`TestGetHistoryScoped_CurrentMemberMatchesUnscopedTail`). No regression of the carried-forward v0.3.8 surface.
