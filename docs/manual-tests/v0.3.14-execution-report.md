## MT-MEMORY-MULTIUSER-001 — the live tenant arc

**Result: the boundary holds.** Two authenticated people, one persona, one process: Alice's disclosure landed under her own principal, Bob got nothing of it, and Alice's arc survived Bob's turn. Both principals coexist in storage — isolation is a recall filter, not a delete.

### The recorded principal values — the ISSUE-0082 proof

The MT's "Record the values" rule, read off `memory.db` in the persona container immediately after Leg 3. This is the evidence the release gate is defined on: a green absence bar with every row still reading `local` would prove only that recall was empty.

```
episodes       [('alice-person', 2), ('bob-person', 1), ('local', 2)]
facts          [('alice-person', 2), ('local', 2)]
relationships  [('alice-person', 1), ('bob-person', 1), ('local', 2)]
```

Both emitted principals are present and distinct — `alice-person` and `bob-person`, the RFC 0039 §F verified `participant_id`s of the two bootstrapped accounts. Neither reads `local`. Per-row detail at Leg 1's stop-and-diagnose point:

```
episodes
  {'principal_id': 'alice-person', 'session_id': '01a013df-b0ec-740d-80df-3878ab420863',
   'summary': 'Alice mentioned that her daughter Mira will turn seven next month. …'}
facts
  {'principal_id': 'alice-person', 'subject': 'alice-person', 'predicate': 'has_child_named', 'object': 'Mira'}
  {'principal_id': 'alice-person', 'subject': 'mira',         'predicate': 'has_age',         'object': 'seven (next month)'}
relationships
  {'principal_id': 'alice-person', 'participant_id': 'ember-owl',
   'other_participant_id': 'alice-person', 'interaction_count': 2}
```

The `relationships` row is the sharp one: its primary key omits `session_id`, so before this release Bob's turn would have read Alice's trust and person-facts.

> **Baseline.** A single pre-arc `relationships` row exists under `local` — `ember-owl ↔ iron-fox`, `interaction_count: 0`, config-seeded at persona init, not produced by a turn. It is present in every group-by above and is not a leak.

### Leg 5 — what was and was not shown

Every `alice-person` row was retagged `local` to model a pre-activation corpus (all three tiers, not just `episodes` as the MT's illustrative SQL says — the `facts` tier carries Mira independently and would otherwise serve it regardless of the episode flip). The `relationships` flip collided with the tier's unique key because a `local` twin already existed, so that row was dropped instead.

The storage half is unambiguous:

```
readable by alice-person after the flip:   episodes 0 · facts 0 · relationships 0
still present under local:                 episodes w/ Mira 6 · facts w/ Mira 12
```

Zero rows readable by `alice-person`; the content still stored. **A partition, not a deletion** — the release-notes claim, demonstrated.

**But the persona still said "Mira."** With zero readable rows, that cannot be memory. It is the DM's channel transcript, which is **not principal-scoped** and still held Alice's original message. A fresh-room re-ask was attempted with `--user alice-cleanroom`; the §F claim correctly ignored it (same `session_id`, same DM) — which is itself a clean confirmation of the MT's "`--user` stops mattering under `enabled`" note, but leaves no CLI route to an empty-transcript room for an existing account.

Two consequences, both carried forward:

1. **A release-notes correction.** The planned wording — the reset being *"indistinguishable from 'the persona forgot everything'"* — is wrong where room history is live. The reset partitions **memory**; the conversation window keeps serving recent content. PR 3's Upgrade Notes must say so.
2. **An MT amendment** (F-3 below): Leg 5, and Leg 4's recall, need a fresh-room / empty-transcript rule. This is the identity-tier twin of the trap v0.3.13 hit at its Leg 2b.

## Findings & follow-ups

### F-1 — `persatrix chat` could not authenticate at all under `auth.mode: enabled` — **release-blocking; fixed in this PR**

The very first live turn returned:

```
error: 401 Unauthorized: authentication required
  hint: run 'persatrix login' to authenticate
```

with a valid, freshly issued token on disk. `whoami` answered `200` on the same credential, and the orchestrator logged `POST /api/v1/agents/ember-owl/chat status=401` at **16 µs** — rejected at the middleware, before any handler.

Cause: `main.rs` installs the bearer as a **default header on the shared client**, but `cmd_chat` builds its **own** long-timeout client for the chat turns (`reqwest::Client::builder()` at `chat.rs:45`) and never re-attached it. `chat.rs` was the only such site in the CLI. So the chat POST was the one unauthenticated verb on the whole surface, and **every** logged-in caller got `401` — on the primary CLI verb, on the exact surface this release activates.

Why no gate caught it: MT-AUTH-001 exercises `chat` only under Leg 6's `disabled` mode, where no header is needed; its `enabled` legs are REST and browser. No automated test covered the chat client's headers.

Fixed by extracting a pure `bearer_headers()` helper and feeding it into the chat client's builder, with four regression tests (`cli/src/commands/chat_tests.rs`): token attaches, credential marked sensitive, logged-out attaches nothing, header-invalid bytes act logged-out rather than failing the command. Rust suite 293 → **297 passed / 0 failed**. Re-verified live on the running stack before the arc proper began.

### F-2 — catch-up replay re-derives memory under the default principal — **new issue, [ISSUE-0130](../issues/ISSUE-0130-catchup-replay-rederives-memory-under-default-principal.md), high**

After Legs 1–2 the surface was clean (`alice-person` only). Immediately after Leg 3's persona restart, two `local` episodes and two `local` facts appeared, **duplicating Alice's private content**, written 2 ms apart in one batch under `session_id='legacy'`.

The agent log names the mechanism:

```
07:59:21.960  PERSATRIX_SESSION_ID unset; defaulting to 'legacy' session
07:59:22.008  channels: catch-up complete agent=ember-owl channels=3 events=6 elapsed_ms=18
07:59:23.412  fact.store … subject=alice-person predicate=has_child_named object=Mira
```

`_build_replay_event` seeds `replay_mode`, the wire interaction keys and the RFC 0037 classification — **no principal** — so the persona binds its default and every close-path summary and RFC 0026 extraction on the replayed span lands in `local`. There is nothing to seed: the orchestrator's `messages` table has no principal column, and the emitting tenant exists only as gRPC metadata on the live dispatch.

**The person↔person boundary this release promises is unaffected** — Bob cannot read `local` rows, which is why Leg 3 passed for the right reason. What breaks is person→anonymous: `local` is what the persona fleet, every autonomous turn, and every caller under `auth.mode: disabled` resolve. It also compounds — `local` episodes grew `0 → 2 → 5 → 13 → 18 → 29 → 37` across the arc (which carried extra operator-retry restarts, so the shape is the finding, not the rate).

Filed as the third ISSUE-0082 residual (R-3), with two fix shapes: suppress derivation on an unattributed replay (Python-only, no migration) or persist and seed the principal (channel store `v11 → v12`). Per the direction set on this cycle, the leak-stopper lands **inside v0.3.14 in the PR after this one**; the complete fix is co-designed with R-2 on the v0.3.15 interaction/tenant train, so `messages` is not migrated twice.

### F-3 — `MT-MEMORY-MULTIUSER-001` cannot separate memory from room transcript at Legs 4–5 — **MT amendment, follow-up**

Legs 4 and 5 both re-ask inside Alice's populated DM. The RFC 0034 conversation window is rebuilt from channel history at catch-up and is not principal-scoped, so it can supply the answer either way. Leg 5 made this unmistakable: with **zero** rows readable by `alice-person`, the persona still named Mira. Leg 3 is unaffected — Bob's DM is a distinct, empty channel — so the release-critical absence bar stands.

The MT needs a fresh-room / empty-transcript rule for the recall and reset legs, mirroring the fix v0.3.13 applied to its Leg 2b. Not amended here: this PR reports the run; PR 2 carries doc changes.

### F-4 — operator notes (no action)

- `rm accounts.db` alone leaves `-wal`/`-shm` beside a fresh empty database, and bootstrap then fails `accounts: read user_version: disk I/O error (522)`. The rotation must remove all three sidecars. Worth a line in the MT's two-account note.
- `docker cp` against a **stopped** container in this stack fails on the read-only config mount; run the SQLite work in-container with the stack up instead.
