## v0.3.2 Performance

### Wallet acquire+settle p99 loopback measurement

**Target**: RFC 0023 §Goal #6 — p99 ≤ 5 ms (informational, not a release blocker).
**Harness**: [`scripts/perf/wallet_p99.py`](../../scripts/perf/wallet_p99.py) — 1500 acquire+settle cycles + 50 warmup, against the Docker-composed orchestrator's `WalletService` gRPC on `localhost:9090`. Agent IDs rotate every 20 cycles to stay under the 60 calls/60 s rate-limiter bucket per agent (`x-agent-id` metadata key); `run_id` prefix ensures fresh buckets per invocation.
**Cause**: `CAUSE_UNSPECIFIED` — pure wallet RPC roundtrip; no LLM call, no token-counter coupling.

| Statistic | Latency (ms) |
|-----------|-------------:|
| min       |  3.783 |
| p50       |  9.833 |
| mean      | 10.439 |
| p95       | 18.575 |
| **p99**   | **27.756** |
| max       | 49.374 |

**Result**: ℹ️ **Informational** — p99 above 5 ms target (and above the PR 1 baseline 11.243 ms). The measurement is taken across the Docker bridge network (host → container loopback adds ~1–2 ms per RPC), and was captured immediately after the live MT-COST-003 / MT-COST-004 cycles, so the wallet was warm but the orchestrator was under residual rate-limit-bucket pressure from the recent traffic; the steady-state pure in-process number would be lower. Captured as the v0.3.2 release-prep PR 1 baseline; tracked as [F-3](#follow-ups).

The [#396 dispatcher-level fix](https://github.com/mkhomutov/Persatrix/pull/396) catches `AioRpcError(RESOURCE_EXHAUSTED)` in [`agents/chat_reply.py::dispatch_channel_event_with_chat_error_recovery`](../../agents/chat_reply.py) and publishes a structured-error reply (`"Agent is at capacity — please retry in a moment."` with `error_reason="resource_exhausted"`) — verified by the new `agents/tests/test_chat_path_resource_exhausted.py` unit guards (mocks `dispatcher.dispatch` to raise the `AioRpcError` directly). In live traffic, however, the action loop's generic `except Exception` arm at [`agents/persona_runtime/action_loop.py:423`](../../agents/persona_runtime/action_loop.py) catches the `AioRpcError` **first** (it propagates through `LLMClient.create_message` → `wallet.lease()` → the action loop's wrapper around `create_message`), logs it as `LLM provider error in agent ember-owl: <AioRpcError of RPC that terminated with: status = StatusCode.RESOURCE_EXHAUSTED>`, and returns a `COMPLETE_TASK` action with `payload={"result": "LLM provider error"}`. `ActionExecutor.execute` for `COMPLETE_TASK` (see [`agents/action_executor.py:152-158`](../../agents/action_executor.py)) **does not publish anything on the channel** — it just returns a metadata dict — so the dispatcher's chat-error-recovery wrapper never sees the exception and the orchestrator's `PublishAndAwait` waiter times out with HTTP 504 `DEADLINE_EXCEEDED`. The unit test passes because it bypasses the action-loop layer entirely. **Proposed fix shape** (out of scope for PR 1): the action loop must distinguish `AioRpcError(RESOURCE_EXHAUSTED)` from generic provider errors — the simplest shape is a dedicated `except grpc.aio.AioRpcError` arm ahead of the catch-all that re-raises on `RESOURCE_EXHAUSTED` (so it reaches the dispatcher's wrapper, identical to the existing `BudgetExceededError` re-raise pattern at lines 391-422) on chat / channel paths and short-circuits to `DO_NOTHING` on TICK (symmetric to the budget-denied TICK arm). Either fix needs a new MT-COST-003 re-run on a build that carries it; the live surface is currently HTTP 504 instead of the contracted HTTP 200 + `"Agent is at capacity — please retry in a moment."` under any rate-limiter / active-lease-cap saturation. **Net effect on the v0.3.2 release decision**: the wallet enforcement *itself* — the core RFC 0023 deliverable — is fully working (denial is closed, no provider spend leaks, every lifecycle stage logs cleanly). The MT-COST-003 spec contract (budget-denial → `reply_status="error"`) **is** met. Only the transient back-pressure surface (a *different* error class) leaks as 504; tracked separately from MT-COST-003 acceptance.
- **F-2 — Live `idle_reason=budget_denied` not observed during MT-COST-004 (Edge Case 2 dominated, both PR 1 and re-run)** (MT-COST-004 ⚠️ Accepted-with-known-gap; severity: low). The Python integration test `tests/integration/test_tick_budget_denied_idle.py::test_budget_exhausted_tick_loop_stays_idle` passes — the action loop's `BudgetExceededError` catch → `DO_NOTHING` → `persona_tick_idle` counter with `idle_reason=budget_denied` works as specified. Live, however, every observed ember-owl autonomous tick was classified `idle_reason=empty_context_tick` (5+ ticks across ~5 min observation window with cap `per_agent=$0.01`), matching MT-COST-004 Edge Case 2 verbatim: the RFC 0017 §F empty-context short-circuit runs *before* the LLM call attempt, so the wallet never sees the lease for a tick whose context the persona judges empty. To genuinely live-observe `idle_reason=budget_denied` a future MT iteration needs a richer fixture — e.g. a persona with an active goal, a populated working-memory item, or a recently-arrived event that *forces* the tick into the LLM-call branch under budget pressure. Wallet enforcement under the `CAUSE_AUTONOMOUS_TICK` arm is otherwise structurally identical to the proven `CAUSE_CHANNEL_MESSAGE` arm in MT-COST-003.
- **F-3 — Wallet acquire+settle p99 = 27.756 ms (above 5 ms target, informational, regressed from PR 1's 11.243 ms baseline)**. Loopback measurement across the Docker bridge network; per-RPC overhead includes ~1–2 ms host↔container loopback. The PR 1 vs re-run delta is mostly explained by the wallet being under residual rate-limit-bucket pressure from the immediately-preceding live MT-COST-003 / MT-COST-004 cycles (the harness ran inside the same 60 s window) — steady-state pure in-process number would be lower. RFC 0023 §Goal #6 marks this as informational, not a blocker. Captured as the v0.3.2 baseline.
- **F-4 — operator note for the release checklist** (carry-forward from v0.3.1 F-4). An empty `ANTHROPIC_API_KEY` exported in the shell overrides a populated `.env` under Docker Compose precedence. Every `docker compose` invocation in this run was prefixed with `unset ANTHROPIC_API_KEY` so Compose reads the `.env` file value. Worth keeping a one-line note in the release checklist's environment-setup section.
- **F-5 — gRPC rate limiter (60/60s anonymous-bucket) blocks naive load harnesses + correlates with F-1 surface** (carry-forward from PR 1 F-5). The wallet p99 harness initially failed with `RESOURCE_EXHAUSTED "rate limit exceeded"` because all `WalletService` RPCs without an `x-agent-id` gRPC metadata header share the anonymous rate-limit bucket. Fix shape: harness attaches `x-agent-id` metadata and rotates agent IDs every 20 cycles. Worth documenting at the operator-facing `wallet` section of the v0.3.2 docs so external load harnesses don't trip the same. Additionally, the same rate-limit interceptor is the *source* of the F-1 RESOURCE_EXHAUSTED back-pressure that surfaces as HTTP 504 — burst-y chat traffic (e.g. the warmup sequences this MT run used to clear the rate-limiter) saturates the bucket and the in-flight chat lease hits cap with no published reply.
- **F-6 — orchestrator restart un-registers all agents; rate-limiter bucket survives orchestrator restarts** (new in re-run; severity: low). The MT-COST-003 / MT-COST-004 cycle requires `config/optimization.yaml` edits + orchestrator restarts (`docker compose restart orchestrator`); each restart drops the agent registry to empty (`GET /api/v1/agents` → `[]`) until the agent containers are also restarted (`docker compose restart agent-…`). Mildly painful for repeatable manual-test runs; not a v0.3.2 regression but worth a note in the operator playbook. Separately, the gRPC rate-limiter bucket (60/60s per agent) is **not** flushed on orchestrator restart — fresh post-restart chat attempts can still hit `RATE_LIMITED 429` for up to ~60 s if the prior session burned the bucket.
