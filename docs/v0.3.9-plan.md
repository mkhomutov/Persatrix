# v0.3.9 Plan — Conversations You Can Mine (membership-scoped verbatim recall)

**Status**: 🚧 Planning
**Target version**: v0.3.9 (the *mine* rung — verbatim recall on top of the v0.3.8 brainstorm; closes the [usefulness ladder](v0.3.x-sequencing.md#the-usefulness-ladder)'s v0.3.x arc)
**Created**: 2026-06-17
**Branch prefix**: `feature/v039-`
**Target**: `main`
**Merge strategy**: Squash merge per [BRANCHING.md](BRANCHING.md)
**Codename**: *Conversations you can mine* (completes the *Conversations …* trilogy with v0.3.7 *worth watching* and v0.3.8 *that converge*)

**Goal**: orchestrate v0.3.9 end-to-end. One user-facing story: **personas quote each other accurately, and a human can search the verbatim record of what was said — scoped to the channels each persona was present for**. A persona added to a group channel, removed, then re-added recalls messages from *both* of its stints, and from neither the pre-join period nor the removal gap. This is the verbatim *recall* capability sitting beside the persona-memory *summary* tiers (RFC 0005 / 0008) — "what was literally said," not "what I remember concluding."

Two workstreams, one release contract:

- **RFC 0035 — the membership-interval ledger (the substrate).** An append-only `membership_intervals` ledger in the channel store: one row per membership stint `(channel_id, participant_id, joined_at, left_at)`, written transactionally by `AddMember` / `RemoveMember` / `GetOrCreateDM`, backfilled from the current `memberships` projection. It exists to answer the one question the current-state-only `memberships` table cannot: *"was participant X a member of channel Y at time T?"* — the time-range filter recall is built on. Ships infrastructure only; **no user-visible behaviour of its own.** Owned by an RFC 0035 PR plan (Phase 1 deliverable). Per [RFC 0035 §B/§C/§D](rfcs/0035-channel-membership-interval-ledger.md#b-schema--membership_intervals).
- **RFC 0036 — verbatim message recall (the consumer + the user-facing win).** A new `recall_channel_messages` persona tool searches the verbatim text of past conversations, **server-side in the channel store**, joining a new FTS5 index over `messages` against the RFC 0035 ledger so the access rule is enforced in SQL, not in the persona runtime. The same membership filter is retrofitted onto the RFC 0034 conversation window (Phase 3), so a re-added persona's *live* prompt stops showing removal-gap messages — closing an inconsistency RFC 0034 left open. Owned by an RFC 0036 PR plan (Phase 1 deliverable). Per [RFC 0036 §A–§G](rfcs/0036-persona-message-recall.md#a-architecture--server-side-scoped-search).

Each RFC gets a standalone PR plan opened as Phase 1 of this master plan; **this master plan wraps them** with the release contract + release-prep + tag phases. Same thin-orchestration shape as [v0.3.8-plan.md](v0.3.8-plan.md): the RFC PR plans own the internals; this doc owns which phases, in what order, by what release gate, and locks the scope decisions the RFCs deferred to "the v0.3.9 plan."

**Scope decisions locked at plan-authoring time (2026-06-17):**

- **Recall spans sessions within the epoch; `epoch_id` is hard-filtered (resolves [RFC 0036 §OQ-6](rfcs/0036-persona-message-recall.md#open-questions)).** `epoch_id` is the strict run/test-isolation axis with no carry-over — recall MUST add `AND m.epoch_id = ?` bound to the caller's epoch (a correctness requirement, not an option; omitting it lets a persona recall a different run's or a post-`reset` epoch's messages — an isolation breach). `session_id`, by contrast, is **not** filtered: verbatim recall's value is cross-conversation, and the membership interval is the intended access boundary, so recall searches a persona's whole history in a channel *within its epoch*. This is the RFC's stated lean, now ratified. The decision sets the §C search predicate and the §G `as_participant` history clause **together** — both filter `epoch_id`, neither filters `session_id`.
- **RFC 0036 Phase 3 (conversation-window membership filter) is IN v0.3.9.** The window/catch-up retrofit closes the coherence gap (a re-added persona could *see* gap messages live but could not *recall* them). It is independent of Phases 1–2 and separately reviewable, but it ships in this release because the "scoped to where you were present" promise must hold for the live prompt, not just the recall tool.
- **RFC 0035 Phase 2 (operator inspection endpoint) is IN v0.3.9.** The read-only `GET` membership-history endpoint + `GetAccessibleChannels` convenience method ship for operator debugging / audit reconstruction. It is **not** a dependency of recall (which joins the ledger server-side), so it is sequenced last and may be cut without affecting the headline; its auth gate inherits the surrounding channel-surface trust level ([RFC 0035 §OQ-2](rfcs/0035-channel-membership-interval-ledger.md#open-questions)).

**Out of scope** — explicitly deferred so they don't pressure the recall cut:

- **A durable, retention-immune recall store.** Recall reads the live `messages` table; cap-pruned or user-deleted messages are simply gone from recall ([RFC 0036 §H](rfcs/0036-persona-message-recall.md#h-retention-horizon-and-deletions)). Copying messages into a separate retention-immune index was considered and **rejected** — it re-opens the retention/privacy question and is not needed. A future RFC may revisit it.
- **Semantic / vector recall.** Search is FTS5 lexical (BM25), the same technology the episodic tier uses. Embedding-based semantic recall is a separate, later concern ([RFC 0036 Non-Goals](rfcs/0036-persona-message-recall.md#non-goals)).
- **Cross-persona recall.** A persona recalls *its own* membership scope; the scope `participant_id` is closure-bound and server-bound, never LLM-controllable.
- **A retention / TTL policy for `messages`**, and **pruning closed intervals** ([RFC 0035 §OQ-3](rfcs/0035-channel-membership-interval-ledger.md#open-questions)) — both orthogonal; revisited only when observed-workload data shows table size matters.
- **Reconstructing membership history that predates this RFC** — the backfill recovers one open interval per *currently present* participant; pre-ship removed stints are permanently absent ([RFC 0035 §D](rfcs/0035-channel-membership-interval-ledger.md#d-backfill)). Documented as a known recall limitation, not a bug.
- **Multi-tenant authorization of the recall endpoint** ([RFC 0036 §OQ-1](rfcs/0036-persona-message-recall.md#open-questions)) — the recall endpoint and `as_participant` parameter scope by a caller-supplied participant id on a channel REST surface that is currently unauthenticated (single-tenant trust level). They MUST NOT ship more permissively than their neighbours, and inherit RFC 0009's auth model when it lands. The scope join is correct regardless of who calls; this gates *treating recall as safe on a multi-tenant deployment*, not Phase 1.
- **Cross-referencing recall against the episodic summary tier** ([RFC 0036 §OQ-5](rfcs/0036-persona-message-recall.md#open-questions)) — a possible follow-up once both surfaces are in use.

## Why this plan exists

The two PR plans (the RFC 0035 ledger, the RFC 0036 recall feature) could ship as independent RFC workstreams. Three reasons they get an umbrella:

1. **A patch release needs a release contract, not just PR sequences.** Per [ROADMAP §Version Map](../ROADMAP.md#version-map), a version is defined by what a user *can do*; v0.3.9's promise — "personas quote each other accurately and you can search the verbatim record, scoped to where each was present" — is a release-level gate no single PR owns. RFC 0035 has *no user-visible behaviour at all*; it only earns its place as the substrate that makes RFC 0036's scoping correct. The acceptance bar is the *combined* manual-test outcome (a persona recalls across a join → leave → rejoin and the human searches the record), not either RFC's unit suite.

2. **The two RFCs are a hard dependency chain that must land in order.** RFC 0036 Phase 1's scoped search query joins `membership_intervals`; it **cannot begin** until RFC 0035 Phase 1's table and write hooks exist ([RFC 0036 §Decision/Next Steps](rfcs/0036-persona-message-recall.md#decision--next-steps)). One plan owns the sequencing gate so the substrate is reviewed and merged before the consumer starts, and so the channel-store migration slots (v9 = ledger, v10 = FTS index) are taken in the right order with no collision.

3. **The scoping rule is an access-control decision split across both RFCs.** The `membership_intervals` `EXISTS` clause *is* RFC 0036's authorization check — its correctness depends on the ledger's correctness ([RFC 0035 §Security](rfcs/0035-channel-membership-interval-ledger.md#security-considerations) carries the matching obligation, cross-cited by [RFC 0036 §Security](rfcs/0036-persona-message-recall.md#security-considerations)). A missed interval close becomes a data-exposure bug in recall. One plan owns the join: the ledger's transactional-consistency tests and recall's scope tests are read as a single correctness surface, and the `epoch_id` filter (this plan's §OQ-6 lock) is applied consistently to the recall query and the window filter.

Same thin-orchestration shape as [v0.3.8-plan.md](v0.3.8-plan.md): the RFC PR plans own the internals; this doc owns which phases, in what order, by what release gate.

## Acceptance for v0.3.9

The promise — *personas quote each other accurately, and a human can search the verbatim record of what was said, scoped to the channels each was present for* — is met when:

- **The membership ledger is exact from v9 forward (RFC 0035).** Every `AddMember` that admits a not-currently-present participant opens exactly one open interval; every `RemoveMember` of a present participant closes exactly one; a redundant `AddMember` on a present participant opens **no** second interval; `GetOrCreateDM` opens one interval per DM participant. A join → leave → rejoin cycle yields two distinct, non-overlapping intervals (one closed `[t0,t1)`, one open `[t2,NULL)`). The partial unique index `ux_membership_intervals_open` makes a double-open a hard INSERT failure; `RemoveMember` rolls back rather than commit if it finds no open interval to close (a projection/ledger divergence is a data-exposure bug, treated loudly). The v8 → v9 backfill seeds one open interval per current `memberships` row; the migration stamps `user_version` inside its transaction and is idempotent on reopen. `memberships` keeps its exact shape and the publish hot path is unchanged.
- **A persona recalls verbatim text, scoped server-side (RFC 0036).** `recall_channel_messages(query, channel_id?, sender?, limit?)` returns verbatim `{message_id, channel_id, sender, timestamp, content}` rows ranked by relevance, scoped by the `membership_intervals` `EXISTS` clause: only messages inside one of the calling persona's stints for the message's channel are ever returned. Pre-join and removal-gap messages are unreachable; a removed-and-re-added persona recalls **both** stints. The scope `participant_id` is bound from the endpoint path and `agent_id` is closure-bound in the tool — the LLM **cannot** supply or override it. Default call (`query` only) searches every accessible channel.
- **`epoch_id` is hard-filtered; sessions are spanned (this plan's §OQ-6 lock).** The §C search query and the §G `as_participant` history clause both add `AND m.epoch_id = ?` bound to the caller's epoch and **do not** filter `session_id`. Test: a message from a different epoch / post-`reset` epoch is never recalled; two messages in the same channel and epoch but different sessions are *both* recallable (subject to the membership filter).
- **Recalled content cannot inject the prompt (RFC 0036 §F).** Every recalled `content` string passes through the same `_format_event` `CHANNEL_MESSAGE` delimiter-escape RFC 0034 §D established, applied per row as the tool assembles its `tool_result`; a `<|user_message|>` literal round-trips inert. Each row is tagged with its origin `channel_id` and `sender` so the model is aware it is quoting cross-context material.
- **The live window and catch-up respect membership (RFC 0036 Phase 3).** `GET /api/v1/channels/{id}/messages?as_participant=<id>` applies the §C `EXISTS` clause to the history query; `conversation_window._fetch_window`, `HttpChannelHistoryFetcher`, and `channel_catchup.py` pass the persona's `agent_id`. A re-added persona's live prompt and episodic seeding both exclude removal-gap messages; for a current single-stint member the filter is a no-op on recent messages. Human/CLI callers omit `as_participant` and are unaffected.
- **Recall is honest about the retention horizon (RFC 0036 §H).** A cap-pruned or user-deleted message is absent from results (gone from `messages_fts` via the delete trigger); the tool description does not promise total recall; the FTS5-unavailable build falls back to a `LIKE` substring scan under the identical scope (its text match diverges from FTS5's whole-token match, but access cannot widen).
- **Recall is audited and bounded (RFC 0036 §Security).** Every `recall_channel_messages` call emits an RFC 0009 audit event **server-side, in the endpoint handler** (a bypassed tool client cannot suppress the trail), recording the persona, query, narrowing params, and result count (not content). `limit` is clamped server-side to a hard maximum; FTS5 `MATCH` operator syntax in the query is escaped so it cannot error the statement or alter scope.
- **A new `channels:recall` permission gates the tool.** Distinct from `memory:read` — verbatim cross-channel recall is materially more sensitive than reading the persona's own summaries, so an operator can enable episodic recall while leaving verbatim recall off. A `channels:recall` denial returns a failed `ToolResult`.
- **The operator can inspect membership history (RFC 0035 Phase 2).** The read-only `GET` membership-history endpoint returns a participant's intervals; it inherits the surrounding channel-surface trust level. Cut-tolerant (not load-bearing for recall) but in scope for this release.
- **The combined story is documented and demonstrable.** `MT-PERSONA-RECALL-001` (persona added → removed → re-added; recall succeeds for stint-1 content, correctly *cannot* recall gap content, succeeds for post-re-add content) is authored and passes live. CHANGELOG `[0.3.9]` describes the recall win and the new `channels:recall` permission; `docs/guides/persona-agents.md` + `docs/diagrams/memory-architecture.md` document the recall tool and the verbatim-vs-summary distinction.
- **Defaults are additive.** Existing channels and personas without the `channels:recall` permission behave exactly as v0.3.8 (the tool is simply unavailable); the ledger is written transparently; the window filter is a no-op for current single-stint members. A back-compat check proves the persona prompt is byte-identical for a current member.

Out of acceptance: a durable recall store; semantic/vector recall; cross-persona recall; a `messages` retention policy; closed-interval pruning; multi-tenant recall-endpoint auth; recall↔episodic cross-referencing (all deferred per the **Out of scope** list above).

## Phase 1 — Implement the ledger + recall

**Branch prefixes**: `feature/v039-rfc0035-`, `feature/v039-rfc0036-`
**Goal**: execute the two workstreams that jointly deliver verbatim recall. The first step of this phase is **authoring the two PR plans** (`docs/rfcs/0035-pr-plan.md`, `docs/rfcs/0036-pr-plan.md`, modeled on prior RFC PR plans); they own per-PR scope, tests, and checklists. Rows 1a/1b of the [Master Progress Overview](#master-progress-overview) stand for those sequences. **RFC 0035 must merge before RFC 0036 Phase 1 begins** (the hard dependency; the v9-before-v10 migration ordering enforces it).

**Workstream 1a — RFC 0035 membership-interval ledger** (`feature/v039-rfc0035-`):
- **Phase 1 (load-bearing):** channel-store migration **v9** (`case 9:` in [`sqlite_migrations.go`](../internal/channels/sqlite_migrations.go) → `migrateV8ToV9` in `sqlite_membership_intervals_migration.go`): `membership_intervals` table, `idx_membership_intervals_lookup`, the partial unique `ux_membership_intervals_open`, the §D backfill; bump `channelStoreSchemaVersion` to 9 in [`sqlite_schema.go`](../internal/channels/sqlite_schema.go); stamp `user_version` inside the transaction.
- `MembershipInterval` struct + `GetMembershipIntervals` read method + `InScope` predicate helper in [`channels.go`](../internal/channels/channels.go); `ChannelStore` interface gains `GetMembershipIntervals`.
- Write hooks (§C): `AddMember` becomes transactional and opens an interval on a real insert (`RowsAffected()==1`); `RemoveMember` closes the open interval (rolls back on a zero-row close — invariant violation); `GetOrCreateDM` opens an interval per DM participant.
- **Phase 2 (sequenced last, cut-tolerant):** read-only `GET` membership-history endpoint in [`channel_handlers.go`](../internal/server/channel_handlers.go) + `GetAccessibleChannels`; auth inherits the surrounding surface.
- Unit + migration + integration tests per [RFC 0035 §Test Strategy](rfcs/0035-channel-membership-interval-ledger.md#test-strategy) (add/remove/re-add two-stint history; double-open rejected; backfill exact; idempotent reopen; `InScope` half-open boundaries).

**Workstream 1b — RFC 0036 verbatim message recall** (`feature/v039-rfc0036-`):
- **Phase 1:** channel-store migration **v10** (`migrateV9ToV10` + `case 10:`): `messages_fts` FTS5 virtual table + insert/update/delete triggers, FTS5-availability probe, `('rebuild')` backfill; bump const to 10. New `internal/channels/sqlite_search.go`: the scoped search query (§C) with the `membership_intervals` `EXISTS` clause, **`AND m.epoch_id = ?` (this plan's §OQ-6 lock; `session_id` not filtered)**, BM25/recency ranking, `MATCH` escaping, and the `LIKE` fallback. `POST /api/v1/personas/{id}/recall` endpoint + request/response types; the RFC 0009 audit event emitted **here, server-side**; new audit-event constant in [`audit_event.go`](../internal/security/audit_event.go).
- **Phase 2:** `create_recall_tool` factory + `HttpRecallClient` in a new `agents/tools/recall.py` (closure-bound `agent_id`); the new `channels:recall` permission wired into the registry + agent allowlist ([`config/agents.yaml`](../config/agents.yaml), [`schemas/agent.schema.json`](../schemas/agent.schema.json)); per-row `_format_event` sanitization (§F).
- **Phase 3 (independent; §OQ-6 lock applies here too):** `?as_participant=<id>` on `GET /api/v1/channels/{id}/messages` applying the same `EXISTS` + `epoch_id` clause; `conversation_window._fetch_window` + `HttpChannelHistoryFetcher` + `channel_catchup.py` pass the persona's `agent_id`.
- Unit + integration tests per [RFC 0036 §Test Strategy](rfcs/0036-persona-message-recall.md#test-strategy), incl. the epoch-filter / session-span assertions this plan adds and the closure-bound-`agent_id` / `channels:recall`-denial / delimiter-escape cases.

**Acceptance**:
- All PRs across both PR plans merged, meeting every [Acceptance for v0.3.9](#acceptance-for-v039) structural gate.
- `make test` / `make validate` (or repo equivalents) green; both migrations idempotent and `user_version`-stamped in-transaction; the `channels:recall` permission accepted and existing configs without the recall tool load unchanged (back-compat test).
- With no `channels:recall` grant the persona prompt is byte-identical to v0.3.8 (additive proof); the window filter is a no-op for a current single-stint member.
- ROADMAP/RFC status flips applied per [§ROADMAP hygiene](#roadmap-hygiene) as each PR plan reaches its milestone.

## Candidate fold-ins (maintainer decision)

Surfaced during pre-planning triage. None is required for the recall cut; the maintainer owns whether to commit them — default is the two workstreams alone, so the CHANGELOG story stays singular.

| Item | Recommendation |
|------|----------------|
| **Multi-tenant authorization for the recall endpoint** ([RFC 0036 §OQ-1](rfcs/0036-persona-message-recall.md#open-questions)) | **Defer (default) to RFC 0009.** The scope join is correct regardless of caller; the endpoint matches its unauthenticated neighbours and audits every call. Folding RFC 0009 auth in would pull a whole identity workstream into a recall patch. |
| **Durable, retention-immune recall store** | **Defer (default).** Explicitly rejected for this RFC ([RFC 0036 Non-Goals](rfcs/0036-persona-message-recall.md#non-goals)); re-opens the retention/privacy question. Revisit only if a recall horizon longer than the channel cap is ever required. |
| **Drop RFC 0035 Phase 2 (inspection endpoint)** to shrink the cut | **Hold IN (default), but cut-tolerant.** It is not a recall dependency; if the cut tightens, drop it without affecting the headline — it can ride a later patch. |
| **Cross-reference recall against episodic summaries** ([RFC 0036 §OQ-5](rfcs/0036-persona-message-recall.md#open-questions)) | **Defer.** A follow-up once both surfaces are in real use; needs usage data to know whether dedupe/annotation helps. |
| **Calibrate the BM25/recency ranking blend** ([RFC 0036 §OQ-3](rfcs/0036-persona-message-recall.md#open-questions)) | **Defer.** Ship a BM25-dominant default; retune when recall-usage data exists, not on a schedule. |

## Risk and mitigations

The per-PR implementation risks live in the two Phase-1 PR plans (authored in Phase 1). The release-level risks:

| Risk | Mitigation |
|------|------------|
| The ledger is an **access-control record**; a missed interval close or spurious open becomes a data-exposure / data-suppression bug in recall. | RFC 0035 §C makes every write transactional with its `memberships` mutation; the partial unique `ux_membership_intervals_open` makes a double-open a hard INSERT failure; `RemoveMember` rolls back rather than commit on a zero-row close. The ledger's transactional-consistency tests and recall's scope tests are reviewed as one correctness surface ([§Why this plan exists](#why-this-plan-exists) #3). |
| Recall **leaks across runs** if the `epoch_id` filter is forgotten — recall could surface a different run's or a post-`reset` epoch's messages. | This plan locks `epoch_id` as a **non-optional** filter on both the §C search query and the §G `as_participant` clause ([§OQ-6 lock](#open-question-status)); acceptance requires a different-epoch message to be unrecallable; the test is explicit, not incidental. |
| Recalled verbatim text is a **larger prompt-injection surface** than a single live message (arbitrary historical text pulled on demand). | Every recalled `content` is delimiter-escaped per row through the same `_format_event` sanitizer RFC 0034 §D established (RFC 0036 §F); a `<|user_message|>` literal round-trips inert (tested); each row is tagged with its origin so the model knows it is quoting cross-context material. |
| The two migrations (v9 ledger, v10 FTS) land out of order, or the FTS index desyncs from `messages`. | The RFC 0035 → RFC 0036 dependency forces v9 to merge before v10 is authored ([§Migration-slot note](#open-question-status)); the FTS delete trigger keeps the index consistent with hard deletes; the `VACUUM`/rowid-stability caveat is recorded in the migration ([RFC 0036 §B](rfcs/0036-persona-message-recall.md#b-fts5-index-over-messages)) — no code path runs `VACUUM` today. |
| **Rebroadcast** — even within scope, a persona can lift user A's exact words from channel X into channel Y. | Cannot be fully prevented (recall *is* read access); mitigated by origin-tagging each row + system-prompt guidance that recalled content is reference material, not a licence to rebroadcast. Residual risk documented and accepted ([RFC 0036 §Security](rfcs/0036-persona-message-recall.md#security-considerations)). |
| Recall **re-introduces idle / unexpected cost** or runs unbounded. | Recall is FTS5/`LIKE` SQL in the channel store — **no LLM call**, so it does not touch the wallet or the zero-idle-cost invariant; `limit` is clamped server-side; the only write amplification is one index-insert per published message (bounded, same order as existing channel indexes). |
| Two RFCs in one patch reads as scope creep. | RFC 0035 has **no** user-facing behaviour — it earns its place only as RFC 0036's substrate; both serve the single Version-Map story (quote accurately + search the record, scoped to presence). The ledger without recall ships nothing a user can see; recall without the ledger cannot scope correctly. [§Candidate fold-ins](#candidate-fold-ins-maintainer-decision) makes every further addition an explicit opt-in. |
