# EXP-001 — The harness's frozen choices: holding the meetings

> **Status**: 🚧 **In Progress** — PR 5a's and PR 5b's rows froze when they merged; PR 5c's rows freeze when it merges.
> **Last updated**: 2026-09-28
> **Part of**: the [EXP-001 harness](EXP-001-harness.md); the [first part](EXP-001-harness-choices.md) holds the choices of PRs 1 to 4 and the arm order

These are the frozen choices of the harness PRs that hold the meetings: how
arms B and C deploy their advisers and hold each meeting (PR 5a), what the
harness does, for every arm, when a meeting goes wrong (PR 5b), and how arm
D keeps one deployment for a series (PR 5c). PR 5a's
rows moved here from the [first part](EXP-001-harness-choices.md) word for
word when that table passed its size limit. The first part's rule holds for
them too: until the first scored meeting a row changes only through a later
harness PR that says what changed and why, and from then on nothing changes.

## Frozen choices

| Choice | What the harness does | PR |
|---|---|---|
| The advisers, deployed | Each adviser's `agents.yaml` entry is its panel agent config, with nothing under `persona` added or changed, and: the `quality` alias; temperature 0.7; no tools, so only the built-in note tools remain and channel recall is denied; the panel's permissions, relationships, reactive autonomy and 32 000-token, 200-turn conversation window. Where the panel is silent it takes the shipped reactive personas' values: 2 retries and a 300-second timeout, which nothing on the persona path reads, one action a tick, idle after five ticks, and their notes settings. A turn ends at the runtime's own 300-second event timeout, and the provider library keeps its own retries. No reply limit and no timezone is set. Each adviser keeps its memory in a file of its own | 5a |
| The deployment's config | The shipped `optimization.yaml`, with the `quality`, `fast` and `summarizer` aliases all on `claude-sonnet-4-6` at $3.00 and $15.00 per million tokens, one pricing row for that model, the global, per-workflow and per-agent spending limits at 0, which turns each off, and the arm's memory budget. The shipped `channels.yaml` fleet settings, declaring only the meeting's channel; the shipped `security.yaml` and `ui.yaml`. The written config must pass the schemas `make validate` uses before anything starts | 5a |
| The rate limiter | Off, with `SECURITY_RATE_LIMIT_ENABLED=false`. The advisers send no ID of their own, so all four share one anonymous bucket of 60 requests a minute ([ISSUE-0111](../issues/ISSUE-0111-anonymous-wallet-rpcs-share-rate-limit-bucket.md)), and a refused publish drops an adviser's reply from the channel, though its model call is in the call log; on the mock provider it dropped the chair's memo. The switch also turns off the circuit breaker and the per-agent limit on the wallet's gRPC calls. A meeting whose orchestrator has not logged the limiter off is refused before the operator speaks. The harness's own requests carry the ID `exp001-harness` | 5a |
| The meeting's channel | Declared in the deployment's `channels.yaml`, shaped like the shipped `roundtable`: the arm's members and governance from `panel.yaml`, the operator as an observer, armed, with the organisation's one-line description as its description, which every adviser's prompt shows, the topic "Advice for" and the organisation, an empty agenda, the panel's goal and convener, round limit 8, a 2 000 000-token budget, depth cap 5 and classification `internal`. It is named `advice-` and the meeting's place in its series, the same in every arm | 5a |
| A deployment per meeting | Arms B and C hold each meeting in a directory of its own, refused unless empty, which holds the deployment, the call log and the meeting's record. The processes run this checkout's orchestrator binary and `python -m agents.server`, on loopback, and inherit no `PERSATRIX_` or `SECURITY_` setting from the harness's shell. The model client's own settings, such as `ANTHROPIC_BASE_URL`, pass through, as they do to arm A's calls. The meeting's clock anchor is the moment its deployment starts. The advisers stop first, each draining its memory summaries, then the orchestrator; a process still running 90 seconds after its stop signal is killed. A hangup or `SIGTERM` stops the deployment as Ctrl-C does, and if the stop is itself interrupted, every process still running is killed | 5a |
| The close | The first close the orchestrator logs for the channel after the operator's message, by end vote or by bounded close (round limit, depth cap or cost), or the end of the first 600 seconds with no message, between two messages or since the last, whichever comes first; 600 seconds is the orchestrator's idle window, which no channel here changes. The record says what closed the discussion as part 2 reports it: a vote, the depth cap, the round limit, the cost bound or the idle window; the depth cap is the bounded close of an interaction the orchestrator logged at that cap. The memo request keeps the orchestrator's own stamp of that close in the transcript, and a stamp naming another close is recorded as a failure. Nothing else ends the wait: disarming while the chair's closing synthesis is pending would abandon the close | 5a |
| The memo turn | After a close, the harness waits until the orchestrator has no turn in flight in the channel, for at most 5 minutes, so a turn sent before the close posts while the channel is still armed. Then, at every meeting but the briefing, it disarms the channel at the configuration revision it has just read, makes the three other advisers observers, reads each adviser's energy from its store, and posts the panel's plan or recall instruction as the operator, mentioning only the chair. The memo turn's time is the harness's real time just before that post. The memo is the chair's first message after the request, leaving out a closing synthesis that ran late (marked `synthesis_reply`) | 5a |
| Failures a meeting shows | A discussion still open 60 minutes after the operator's message never closed; that is recorded, and no memo turn is held, so the meeting has no memo. A chair that has not answered 35 minutes after the request wrote no memo: a persona turn ends at the runtime's 300-second event timeout, and a turn that runs out posts nothing, so 35 minutes covers the memo turn and six turns queued ahead of it. Any other message after the request, 10 seconds after the memo, is recorded as the memo turn going on. A process that exited before the harness stopped it, and a lease refused for any reason but a spending limit, are recorded too. None of these is retried: retries come with PR 5b. A meeting that fails midway leaves a record naming the error. A lease a spending limit refused fails the meeting once it is stopped and recorded (check 6), and an orchestrator that serves no wallet fails it before the operator speaks | 5a |
| Attempts and tries | An attempt is one run of a series from its briefing: 1, or 2 once it has started again. A try is one holding of a meeting within an attempt, counted from 1. Every call-log line carries both, as the tags `attempt` and `try`, and a line without either is refused. Arms B and C hold each try in a directory of its own, `attempt-N/<meeting>/try-M` under the arm's series directory, made absolute; arm A logs each series to one new file, in a folder the harness makes if need be | 5b |
| Provider errors | A failed call whose exception class is `RateLimitError`, `InternalServerError` (any 5xx but 529), `OverloadedError` (529, "overloaded"), `ConflictError` (409), `APITimeoutError` or `APIConnectionError`. The provider library retries these twice itself before one reaches the call log; those retries are not counted. `CancelledError` counts too: it is how the call log records a call the runtime cut off at its own limit, a turn at 300 seconds or a memory summary at 30. A 408 does not: the library raises a bare `APIStatusError` for it, as for a 402 billing error, and the Claude API does not send it | 5b |
| Holding a meeting again | One provider-error line in a try, from any adviser, means the meeting is held again, since a persona turn that ends in one posts nothing. A failed call outside the arm's design, such as a memory summary in B or C, does not count. The harness reads a channel-arm try's call log every 5 seconds while the meeting runs and ends the try at the first such line; that try leaves its call log and deployment but no meeting record. Before the next try it waits 1, 5, then 15 minutes, so an outage of a few minutes does not use up the retries. After three retries it waits 30 minutes and starts the series again from its briefing, once; if a meeting then fails the same way, the series is dropped from every arm's comparisons, and with fewer than four series kept the run is incomplete | 5b |
| Failures the system causes, by the call log | In a B or C try, a call the provider refused as malformed (`BadRequestError`, `UnprocessableEntityError`) is recorded and not retried: the runtime built the request. When no call of the try answered and every failed one was refused, it is a harness fault instead: a spend limit or an empty balance is refused with the same 400. An orchestrator that exits mid-meeting is recorded, as an adviser that exits is, and the meeting stands without a result | 5b |
| Harness faults | Every other exception class in the call log is a harness fault. `AuthenticationError`, `PermissionDeniedError` and `NotFoundError` are among them, and so is any class a later SDK adds. For arm A, so is anything its one call raises but a provider error, since the harness builds that request. For arms B and C, so is anything a meeting raises but a start failure or an orchestrator that exited. That covers a rate limiter left on, a wallet not served, a spending limit that refused a lease and a config that fails its schemas. It also covers an orchestrator reply the harness cannot read and a call log it cannot read. A read of the orchestrator that fails in transit or with a 5xx is first asked twice more, a second apart; a write is sent once. Each fault stops the run with `HarnessFault`, which names the arm, series, meeting, attempt and try, and carries the series' tries so far | 5b |
| A deployment that does not start | A process that exits while starting, or advisers not all registered within 120 seconds, before the operator's message. The meeting is held again, in a new directory, after the same waits as a provider error, and it uses none of the three retries. One that has not started four times is a harness fault, which says why the last did not | 5b |
| Dollars per plan, by try | Only the calls of each meeting's try that finished count, in the attempt that finished; a try that is not known is refused rather than guessed. Every try's calls are real spend. This reads pre-registration §3's "a failed attempt's spend is reported, but not counted in dollars per plan" as covering a try a provider error cut short, since each try is an attempt at holding the meeting. It narrows PR 1's "Dollars per plan" row, which counts every call of the attempt that finished | 5b |
| Arm D's deployment | Each attempt at a series has a deployment of its own, `attempt-N/deployment` under the arm's series directory, which the briefing's first try writes, refused unless new. It declares a channel for every meeting of the series, each named and shaped as arm B's and C's one channel, with D's governance, which is C's, and D's 1 500-token memory budget. No other arm, series or attempt uses it | 5c |
| A try in arm D | Every try starts all of the deployment's processes, the orchestrator included, with the meeting's clock and call-log settings, and stops them all when the meeting ends, as B's and C's are stopped. The meeting's clock anchor is the moment the try starts. The try's directory, refused unless empty, holds its call log, its record and its processes' logs. The orchestrator restarts too, so that a meeting held again can find its stores as they were | 5c |
| Between meetings | Before each start the harness clears each adviser's saved persona state, its mood, stress, energy and goal progress, so the runtime starts it from its defaults, as a new adviser. Every memory tier, and the interaction counter that paces note reflection, stay as they were, since an adviser left running would keep both through a quiet week | 5c |
| A restart leaves memory as it was | An adviser replays recent channel messages into memory as it starts, but only those from after its clock anchor, and every try sets a new anchor. So once every adviser has logged the end of its catch-up pass, within 90 seconds of the start, the pass must have replayed no message, and each adviser's store that existed before the start must hold exactly the rows it held then, in every table but `agent_state`, the saved state. Otherwise the meeting fails before the operator speaks, and the run stops on a harness fault (check 2) | 5c |
| Holding a D meeting again | Before a meeting's first try, with every process stopped, the harness copies the deployment's stores, each adviser's memory file and the orchestrator's databases but not its logs, into `stores-before` beside the meeting's tries. Before any later try it removes the stores and puts the copy back, so the try starts from the memory the first try began with, in a channel without the failed try's messages. A close summary cut off at its 30-second limit is one of the provider errors that call for this, since D's summaries count | 5c |
