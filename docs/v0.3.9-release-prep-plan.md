**Scope**: the release-prep workstream for the v0.3.9 surface — the recall cluster that lets a persona **quote the verbatim record of what was said, scoped to the channels it was actually present for**. Two landed workstreams jointly own the headline:

1. **The substrate — the membership-interval ledger** ([RFC 0035](rfcs/0035-channel-membership-interval-ledger.md)). An append-only `membership_intervals` ledger in the channel store (one row per join/leave stint `(channel_id, participant_id, joined_at, left_at)`), written transactionally by `AddMember` / `RemoveMember` / `GetOrCreateDM` / `CreateChannelWithMembers`, guarded by the partial unique `ux_membership_intervals_open` (≤1 open stint per pair), backfilled from the current `memberships` projection. It answers the one question the current-state-only `memberships` table cannot — *"was participant X a member of channel Y at time T?"* — and ships **no user-visible behaviour of its own**; it earns its place only as the substrate RFC 0036's scoping joins against. Plus the cut-tolerant Phase 2 read-only `GET …/members/{id}/history` operator inspection endpoint + `GetAccessibleChannels`.
2. **The consumer + the user-facing win — verbatim message recall** ([RFC 0036](rfcs/0036-persona-message-recall.md)). The `recall_channel_messages` persona tool searches the verbatim text of past conversations **server-side in SQL** — a `messages_fts` FTS5 index over `messages` joined against the RFC 0035 ledger, so the access rule is enforced in the store, not the persona runtime. A persona added → removed → re-added recalls messages from *both* of its stints and from neither the pre-join period nor the removal gap. Recall is `epoch_id`-hard-filtered (run isolation), spans sessions within the epoch, audited server-side, gated by the new opt-in `channels:recall` permission, and delimiter-escaped against prompt injection. The same membership filter is retrofitted onto the live RFC 0034 conversation window + boot-time catch-up (Phase 3), so a re-added persona's *live* prompt also stops at its membership boundary.

It covers: **execution** of the already-authored headline manual test ([`MT-PERSONA-RECALL-001`](manual-tests/MT-PERSONA-RECALL-001.md) — add → remove → re-add; recall stint-1 ✓, gap ✗, post-re-add ✓; the deterministic `POST …/recall` endpoint *and* the persona tool path; the membership-history + audit cross-check) plus the carried-forward v0.3.8 convergence surface; a documentation refresh (the persona-agents guide's verbatim-vs-summary distinction + the memory-architecture diagram, both authored during implementation → verified here) and a new release checklist; version bump `0.3.8` → `0.3.9`; dating the existing `[0.3.9]` `Unreleased` changelog into a tagged `[0.3.9]`; and final pre-tag verification (the **two channel-store migrations** — v8→v9 ledger and v9→v10 FTS — are the release gates).

**Out of scope**: new feature work. Both workstreams are fully landed with no outstanding PRs (see [§RFC PR roll-up](#rfc-pr-roll-up)). Deferred — documented as Known Gaps in the release notes, not release gates:

- **A durable, retention-immune recall store** → **future RFC**. Recall reads the live `messages` table; a cap-pruned or user-deleted message is simply gone from results ([RFC 0036 §H](rfcs/0036-persona-message-recall.md#h-retention-horizon-and-deletions)). Copying messages into a separate retention-immune index was considered and **rejected** for this RFC — it re-opens the retention/privacy question.
- **Semantic / vector recall** → **later** (the [RFC 0005 §5](rfcs/0005-persona-agent-memory.md) episodic-tier pattern). Search is FTS5 lexical (BM25), the same technology the episodic summary tier uses; embedding-based semantic recall is a separate concern ([RFC 0036 Non-Goals](rfcs/0036-persona-message-recall.md#non-goals)).
- **Multi-tenant authorization of the recall / inspection endpoints** ([RFC 0036 §OQ-1](rfcs/0036-persona-message-recall.md#open-questions) / [RFC 0035 §OQ-2](rfcs/0035-channel-membership-interval-ledger.md#open-questions)) → **RFC 0009**. The endpoints scope by a caller-supplied participant id on a channel REST surface that is currently unauthenticated (single-tenant trust level); they ship **no more permissively than their neighbours** and audit every recall call. The scope join is correct regardless of who calls; this gates *treating recall as safe on a multi-tenant deployment*, not the cut.
- **A `messages` retention / TTL policy and closed-interval pruning** ([RFC 0035 §OQ-3](rfcs/0035-channel-membership-interval-ledger.md#open-questions)) → **post-soak**. Negligible at the foreseeable workload; revisited only when observed table size matters.
- **Cross-referencing recall against the episodic summary tier** ([RFC 0036 §OQ-5](rfcs/0036-persona-message-recall.md#open-questions)) → **follow-up** once both surfaces are in real use.
- **RFC 0030 Layer 5 — moderator / bid-and-select** → **v0.4.0** (carried forward from v0.3.8; not a v0.3.9 dependency). The `chair` stays a low-threshold facilitator with the [`chair_moderation.py`](../agents/chair_moderation.py) seam inert.

**Documentation timing policy** (carry-forward from [v0.3.8 prep](v0.3.8-release-prep-plan.md#documentation-timing-policy)): public docs updated *before* tag; post-tag-only artifacts (tag link, release URLs, "Released" stamps) → [v0.3.9-plan Phase 4](v0.3.9-plan.md#phase-4--tag-and-post-release-follow-up).

### Schema / migration state

**Unlike v0.3.8** (which advanced *both* stores — channel store v6→v8 and persona-memory v14→v15), v0.3.9 advances **only the channel store**, but with **two migrations within it** — `channels.db` ([`internal/channels/sqlite_schema.go`](../internal/channels/sqlite_schema.go), `channelStoreSchemaVersion`) goes from **v8** (the v0.3.8 RFC 0050 config columns) to **v10**. The **persona-memory store stays at v15** (untouched this release — recall is a channel-store capability; the verbatim record lives in `messages`, not the persona's memory DB). Both channel-store migrations are additive / forward-only with no rollback path, per the established migration contract; each migrate function lives in its own sibling file under the 500-line cap, dispatched by the [`sqlite_migrations.go`](../internal/channels/sqlite_migrations.go) runner.

- **v9 — RFC 0035 ([`sqlite_membership_intervals_migration.go`](../internal/channels/sqlite_membership_intervals_migration.go), `migrateV8ToV9`):** the append-only `membership_intervals` table, `idx_membership_intervals_lookup`, the partial unique `ux_membership_intervals_open` (≤1 open stint per `(channel_id, participant_id)`), and the §D backfill — one open interval per current `memberships` row. **No runtime behaviour change of its own**; it is the substrate recall joins.
- **v10 — RFC 0036 ([`sqlite_messages_fts_migration.go`](../internal/channels/sqlite_messages_fts_migration.go), `migrateV9ToV10`):** the `messages_fts` FTS5 virtual table over `messages` with insert/update/delete triggers (so the index tracks the live table, including hard deletes), an FTS5-availability probe, and the `('rebuild')` backfill. On a SQLite build **without FTS5** the migration records the unavailable flag and recall transparently falls back to a `LIKE` substring scan under the *identical* membership scope (text match diverges from FTS5's whole-token match, but access cannot widen — [`sqlite_search_fallback_test.go`](../internal/channels/sqlite_search_fallback_test.go)).

Both stamp `user_version` **inside** the migration transaction and are idempotent on reopen (an already-v10 store is a no-op open). PR 4 confirms a **pre-v0.3.9 channel store forward-migrates v8→v9→v10 cleanly** (ledger table + indexes present and backfilled to one open interval per current member; `messages_fts` present and rebuilt over existing messages; no data loss). There is no rollback path — forward-only.

### Known follow-up issues

All Known Gaps for the release notes, not release gates:

1. **Durable, retention-immune recall store deferred** → **future RFC**. Recall reads the live `messages` table; cap-pruned or user-deleted messages are gone from results (removed from `messages_fts` by the delete trigger). The tool description does not promise total recall ([RFC 0036 §H](rfcs/0036-persona-message-recall.md#h-retention-horizon-and-deletions)).
2. **Pre-upgrade closed membership stints are unrecallable.** The RFC 0035 §D backfill recovers **one open interval per *currently present* participant**; stints that *closed* before migration v9 shipped are permanently absent from the ledger, so messages inside them cannot be recalled or surfaced by the window filter. An [accepted gap](rfcs/0035-channel-membership-interval-ledger.md#d-backfill) ([RFC 0035 OQ #1](rfcs/0035-channel-membership-interval-ledger.md#open-questions)), not a bug — recall and membership history are exact from v9 forward.
3. **Epoch isolation is deterministic-only by design.** The production channel store is single-epoch (`live`); the `epoch_id` hard filter is a forward-looking guard pinned by the deterministic suite, not a live MT lever (see [§Manual test state](#manual-test-state)).
4. **Semantic / vector recall deferred** → **later**. Search is FTS5 lexical (BM25); embedding-based recall is a separate concern ([RFC 0036 Non-Goals](rfcs/0036-persona-message-recall.md#non-goals)).
5. **Multi-tenant recall- / inspection-endpoint auth deferred** → **RFC 0009**. The endpoints match their unauthenticated channel-surface neighbours and audit every recall call; the scope join is correct regardless of caller. Folding RFC 0009 auth in would pull a whole identity workstream into a recall patch ([RFC 0036 §OQ-1](rfcs/0036-persona-message-recall.md#open-questions)).
6. **`messages` retention policy / closed-interval pruning deferred** → **post-soak** ([RFC 0035 §OQ-3](rfcs/0035-channel-membership-interval-ledger.md#open-questions)).
7. **Recall ↔ episodic summary cross-referencing deferred** → **follow-up** once both surfaces are in real use ([RFC 0036 §OQ-5](rfcs/0036-persona-message-recall.md#open-questions)).
8. **BM25 / recency ranking blend is a reasonable default** (BM25-dominant, recency a mild tiebreak), **not yet calibrated** — retune when recall-usage data exists, not on a schedule ([RFC 0036 §OQ-3](rfcs/0036-persona-message-recall.md#open-questions)).
9. **Rebroadcast residual risk** — within scope, a persona can lift user A's exact words from channel X into channel Y. Cannot be fully prevented (recall *is* read access); mitigated by origin-tagging each row + system-prompt guidance that recalled content is reference material. Documented and accepted ([RFC 0036 §Security](rfcs/0036-persona-message-recall.md#security-considerations)).
10. **RFC 0030 Layer 5 (moderator / bid-and-select) deferred** → **v0.4.0** (carried forward from v0.3.8; not a v0.3.9 concern).
