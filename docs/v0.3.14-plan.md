# v0.3.14 Plan — One Persona, Many People (verified-principal emission + the tenant residuals)

**Status**: 📋 Planned — Phase 0 (this planning PR) open
**Target version**: v0.3.14 (the *multi-user isolation activation* release — the last patch before the v0.4.0 Agent Organizations train)
**Created**: 2026-08-05
**Branch prefix**: `feature/v0314-`
**Target**: `main`
**Merge strategy**: Squash merge per [BRANCHING.md](BRANCHING.md)
**Codename**: *One persona, many people*

**Goal**: light the tenant rail that has been armed and unfed since 2026-05-29. [ISSUE-0081](issues/ISSUE-0081-session-id-process-global-not-task-local.md) built the whole persona-side principal vertical — a `principal_id` dimension on all five memory tables (migration v11), **strict-equality** recall with no carve-out, a `principal_scope` ContextVar, the `persatrix-principal` gRPC rail bound per request in `on_event` — and v0.3.13 PR 1 ([#809](https://github.com/mkhomutov/Persatrix/pull/809)) threaded the same axis across the executor hop. All of it resolves to the single-tenant `'local'` principal today, because **nothing emits a principal**. [RFC 0039](rfcs/0039-user-accounts-authentication.md) Phases 1–2 shipped in v0.3.12 and made the caller's `participant_id` a *verified* claim (§F) — the only thing [ISSUE-0082](issues/ISSUE-0082-orchestrator-per-request-session-principal-emission.md) Part 2 was ever gated on. This release supplies the **source**.

The gap is not theoretical: the console is supported beyond localhost under `auth.mode: enabled` as of v0.3.12, persona memory is bounded by room membership and RFC 0037 classification but never by *which account is speaking*, and the deliberately cross-room tiers (travelling facts; the person-identity record, whose primary key omits `session_id`) therefore carry **across accounts**.

Scope was ratified by the [sequencing Amendment 2026-08-02](v0.3.x-sequencing.md#amendment-2026-08-02--v0313--v0314-the-two-release-tail-to-v040), whose next-steps item 3 this plan executes. Like v0.3.13 this is an issue-driven release with one cuttable RFC slice, so **this doc owns the per-PR breakdown directly** — ISSUE-0082 Part 1 had its own [PR plan](issues/ISSUE-0082-part1-session-emission-pr-plan.md), but Part 2 is smaller: the mechanism already exists on both sides of the wire.

At the tag, the issue tracker's **only two open high-severity issues both close**.

## Scope decisions locked at plan opening (2026-08-05)

The amendment named three calls to make here (its next-steps item 3): the principal-emission surface and its derivation source, how far the per-principal sweep/erasure residuals ride, and RFC 0040 Phase 1 in/out.

- **Derivation source: the RFC 0039 §F verified `participant_id`, not the account id.** `authMiddleware` already resolves `authIdentity.ParticipantID` from the bearer/cookie session (`internal/server/auth_middleware.go`); RFC 0039 §A binds each account 1:1 to a `UserParticipant`, and §F already stamps that same value onto `ChatRequest.user_id` as the verified claim. Keying memory on the participant id means the tenant dimension and the conversation surface name the *same* identity — an account rename or a future second credential per participant does not re-partition anyone's memory. The amendment's risk table pre-committed this as "a scope lock, not a new question"; it is exercised here.
- **Emission surface: the dispatch chokepoint, one new wire key, one new ctx carrier.** `grpcmeta` gains `MDPrincipal = "persatrix-principal"` + `InjectPrincipal` beside `MDSession`/`MDEpoch`; the REST handlers thread the resolved identity onto the request ctx (`channels.WithPrincipal`, the `WithSessionOverride`/`WithEpochOverride` precedent, which already survives the fanout's `context.WithoutCancel`); `GRPCMessageDispatcher.Dispatch` injects it beside the session and epoch headers. The wire value MUST byte-match `agents.principal_id.PRINCIPAL_METADATA_GRPC_KEY` — a rename either side silently disables the rail, so it gains the lockstep guard the session key carries.
- **Emission is `auth.mode: enabled`-only; `disabled` stays byte-identical.** Under `disabled` (and for any unauthenticated caller) the middleware resolves the anonymous `local` identity and the orchestrator emits **nothing** — the persona falls back to the `'local'` default exactly as today. No-delta under `disabled` is an acceptance criterion, not an assumption.
- **Propagation posture: the principal rides the turn, including orchestrator-authored hops derived from it.** A fanout child, chair escalation, close notification, convene or synthesis dispatch that descends from a principal-bearing publish carries that principal; a turn with no human origin (autonomous roster fire, idle rotation, agent-initiated publish) emits nothing and collapses to `'local'`. This matches what the Python side already does in-process — v0.3.13 PR 1 seeds `EVENT_PRINCIPAL_METADATA_KEY` onto legacy cascade children — so the two cascade routes cannot diverge. Revisitable in [PR 2](#pr-2--featurev0314-issue0082-principal-producer), which is where the ctx flow is actually read.
- **Residuals split by class: erasure is IN, the capacity sweeps are OUT (cut to v0.4.0).** `delete_by_subject` (`agents/memory/_facts_erasure.py`) scopes both DELETEs to `agent_id` only — the day principals become real, an erasure request from one person deletes another person's facts about the same subject. That is a privacy/correctness boundary that *breaks on the same day this release ships*, and the fix is two predicates and a test, so it rides ([PR 3](#pr-3--featurev0314-issue0081-erasure-principal-scope)). The agent-global capacity sweeps (episode TTL + size-cap eviction, procedural decay, superseded-fact prune, note prune) stay agent-global: ISSUE-0081 classes them as capacity/retention policy rather than read-confidentiality (recall stays principal-filtered either way), and per-principal quota semantics is a design question, not a predicate. It ships as a **named Known Gap** in the release body and is scoped forward to v0.4.0.
- **RFC 0040 Phase 1: IN, cuttable — and decoupled from the Proposed → Accepted flip.** The amendment wrote Phase 1 as "gated on RFC 0040 Proposed → Accepted"; the RFC's own Phase 1 text is the more specific statement and says the opposite — *"No proto change, no RFC-blocking dependency — Phase 1 can land on whichever v0.3.x patch is open."* Every gate on the Accepted flip (Open Questions 1/2/3, the §D `sender_id` call) bears on the **proto** of Phases 2–4, which this release does not touch; Phase 1 is a JSON Schema plus a contract test over the *existing* REST payloads, and that schema survives Phase 2 however those questions resolve. So it boards as [PR 4](#pr-4--featurev0314-rfc0040-phase1-contract-cuttable) — and stays the first thing cut if the release runs long, riding the v0.4.0 train instead. *(A deliberate deviation from the amendment's gating clause, recorded here rather than by amending it; reversible at review.)*

**Out of scope** — explicitly deferred so they don't pressure the cut:

- **Per-principal capacity sweeps and quota policy** — see the residuals lock above; Known Gap + v0.4.0.
- **RFC 0039 Phase 3** (account administration REST, self-service password, session admin, failed-login lockout) — v0.4.0 on-ramp, unchanged by this release.
- **RFC 0040 Phases 2–4** — the `OrchestratorService` proto and the agent-side migration are the v0.4.0 train.
- **The v0.4.0 on-ramp generally** — RFC 0038 §C–§E, RFC 0049 Phases 2–4, RFC 0041 Phase 1.
- **Multi-tenancy beyond memory isolation** — RFC 0039's Non-Goals (org/tenant objects, per-tenant config, billing) stand; this release makes the *memory* boundary real, nothing else.
- **Retiring the session `legacy` carve-out** — retained by the ISSUE-0081 PR 4 decision, already principal-bounded by the unconditional `AND principal_id = ?`.

## Acceptance for v0.3.14

The release ships when **all** hold:

- **ISSUE-0082 is closed** — under `auth.mode: enabled` the orchestrator emits `persatrix-principal` derived from the §F verified claim on every human-originated dispatch; the persona side binds it in `on_event` **and** re-enters it across the executor hop (the v0.3.13 threading, now with a live producer). Pinned end-to-end by an integration test in the shape of `tests/integration/test_session_emission_isolation.py`: two authenticated principals, one agent, one process → isolated recall through the live gRPC path.
- **ISSUE-0081 is closed** — its umbrella condition ("stays open until the principal half is fed") is met, and the erasure residual is principal-scoped. The capacity-sweep residual is recorded as a Known Gap with a v0.4.0 target rather than silently dropped.
- **`auth.mode: disabled` is byte-identical** — no header emitted, every request resolves `'local'`, and a deterministic test pins the no-delta.
- **The live proof exists** — a new manual test (`MT-MEMORY-MULTIUSER-001`, authored in [PR 2](#pr-2--featurev0314-issue0082-principal-producer), executed at release-prep) runs two real authenticated accounts against one persona on a live provider: A tells the persona something, B asks and the persona does not have it, A's own continuity is intact, `disabled`-mode no-delta re-confirms. As in v0.3.13, a green leg that never exercised the contested surface is not proof — the report records the **emitted principal values** seen in provenance for both people's turns.
- **The shared-room semantics are stated, not discovered** — the release notes say plainly what principal-partitioned memory means when two authenticated people share one channel (per-speaker persona memory; the channel transcript itself is not principal-scoped, so room continuity survives via verbatim history). See the risk table.
- **Docs are edited, not just verified** — [auth guide](guides/auth.md) (its Part 2 pointer becomes shipped behaviour), the RFC 0031 §C/§E amendments (principal axis active), RFC 0039 §F's downstream-consumer note, and the memory/sessions guides carry the new boundary.
- **The full gate sweep is green live on host** — Go `-race`, `cargo test`, the Python suites (including the separate `mypy tests/` leg), Vitest, ruff/clippy/go-vet, `make validate`, eval-replay, the license gate. No new store migration is expected (v11 already carries `principal_id`); the checklist states that explicitly rather than omitting the section.

## Phase 1 — Implementation PRs

### PR 1 — `feature/v0314-issue0082-principal-rail`

The mechanism, landing **dormant**: `grpcmeta.MDPrincipal` + `InjectPrincipal` (empty id → no-op, matching `InjectSession`/`InjectEpoch`); `channels.WithPrincipal` / `PrincipalFromContext` mirroring `session_override.go`; the injection at the `Dispatch` chokepoint beside the session and epoch blocks, with the low-cardinality `principal.id` span attribute the other two axes set. Plus the **wire-key lockstep guard** — a test asserting the Go constant byte-matches `agents.principal_id.PRINCIPAL_METADATA_GRPC_KEY`, since a silent rename disables tenant isolation without failing anything else. Nothing threads a principal onto ctx yet, so behaviour is unchanged and the PR is reviewable in isolation.

### PR 2 — `feature/v0314-issue0082-principal-producer`

The source. Under `auth.mode: enabled`, the REST handlers that originate a dispatch — `handlePublishMessage` (`internal/server/channel_handlers.go`) and the chat handler (`internal/server/chat_handler.go`, which already reads `identityFrom(r.Context()).ParticipantID` for §F) — thread the resolved identity onto the request ctx; unauthenticated / `disabled`-mode requests thread nothing. Confirm the ctx actually survives to every orchestrator-authored hop that descends from the publish (the propagation lock above) and pin the autonomous/agent-origin path emitting nothing. TDD: a red test showing today's cross-principal recall through the live gRPC path, then the producer; the end-to-end gate lands as `tests/integration/test_principal_emission_isolation.py` in the shape of its session sibling; a `disabled`-mode no-delta test pins the fallback. Authors `MT-MEMORY-MULTIUSER-001` (executed at Phase 3, the v0.3.13 pattern of authoring the MT in the implementing PR).

### PR 3 — `feature/v0314-issue0081-erasure-principal-scope`

Scope `delete_by_subject` to the principal: both DELETEs in `agents/memory/_facts_erasure.py` gain `AND principal_id = ?`, resolved from the request scope like every other per-request path, with the RFC 0013 §C / RFC 0026 §H return shape unchanged. TDD gate in the ISSUE-0081 PR 4 idiom: *a foreign principal's erasure call can neither count nor delete another principal's rows*. Also audit the callers (the RFC 0013 traversal point, any operator surface) so an operator-initiated erasure has a defined principal — if that turns out to need an all-principals operator verb, it files as an issue and slots v0.4.0 rather than growing this PR.

### PR 4 — `feature/v0314-rfc0040-phase1-contract` *(cuttable)*

RFC 0040 Phase 1 exactly as the RFC scopes it: a shared JSON Schema for the channel-publish and channel-history payloads, validated on the agent send side and the orchestrator decode side, plus a contract test asserting the agent's request shape against the orchestrator's REST handler expectation. No proto, no transport change. If it slips, it cuts — the RFC's Master-Index target moves to v0.4.0 with the Phases 2–4 train.

Findings from the Phase 3 live arc become additional in-release fix PRs as needed (the v0.3.13 precedent).

## Risk and mitigations

| Risk | Mitigation |
|------|------------|
| Shared-room semantics read as a regression: two authenticated people in one channel now get per-speaker persona memory, so neither turn recalls the other's disclosures. | This *is* the promise, applied inside a room; the release notes state it and an MT leg observes it. Room continuity is unaffected — the channel transcript and verbatim history are not principal-scoped. Wanting a per-room principal instead is an RFC 0031 amendment, not an in-release patch. |
| The propagation posture (principal rides orchestrator-authored hops) turns out wrong for some fan — e.g. a close notification reaching a persona that never served that person. | Locked with a default and a named owner PR; PR 2 reads the actual ctx flow and either takes it or records why a per-hop drop is correct. Either way the fallback is `'local'` — a separate namespace, never another person's. |
| Emission lands but the executor hop still resolves the construction principal somewhere v0.3.13 missed. | v0.3.13 PR 1 threaded the axis structurally and pinned it (`tests/unit/python/test_dispatch_context_scope_threading.py`); PR 2's end-to-end test exercises the seams *through* the live gRPC path rather than trusting the unit pins, and the live MT is the third check. |
| The residual split is wrong — the capacity sweeps bite before v0.4.0 (one heavy tenant evicts another's episodes). | Capacity, not confidentiality: recall stays principal-filtered. Shipped as a named Known Gap so it is a documented bound, not a surprise; a v0.4.0 quota design owns it. |
| RFC 0040 Phase 1 expands into the proto work the RFC gates on its Accepted flip. | Phase 1's deliverables are enumerated in the RFC (schema + contract test, no proto); anything beyond them is out of scope by construction, and the PR is cuttable whole. |
| Scope creep — the multi-user story invites account admin, quotas, per-tenant config. | All three are RFC 0039 Phase 3 / v0.4.0 by the amendment's table; anything new files as an issue and slots forward. |
