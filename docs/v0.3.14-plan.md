# v0.3.14 Plan — One Persona, Many People (verified-principal emission + the tenant residuals)

**Status**: 📋 Planned — Phase 0 (this planning PR) open
**Target version**: v0.3.14 (the *multi-user isolation activation* release — the last patch before the v0.4.0 Agent Organizations train)
**Created**: 2026-08-05
**Branch prefix**: `feature/v0314-`
**Target**: `main`
**Merge strategy**: Squash merge per [BRANCHING.md](BRANCHING.md)
**Codename**: *One persona, many people*

**Goal**: light the tenant rail armed and unfed since 2026-05-29. [ISSUE-0081](issues/ISSUE-0081-session-id-process-global-not-task-local.md) built the persona-side principal vertical — a `principal_id` dimension on all five memory tables (migration v11), **strict-equality** recall with no carve-out, a `principal_scope` ContextVar, the `persatrix-principal` gRPC rail bound per request in `on_event` — and v0.3.13 PR 1 ([#809](https://github.com/mkhomutov/Persatrix/pull/809)) threaded the axis across the executor hop. All of it resolves to `'local'` today, because **nothing emits a principal**. [RFC 0039](rfcs/0039-user-accounts-authentication.md) Phases 1–2 shipped the caller's `participant_id` as a *verified* claim (§F) in v0.3.12 — the only thing [ISSUE-0082](issues/ISSUE-0082-orchestrator-per-request-session-principal-emission.md) Part 2 was gated on. This release supplies the **source**.

The gap is not theoretical: the console is supported beyond localhost under `auth.mode: enabled`, and persona memory is bounded by room membership and RFC 0037 classification but never by *which account is speaking* — so the cross-room tiers (travelling facts; the person-identity record, whose primary key omits `session_id`) carry **across accounts**.

Scope was ratified by the [sequencing Amendment 2026-08-02](v0.3.x-sequencing.md#amendment-2026-08-02--v0313--v0314-the-two-release-tail-to-v040), whose next-steps item 3 this plan executes. Like v0.3.13 it is an issue-driven release with one cuttable RFC slice, so **this doc owns the per-PR breakdown directly**: Part 2 is smaller than [Part 1](issues/ISSUE-0082-part1-session-emission-pr-plan.md) — the mechanism already exists on both sides of the wire. At the tag, the issue tracker's **only two open high-severity issues both close**.

## Scope decisions locked at plan opening (2026-08-05)

The amendment named three calls (its next-steps item 3); the surface audit forced two more — the origin set and the activation-day reset.

- **Derivation source: the RFC 0039 §F verified `participant_id`, not the account id.** `authMiddleware` already resolves `authIdentity.ParticipantID` from the bearer/cookie session (`internal/server/auth_middleware.go`); §A binds each account 1:1 to a `UserParticipant`, and §F stamps that same value onto `ChatRequest.user_id` as the verified claim. Keying memory on it means the tenant dimension and the conversation surface name the *same* identity — an account rename does not re-partition anyone's memory.
- **Emission surface: the dispatch chokepoint, one new wire key, one new ctx carrier.** `grpcmeta` gains `MDPrincipal = "persatrix-principal"` + `InjectPrincipal`; the REST handlers thread the resolved identity onto the request ctx (`channels.WithPrincipal`, the `WithSessionOverride` precedent, which already survives the fanout's `context.WithoutCancel`); `GRPCMessageDispatcher.Dispatch` injects it beside the session and epoch headers. The wire value MUST byte-match `agents.principal_id.PRINCIPAL_METADATA_GRPC_KEY` — a rename either side silently disables the rail, so it gains the lockstep guard the session key carries.
- **Origin set: enumerated, not sampled.** A missed dispatch origin fails **open** — no error, no red test, just a silent collapse to `'local'` where two people's rows co-mingle, the exact defect this release closes. So every mux route is classified (principal-threading, or declared agent/autonomous-origin) and pinned by a route-table test. The audit already found a third origin the propagation lock does *not* cover: **`handleConveneChannel`** (`POST /api/v1/channels/{id}/convene`) calls `channelRouter.ConveneChannel(r.Context(), …)` directly, descending from no publish. `workflows/run` and the `handleRecallMessages` read surface are classified in [PR 2](#pr-2--featurev0314-issue0082-principal-producer), not assumed.
- **Activation day: the pre-existing `'local'` corpus does not follow an authenticated principal — accepted, and stated.** Migration v11 backfilled every existing row to `'local'` and the predicate is strict equality, so a deployment running `auth.mode: enabled` since v0.3.12 finds each persona's accumulated memory unreachable the day emission lands — indistinguishable from "the persona forgot everything." The session axis absorbed its equivalent with the §D `legacy` carve-out; the principal axis cannot, because an always-visible principal *is* the cross-tenant bridge the boundary forbids (`agents/principal_id.py`). The reset is taken as-is and made visible: an MT leg observes it, release notes and Known Gaps state it with the operator remedy.
- **Emission is `auth.mode: enabled`-only; `disabled` stays byte-identical.** Under `disabled` (and for any unauthenticated caller) the middleware resolves the anonymous `local` identity and the orchestrator emits **nothing** — the persona falls back to the `'local'` default exactly as today. No-delta under `disabled` is an acceptance criterion, not an assumption.
- **Propagation posture: the principal rides the turn, including orchestrator-authored hops derived from it.** A fanout child, chair escalation, close notification, convene or synthesis dispatch descending from a principal-bearing publish carries that principal; a turn with no human origin (autonomous roster fire, idle rotation, agent-initiated publish) emits nothing and collapses to `'local'`. This matches what the Python side does in-process — v0.3.13 PR 1 seeds `EVENT_PRINCIPAL_METADATA_KEY` onto legacy cascade children — so the two cascade routes cannot diverge. Revisitable in [PR 2](#pr-2--featurev0314-issue0082-principal-producer).
- **Residuals split by class: erasure is IN, the capacity sweeps are OUT (cut to v0.4.0).** `delete_by_subject` (`agents/memory/_facts_erasure.py`) scopes both DELETEs to `agent_id` only — the day principals become real, one person's erasure deletes another's facts about the same subject. A privacy boundary that *breaks on the same day this release ships*, fixed by two predicates and a test, so it rides ([PR 3](#pr-3--featurev0314-issue0081-erasure-principal-scope)). The capacity sweeps (episode TTL + size-cap eviction, procedural decay, superseded-fact prune, note prune) stay agent-global: ISSUE-0081 classes them as capacity policy rather than read-confidentiality (recall stays principal-filtered either way), and per-principal quota semantics is a design question, not a predicate. **Named Known Gap**, scoped to v0.4.0.
- **RFC 0040 Phase 1: IN, cuttable — and decoupled from the Proposed → Accepted flip.** The amendment wrote Phase 1 as "gated on RFC 0040 Proposed → Accepted"; the RFC's own Phase 1 text is the more specific statement and says the opposite — *"No proto change, no RFC-blocking dependency — Phase 1 can land on whichever v0.3.x patch is open."* Every gate on the Accepted flip (Open Questions 1/2/3, the §D `sender_id` call) bears on the **proto** of Phases 2–4, untouched here; Phase 1 is a JSON Schema plus a contract test over the *existing* REST payloads, and that schema survives Phase 2 however those resolve. So it boards as [PR 4](#pr-4--featurev0314-rfc0040-phase1-contract-cuttable), first to cut if the release runs long. *(A deliberate deviation from the amendment's gating clause, recorded rather than amended; reversible at review.)*

**Out of scope** — explicitly deferred so they don't pressure the cut:

- **Per-principal capacity sweeps and quota policy** — see the residuals lock; Known Gap + v0.4.0.
- **RFC 0039 Phase 3** (account admin REST, self-service password, session admin, login lockout) — v0.4.0 on-ramp.
- **RFC 0040 Phases 2–4** — the `OrchestratorService` proto and the agent-side migration are the v0.4.0 train.
- **The v0.4.0 on-ramp generally** — RFC 0038 §C–§E, RFC 0049 Phases 2–4, RFC 0041 Phase 1.
- **Multi-tenancy beyond memory isolation** — RFC 0039's Non-Goals (org/tenant objects, per-tenant config, billing) stand; this release makes the *memory* boundary real, nothing else.
- **Retiring the session `legacy` carve-out** — retained by the ISSUE-0081 PR 4 decision, already principal-bounded by the unconditional `AND principal_id = ?`.

## Acceptance for v0.3.14

The release ships when **all** hold:

- **ISSUE-0082 is closed** — under `auth.mode: enabled` the orchestrator emits `persatrix-principal` derived from the §F claim on every human-originated dispatch; the persona binds it in `on_event` **and** re-enters it across the executor hop. Pinned in the shape of `tests/integration/test_session_emission_isolation.py`: two authenticated principals, one agent, one process → isolated recall through the live gRPC path.
- **ISSUE-0081 is closed** — its umbrella condition ("stays open until the principal half is fed") is met and the erasure residual is principal-scoped; the capacity-sweep residual is a Known Gap with a v0.4.0 target, not a silent drop.
- **No origin is missed** — the route-table test asserts every dispatch-originating REST route either threads a principal under `enabled` or is declared agent/autonomous-origin, `handleConveneChannel` included.
- **`auth.mode: disabled` is byte-identical** — no header emitted, every request resolves `'local'`, and a deterministic test pins the no-delta.
- **The activation-day reset is stated, not discovered** — the release notes and Known Gaps carry it, and an MT leg observes a pre-activation `'local'` row going unreachable for an authenticated principal.
- **The live proof exists** — `MT-MEMORY-MULTIUSER-001` (authored in [PR 2](#pr-2--featurev0314-issue0082-principal-producer), executed at release-prep) runs two real authenticated accounts against one persona on a live provider: A tells the persona something, B asks and it does not have it, A's own continuity is intact, `disabled`-mode no-delta re-confirms. As in v0.3.13, a green leg that never exercised the contested surface is not proof — the report records the **emitted principal values** seen in provenance for both turns.
- **The shared-room semantics are stated, not discovered** — the release notes say plainly what principal-partitioned memory means when two authenticated people share one channel (see the risk table).
- **Docs are edited, not just verified** — [auth guide](guides/auth.md), the RFC 0031 §C/§E amendments (principal axis active), RFC 0039 §F's downstream-consumer note, and the memory/sessions guides carry the new boundary.
- **The full gate sweep is green live on host** — Go `-race`, `cargo test`, the Python suites (including the separate `mypy tests/` leg), Vitest, the linters, `make validate`, eval-replay, licenses. No new store migration is expected (v11 already carries `principal_id`); the checklist states that explicitly.

## Phase 1 — Implementation PRs

### PR 1 — `feature/v0314-issue0082-principal-rail`

The mechanism, landing **dormant**: `grpcmeta.MDPrincipal` + `InjectPrincipal` (empty id → no-op, matching `InjectSession`/`InjectEpoch`); `channels.WithPrincipal` / `PrincipalFromContext` mirroring `session_override.go`; the injection at the `Dispatch` chokepoint beside the session and epoch blocks, with the low-cardinality `principal.id` span attribute the other axes set. Plus the **wire-key lockstep guard** — a test asserting the Go constant byte-matches `agents.principal_id.PRINCIPAL_METADATA_GRPC_KEY`, since a rename disables tenant isolation without failing anything else. Nothing threads a principal onto ctx yet, so behaviour is unchanged.

### PR 2 — `feature/v0314-issue0082-principal-producer`

The source. **First deliverable: the enumeration** (the origin-set lock) — walk the mux, classify every route, pin it with a route-table test so a route added later cannot leak by omission. Known at plan opening: `handlePublishMessage` (`internal/server/channel_handlers.go`), the chat handler (`internal/server/chat_handler.go`, already reading `identityFrom(r.Context()).ParticipantID` for §F), and `handleConveneChannel` (`internal/server/channel_convene_handlers.go`); `workflows/run` and `handleRecallMessages` are classified here — the recall surface reads under a principal or is declared operator-scoped, never silently `'local'`. Each threads the resolved identity onto the request ctx under `auth.mode: enabled`; unauthenticated / `disabled`-mode requests thread nothing. Then confirm the ctx survives to every orchestrator-authored hop descending from the publish, and pin the agent-origin path emitting nothing. TDD: a red test showing today's cross-principal recall through the live gRPC path, then the producer; the end-to-end gate lands as `tests/integration/test_principal_emission_isolation.py`, plus a `disabled`-mode no-delta test. Authors `MT-MEMORY-MULTIUSER-001` (executed at Phase 3).

### PR 3 — `feature/v0314-issue0081-erasure-principal-scope`

Scope `delete_by_subject` to the principal: both DELETEs in `agents/memory/_facts_erasure.py` gain `AND principal_id = ?`, resolved from the request scope, RFC 0013 §C / RFC 0026 §H return shape unchanged. TDD gate in the ISSUE-0081 PR 4 idiom: *a foreign principal's erasure call can neither count nor delete another principal's rows*. Also audit the callers so an operator-initiated erasure has a defined principal — if that needs an all-principals verb it files as an issue ([ISSUE-0086](issues/ISSUE-0086-operator-all-sessions-recall-verb.md) is the read-side class) and slots v0.4.0.

### PR 4 — `feature/v0314-rfc0040-phase1-contract` *(cuttable)*

RFC 0040 Phase 1 exactly as the RFC scopes it: a shared JSON Schema for the channel-publish and channel-history payloads, validated on the agent send side and the orchestrator decode side, plus a contract test asserting the agent's request shape against the REST handler's expectation. No proto, no transport change. If it slips it cuts, and the RFC's Master-Index target moves to v0.4.0.

Findings from the Phase 3 live arc become in-release fix PRs as needed (the v0.3.13 precedent).

## Risk and mitigations

| Risk | Mitigation |
|------|------------|
| Shared-room semantics read as a regression: two authenticated people in one channel get per-speaker persona memory, so neither turn recalls the other's disclosures. | This *is* the promise, applied inside a room; the release notes state it and an MT leg observes it. Room continuity is unaffected — transcript and verbatim history are not principal-scoped. A per-room principal instead would be an RFC 0031 amendment, not an in-release patch. |
| A dispatch origin is missed, so one route keeps writing under `'local'` while the rest partition — the release reads as shipped with a hole in the boundary. | It fails silently, so enumeration is a deliverable, not a review question: PR 2 classifies every mux route and the route-table test fails on an unclassified one. `handleConveneChannel` was found this way at plan opening. |
| The propagation posture (principal rides orchestrator-authored hops) turns out wrong for some fan — e.g. a close notification reaching a persona that never served that person. | Locked with a default and an owner PR; PR 2 reads the ctx flow and either takes it or records why a per-hop drop is correct. Either way the fallback is `'local'` — a separate namespace, never another person's. |
| The activation-day reset lands as a support surprise: an operator upgrades and the persona appears to have forgotten everything. | A boundary to state, not a bug to fix — bridging it would be the cross-tenant bridge the release forbids. Locked, observed by an MT leg, stated in the release notes with the operator remedy. |
| Emission lands but the executor hop still resolves the construction principal somewhere v0.3.13 missed. | v0.3.13 PR 1 threaded the axis and pinned it (`tests/unit/python/test_dispatch_context_scope_threading.py`); PR 2's end-to-end test exercises the seams *through* the live gRPC path rather than trusting the unit pins, and the live MT is the third check. |
| The residual split is wrong — the capacity sweeps bite before v0.4.0 (one heavy tenant evicts another's episodes). | Capacity, not confidentiality: recall stays principal-filtered. Shipped as a named Known Gap, so it is a documented bound; a v0.4.0 quota design owns it. |
| RFC 0040 Phase 1 expands into the proto work the RFC gates on its Accepted flip. | Phase 1's deliverables are enumerated in the RFC (schema + contract test, no proto); anything beyond is out of scope by construction, and the PR is cuttable whole. |
| Scope creep — the multi-user story invites account admin, quotas, per-tenant config. | All three are RFC 0039 Phase 3 / v0.4.0 by the amendment's table; anything new files as an issue. |
