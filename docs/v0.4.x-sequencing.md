## Amendment 2026-10-18 — v0.4.0's shape: its prerequisites, its cuts, and the end of the v0.3.x line

The [amendment that opened v0.4.0](v0.3.x-sequencing.md#amendment-2026-10-18--a-society-that-pursues-long-goals-exp-001-measures-v040-opens) named its contents: RFC 0012 Phases 1–3 and RFC 0028 Phases 1–3, with the on-ramp. The audit that has to run before the plan opens ([release cycle](methodology/release-cycle.md#planning-readiness-audit)) found that the plan could not open on that alone. The named phases cannot be built without RFCs the amendment does not name. It names nothing as cuttable and no next version. It does not say whether this minor release keeps the one-document plan. And earlier decisions and the ROADMAP still place ten more RFCs in v0.4.0 that the goal amendment's table does not name. This amendment settles those points and adds nothing else. The goal (ruling g), EXP-001 (rulings h and l) and EXP-002 (ruling k) are unchanged.

### Why this changes

1. **The named phases depend on RFCs the release does not carry.** Each RFC states these dependencies in its own phase plan:
   - RFC 0012 Phase 1 stores the organization graph in the society store, which [RFC 0029](rfcs/0029-personal-society-storage-split.md) Phase 3 introduces ([RFC 0012 §J](rfcs/0012-protocols-organizations.md#j-storage)). The facade from RFC 0029 Phase 1 already exists, but it has no society backend behind it.
   - RFC 0012 Phase 2 records directives on the commitments tier, which is [RFC 0021](rfcs/0021-persona-temporal-awareness.md) Phase 2.
   - RFC 0012 Phase 3 needs RFC 0028's approval tokens (Phase 2a) and [RFC 0009](rfcs/0009-security-sandboxing.md)'s agent capability tokens, which are Phase 4. RFC 0009 Phase 4 in turn lists Phase 3 as its dependency.
   - Authority means nothing if a directive's issuer can be faked, and today the orchestrator takes an agent's `sender_id` as sent ([RFC 0040 §D](rfcs/0040-agent-orchestrator-transport-unification.md)). RFC 0009 Phase 4 checks its tokens on gRPC calls only, while agents still publish over REST. RFC 0040 Phases 2–3 would move only publish, history and registration to gRPC, and keep REST as a fallback. So the tokens must be checked on the agents' REST calls whichever route is taken.
2. **The on-ramp pulls in still more.** [RFC 0049](rfcs/0049-memory-consolidation-gradient.md) Phase 2 needs the unbuilt RFC 0027 reflection engine. Phase 3 needs a decision store in the society database (RFC 0029 Phase 5). Phase 4 reconciles with RFC 0042, which is still a draft.
3. **The release cycle asks the opening amendment for things this one lacks.** An amendment names each version's cuttable items with a cut condition, and the version that follows it ([release-cycle.md](methodology/release-cycle.md#sequencing-amendment); [decisions.md](methodology/decisions.md#sequencing-amendments) rule 3). The amendment that opens a minor release says whether that release keeps the one-document plan ([release-cycle.md](methodology/release-cycle.md)).
4. **v0.4.0 was defined in two places that disagree.** The goal amendment's table names RFC 0012, RFC 0028 and the on-ramp, and says v0.4.0 opens "with the contents earlier amendments gave it". Earlier text gave it more:
   - the 2026-05-10 decision placed RFC 0024 Phase 5, RFC 0026's cross-agent fact sharing, RFC 0027 and RFC 0029 Phases 2–6 there;
   - the 2026-06-04 amendment's v0.3.8 scope lock kept RFC 0030 Phase 2, the moderator, there;
   - the 2026-08-02 amendment placed RFC 0040 Phases 2–4 there;
   - the ROADMAP alone adds RFC 0007, RFC 0010, RFC 0014 and RFC 0021 Phases 2–4, and makes RFC 0012 wait on RFC 0010. No RFC 0012 phase lists RFC 0010 as a dependency; only RFC 0012's next steps pointed at that ROADMAP chain.

### Rulings

Rulings (a) to (l) live in [v0.3.x-sequencing.md](v0.3.x-sequencing.md) and hold as last amended. Each ruling below holds until a later amendment says otherwise.

- **(m)** v0.4.0's scope is the table above. Every other v0.4.0 placement is superseded, whether it came from an earlier decision or only from the ROADMAP: RFC 0007, RFC 0010, RFC 0014, RFC 0021 Phases 3–4, RFC 0024 Phase 5, RFC 0026's cross-agent fact sharing, RFC 0027, RFC 0029 Phases 2 and 4–6 (Phase 4 apart from ruling n), RFC 0030 Phase 2, RFC 0040 Phases 2–4 (Phases 2–3 apart from ruling n) and RFC 0049 Phases 2–4. Each becomes **unslotted**, not retired. The plan's goal audit may propose any of them back, and only an amendment adds it. RFC 0012 does not wait on RFC 0010.
- **(n)** The prerequisites board with the phase that needs them:
  - **RFC 0029 Phase 3**, a society backend for the organization graph. Ruling (j) leaves its form to a scope lock in the plan. The lock chooses one of three forms:
    - Postgres as RFC 0029 writes it. This also swaps the channels store and needs Phase 4's migration tooling, which then boards too.
    - Postgres for the new society tables only, leaving the channels store as it is.
    - The society tables in the existing SQLite channels store. The [storage roadmap](storage-architecture-roadmap.md) allows this while a benchmark shows SQLite holds.

    Every form needs an RFC 0029 amendment, and the lock's PR carries it: the first to keep its `persatrix memory` commands out under the Rust CLI freeze, as ruling (p) does for RFC 0039's, and the second and third to change the backend too.
  - **RFC 0021 Phase 2**, the commitments tier, and only that phase. Its new table is a store migration, so the plan names it and a lock rules on it (ruling j).
  - **RFC 0009 Phase 4**, agent capability tokens and the approval queue, with **Phase 3**, which Phase 4 lists as its dependency. Phase 3 is cut if an RFC 0009 amendment records that Phase 4 needs none of it.
  - **Agent identity on the agents' own calls.** RFC 0009's tokens are checked on every call an agent makes, which needs an RFC 0009 amendment. A second scope lock in the plan rules the route:
    - check them on the agents' REST calls; or
    - move publish, history and registration to gRPC first, so RFC 0040 Phases 2–3 board and its Phase 4 stays unslotted, and check them on the calls left on REST, REST publish included, since those phases keep it as a fallback.
- **(o)** Ruling (b) is applied here only where it decides what has to board. RFC 0049 Phase 2 moves memory across rooms, with the declassification projection that comes with it. Phase 4 reconciles the cross-channel relay. Both are memory isolation and audience work, and no outside ask is recorded, so they leave v0.4.0. Phase 3 leaves with them: it needs Phase 2's reflection pass and a decision store that nothing here boards. RFC 0027, RFC 0029 Phase 5 and RFC 0042 therefore do not board. For RFC 0049 Phases 2–4 this supersedes the 2026-09-12 amendment's note that the on-ramp is re-slotted only by the amendment that follows the first review. The rest of the ruling (b) audit stays with the plan, as the goal amendment ruled. That audit covers RFC 0038 §D and §E, RFC 0012 §G's clearance check and RFC 0012 §H's enforced egress gate. If it holds §G or §H back, that deliverable leaves RFC 0012's core phases by an RFC 0012 amendment in the plan PR, and is unslotted rather than cut.
- **(p)** **Cut condition:** a cuttable item that has not merged when the last core PR is ready to start the release gate is cut, and neither the gate nor the tag waits for it. This covers each item in the table's cuttable list, and RFC 0009 Phase 3 under its own clause in ruling (n). RFC 0039 Phase 3's `persatrix account` commands are out under the Rust CLI freeze; its REST endpoints, password change and lockout are the half that boards.
- **(q)** An issue boards only when a phase that boards is its fix. ISSUE-0152 boards because its root fix is the verified agent identity ruling (n) builds. ISSUE-0140 and ISSUE-0117 board because each names agent authentication through RFC 0009 as its designed fix, which either route in ruling (n) delivers on the agents' REST calls. ISSUE-0146 boards only if the identity lock picks gRPC, since it rides with RFC 0040 Phase 2. Every other open issue stays unslotted. The readiness audit records each one's default with a dated note.
- **(r)** v0.4.0 keeps the one-document plan. Plan, scope locks and release checklist go in `docs/v0.4.0-plan.md` under the 3 000-word cap, and its release-prep folds in as a patch release's does. The per-PR breakdown of each phase lives in that RFC's PR plan, an existing kind of document. The first strategy review lives in [project-strategy.md](project-strategy.md#10-review-cadence-and-log). `make plan-status-check` does not judge a minor release, so review holds this ruling. If the plan does not fit, an amendment splits the release; ruling (p) cuts only at the release gate.
- **(s)** The v0.3.x line closes with v0.3.16, and v0.3.17 is withdrawn. Rule 7 in [decisions.md](methodology/decisions.md#sequencing-amendments) moves what a closing train still holds to the next minor, but ruling (m) keeps v0.4.0 to the table above, so the memory-quality follow-ups still marked v0.3.x (ROADMAP §B, §C, §D and §F; the 2026-05-10 decision's MQ items) become unslotted instead, not retired. From this amendment on, the v0.4 line's amendments live in this file; one that would take it past its split point under the size cap goes in a file of its own beside it, `docs/v0.4.x-sequencing-YYYY-MM-DD.md`, which the evidence check already reads, and this file's reading-order note points at it. [v0.3.x-sequencing.md](v0.3.x-sequencing.md) is frozen; only its reading-order note and contents list change, to point here.

### Risk

| Risk | Mitigation |
|------|------------|
| v0.4.0 now carries three or four prerequisite RFCs and is larger than any v0.3.x release. | Each prerequisite is the least a named phase states it needs, and nothing else boards. Ruling (p) gives the plan a cut clause for each cuttable item, and an amendment can split the release. |
| A society backend is a new store, and Postgres would be the stack's first outside service. | Ruling (j)'s scope lock chooses the form with the SQLite route open. No existing data moves unless the lock keeps the channels-store swap, and then Phase 4's migration tooling boards with it. |
| Rule 6: there is no outside evidence. | This amendment adds no capability. Every addition is a dependency the scoped phases state. Every removal is of a placement the goal amendment's table does not name, apart from RFC 0049 Phases 2–4, which ruling (o) takes off the on-ramp. Additions for the goal come through the plan's goal audit, by amendment. |
| Unslotting ten RFCs drops work the goal may need, such as RFC 0021's reminders and RFC 0027's reflection. | They are unslotted, not retired. The goal audit names any the goal needs, and an amendment boards it. RFC 0015, slotted v0.5.0, depends on RFC 0014, so the amendment that opens v0.5.0 slots RFC 0014 first or moves RFC 0015 too. |
| Two amendments are dated 2026-10-18. | They sit in different files with different titles, and the ruling letters continue from (l), so a citation by letter is unambiguous. |
