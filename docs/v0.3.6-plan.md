# v0.3.6 Plan — Web Console (Slice 1: Interactions)

**Status**: 📋 Planning
**Target version**: v0.3.6 (RFC 0048 Phase 1 / Slice 1 — the embedded operator/tester web console)
**Created**: 2026-06-02
**Branch prefix**: `feature/v036-`
**Target**: `main`
**Merge strategy**: Squash merge per [BRANCHING.md](BRANCHING.md)
**Codename**: *Web Console* (proposed — maintainer owns the final codename; "Feel the Taste" is the RFC's motivating phrase)

**Goal**: orchestrate v0.3.6 end-to-end. One user-facing story: **open a URL and talk** — a newcomer runs the orchestrator with `--enable-ui`, opens `http://localhost:8080/ui`, picks a persona, chats with it, and watches a channel, with **zero CLI knowledge**. This is the first vertical slice of the [RFC 0048](rfcs/0048-operator-tester-web-console.md) web console; the backend is mostly a *render-over-existing-API* problem (chat, channel list/history/publish, agent list already exist per RFC 0002 / RFC 0011 / RFC 0016), so a thin first slice lands inside the v0.3.x line.

The umbrella RFC is [RFC 0048](rfcs/0048-operator-tester-web-console.md) (Operator & Tester Web Console — Vertical-Slice, Feature-Toggled UI), 👍 Accepted 2026-06-02. Its **Phase 1 / Slice 1** is the only implementation scope here, and it already has a standalone, self-contained PR plan — [`0048-phase1-pr-plan.md`](rfcs/0048-phase1-pr-plan.md) (6 PRs). That plan owns the per-PR detail; **this master plan wraps it** and adds the release-prep + tag phases, per the phase-1 plan's own note that "if a v0.3.6 master plan is later authored it should reference this workstream rather than the reverse."

Slice 1 in three new-code surfaces (everything else renders over today's API):

- **The embedded-asset scaffold** — `WithUI` `ServerOption` + `--enable-ui` (default off) + `embed.FS` static serving under `/ui/`, following the orchestrator's optional-subsystem pattern.
- **Two read-only endpoints** — `/api/v1/ui/config` (which panels to render) and `/api/v1/ui/context` (who the principal is), plus `config/ui.yaml` + its schema. These are the feature-toggle / forward-compat mechanism.
- **A Svelte SPA + JS build step** — the repo's first JS toolchain, isolated to `web/`, emitting static assets into the embedded directory; a Chat panel and a Channel-timeline panel over the existing API.

**Out of scope** — not part of this story:

- **Memory strip** — deferred to Slice 2 by RFC decision (2026-06-02); it needs a new Go↔Python gRPC read method into the `agents/memory/` tiers, not a thin handler. Its `memory_strip` toggle ships defaulting **off** (Phase 1 PR 2), so the panel lands additively in Slice 2 with no Slice-1 rework.
- **RFC 0048 Slices 2–5** (memory inspector, isolation verifier, cost/observability, control plane) — v0.4.0+, each its own design pass + PR plan; Slice 5 is hard-gated on [RFC 0039](rfcs/0039-user-accounts-authentication.md) auth.
- **Channel real-time push (OQ4)** and **chat token streaming (OQ5)** — named later enhancements; Slice 1 polls and uses synchronous request/response, matching today's API.
- **Authentication / multi-tenancy** — RFC 0039 territory; this slice only commits to *not blocking* it (treats today's no-auth localhost mode as the degenerate `principal=local` single-tenant case).

**Companion documents**: [`0048-phase1-pr-plan.md`](rfcs/0048-phase1-pr-plan.md) (the implementation workstream — the load-bearing document) · [RFC 0048](rfcs/0048-operator-tester-web-console.md) (canonical spec) · [v0.3.5 plan](v0.3.5-plan.md) (structural template) · [v0.3.4 release-prep plan](v0.3.4-release-prep-plan.md) (release-prep template).

## Why this plan exists

The [`0048-phase1-pr-plan.md`](rfcs/0048-phase1-pr-plan.md) is self-contained and could ship without an umbrella. Three reasons it gets one anyway:

1. **A patch release needs a release contract, not just a PR sequence.** Per [ROADMAP §Version Map](../ROADMAP.md#version-map), a version is defined by what a user *can do*. v0.3.6's one-line promise — "open a URL and talk" — is a release-level gate (the console boots, a newcomer chats and watches a channel) that no single PR owns. This plan makes that the acceptance bar and sequences the release-prep + tag phases the PR plan deliberately leaves out.

2. **A repo-first toolchain crosses a release boundary.** Slice 1 adds the repo's **4th language** (JavaScript) and a new build step. The PR plan isolates that to PR 3; this plan owns the release-level guarantee that the Go-only build/test lane stays green against a committed placeholder and only the release/asset lane runs `make ui` — so a v0.3.6 binary embeds a real bundle while a Go-only contributor is never blocked.

3. **The security posture is a release note, not a code change.** The console makes the *unauthenticated* REST surface browser-discoverable. `--enable-ui` defaults off and the orchestrator binds `127.0.0.1`, but "do not expose beyond localhost without an auth reverse proxy until RFC 0039" is an upgrade note the release-prep phase must surface, not bury in a guide.

This is the same thin-orchestration shape as [v0.3.5-plan.md](v0.3.5-plan.md): the RFC's PR plan owns the internals; this doc owns "which phases, in what order, by what release gate."

## Acceptance for v0.3.6

The promise — *open a URL and talk: chat with a persona and watch a channel from the browser, no CLI* — is met when:

- **The scaffold is shippable and inert by default.** `--enable-ui` defaults **off**; with it off, `/ui/` is a clean 404 and no default runtime behaviour changes. `go build ./...` is green with **no** JS toolchain present (the committed placeholder embed compiles).
- **The console boots off its own endpoints.** With `--enable-ui`, the SPA at `/ui/` fetches `/api/v1/ui/config` + `/api/v1/ui/context`, renders only `enabled && available` panels, ignores unknown panels, and derives `user_id` from the `/ui/context` principal — **no hard-coded or free-text user** (the RFC §F forward-compat rule).
- **The Chat panel delivers the hero moment.** Pick a persona (from `GET /api/v1/agents`), send a message (`POST /api/v1/agents/{id}/chat` with `participant_type:"user"`), see the persona's `reply`; the v0.3.5 isolation story is quietly demonstrable via optional session/epoch selectors that pass through to the request.
- **The Channel-timeline panel shows personas interacting.** Channel history renders newest-first (`GET /api/v1/channels/{id}/messages`), stays live by polling with **visibility-pause + error-backoff + head-poll de-dupe**, and optional human publish posts into a group channel and surfaces the agent fan-out on the next poll.
- **The feature-toggle mechanism is real and validated.** `config/ui.yaml` ships Slice-1 panels on (`chat`, `channel_timeline`) and later panels off (`memory_strip`, `cost`); `available` is runtime-derived by the server (never read from YAML); `make validate` checks `config/ui.yaml` against `schemas/ui.schema.json` (a stray `available:` key fails validation).
- **The story is documented and the security posture is loud.** `docs/guides/web-console.md` ships with the localhost-only / reverse-proxy security note; README has a "try it in the browser" entry; CHANGELOG `[0.3.6]` carries the off-by-default upgrade note; `MT-CONSOLE-001` is authored (executed in release-prep).

Out of acceptance: RFC 0048 Slices 2–5 (memory inspector / isolation verifier / cost / control plane — v0.4.0+); the memory strip ([RFC §G](rfcs/0048-operator-tester-web-console.md#g-api-gaps--required-backend-work)); channel real-time push (OQ4); chat token streaming (OQ5); authentication (RFC 0039).

## Risk and mitigations

The per-PR implementation risks live in the [phase-1 PR plan §Risk and Mitigations](rfcs/0048-phase1-pr-plan.md#risk-and-mitigations). The release-level risks:

| Risk | Mitigation |
|------|------------|
| The new JS toolchain (repo's 4th language) destabilises CI or blocks Go-only contributors at a release boundary. | The Go-only build/test lane builds against the committed placeholder embed; only the release/asset lane runs `make ui`. Phase 1 acceptance gates `go build ./...` with no JS toolchain. Frontend work is isolated to `web/`; Node setup is cached on the lockfile. |
| Shipping a browser console makes the **unauthenticated** REST surface more discoverable → accidental beyond-localhost exposure. | `--enable-ui` defaults **off**; the orchestrator binds `127.0.0.1`; the release Upgrade Notes + `docs/guides/web-console.md` state plainly that exposure beyond localhost requires an auth reverse proxy until RFC 0039. The security posture is a first-class release note (Phase 2/3), not buried in a guide. |
| Scope creep: the memory strip or a later slice quietly expands the release past "open a URL and talk." | RFC decision (2026-06-02) defers the memory strip to Slice 2; its toggle ships **off** so it lands additively. [§Candidate fold-ins](#candidate-fold-ins-maintainer-decision) makes every addition an explicit maintainer opt-in; default is Slice 1 alone. |
| Slice 1 ships the interact surface but the release reads as "the whole console," over-promising on memory/cost/control-plane panels. | The Version Map line and CHANGELOG scope it to chat + channel timeline; the RFC's slice roadmap (§E) and this plan's dependency graph name Slices 2–5 as v0.4.0+, so the partial-implementation status is explicit. |
