# v0.3.0 Demo Walkthrough — Three Personas + One Planning Channel

A plain-English guided demo for the v0.3.0 release. By the end of this you
will have three distinct AI personas running in Docker, watched them debate
in a shared planning channel, talked to one of them privately, and verified
that they remember the conversation across a restart.

> **Read this first.** Persatrix talks to the Anthropic API. Every message
> in this demo costs real money. The full demo (Sections 5 → 8) typically
> runs **\$0.20 – \$1.00** depending on how chatty you let the channel get.
> Set a hard spending limit at <https://console.anthropic.com/> before you
> start. See the [Cost Warning in the README](../../README.md#-cost-warning).

---

## What you will demo

The repository ships three demo personas and one demo channel:

| Persona | Role | Voice |
|---------|------|-------|
| **Ember Owl** (`ember-owl`) | VP of Engineering | Direct, big-picture, pragmatic |
| **Iron Fox** (`iron-fox`) | Staff Engineer / Reliability | Detail-focused, cautious, scarred by past incidents |
| **Nova Sparrow** (`nova-sparrow`) | Senior Product Manager | Customer-first, expressive, pushes back on infra-only sprints |

They are configured in [`config/agents.yaml`](../../config/agents.yaml) and
share one declared channel:

| Channel | Address | Members + policy | Pattern |
|---------|---------|------------------|---------|
| **planning** | `group:planning` | `ember-owl`: when_mentioned · `iron-fox`: always · `nova-sparrow`: always | Mixed-policy (RFC 0011 §H) |

`iron-fox` and `nova-sparrow` reply to **every** message in the channel.
`ember-owl` only chimes in when you `@`-mention. That gives you a working
two-agent debate plus an advisor on demand — without the runaway loop you
get when every member is set to `always`.

## 1. What you need

- Docker Desktop (Windows: with WSL 2 backend) running.
- Go 1.24+, Python 3.11+, Rust 1.80+ — only needed if you want to build
  the orchestrator and CLI yourself. The Docker build does this for you.
- An **Anthropic API key**: <https://console.anthropic.com/>
- About **15 minutes** of time and **\$1** of API budget.

If anything below fails, see [§ 9 Troubleshooting](#9-troubleshooting).

---

## 2. One-time setup

Clone and configure:

```bash
git clone https://github.com/mkhomutov/Persatrix.git
cd Persatrix
cp .env.example .env
```

Open `.env` and paste your `ANTHROPIC_API_KEY`. Save the file.

Build the CLI (one binary, used for every command in the demo):

```bash
make build-cli
```

You should now have a `bin/persatrix` (or `bin/persatrix.exe` on Windows)
binary. Test it:

```bash
./bin/persatrix --version
```

---

## 3. Bring up the stack

```bash
docker compose up -d
```

This starts:

- The **orchestrator** (Go) on `http://localhost:8080`.
- Three **task agents** (`planner`, `code-writer`, `code-reviewer`) — used
  for workflow demos, not relevant to this walkthrough.
- Three **persona agents** — `agent-ember-owl`, `agent-iron-fox`, and
  `agent-nova-sparrow`.
- **Observability** — Jaeger (`http://localhost:16686`), Prometheus
  (`http://localhost:9091`).

Watch the logs until you see all three personas register. The line you
are looking for, once per persona, is:

```
agent registered  agent_id=ember-owl
agent registered  agent_id=iron-fox
agent registered  agent_id=nova-sparrow
```

Quick check from the CLI:

```bash
./bin/persatrix channel list
```

You should see the `group:planning` channel with three members.

> **Note.** On a cold first boot, the orchestrator's HTTP listener takes
> a few seconds to come up. If `channel list` returns a connection error,
> wait 5–10 seconds and try again.

## 4. Demo Part A — Talk to one persona privately (chat-as-DM)

The simplest demo: chat with one persona one-on-one. In v0.3.0 this rides
the same channel surface as a group channel — chat is a DM under the hood.

```bash
./bin/persatrix chat ember-owl
```

You will see a `You:` prompt. Try this script:

1. **Introduce yourself.** Type:
   `Hi, I'm Alex. I'm a new tech lead joining your team next month.`
2. **Ask for advice.** Type:
   `What's the one thing you wish new leads knew on day one?`
3. **Type `exit` to leave.**

Now restart the chat:

```bash
./bin/persatrix chat ember-owl
```

Type:
`Do you remember who I am?`

Ember Owl should recognise "Alex" by name. **That is the persona memory
working** — every interaction was committed to the persona's three-tier
memory (notes + episodic + relationship). Type `exit`.

> **What actually happened.** The chat round-tripped via
> `POST /api/v1/agents/ember-owl/chat`, which the orchestrator wrote to
> the canonical `dm:alex:ember-owl` channel and dispatched to the persona
> over gRPC. Memory closes the interaction on idle (default 600 s) and
> writes one episodic entry. See the [chat-as-DM amendment](../rfcs/0011-amendment-chat-as-dm.md)
> for the design.

## 5. Demo Part B — Watch two personas debate in a channel

Open a **second terminal** and start the live channel watcher:

```bash
./bin/persatrix channel watch planning --interval 2
```

Leave that terminal open — it will print every new message in the channel
(polls every 2 seconds).

Back in your first terminal, **join the channel as `alex`** (a fictional
human user). The orchestrator enforces "sender must be a member", so this
one-time step is required before any `--as alex` send will be accepted:

```bash
./bin/persatrix channel join planning --as alex --respond never
```

`--respond never` is the right policy for a human posting prompts — it
makes `alex` a member (so publishes are allowed) without making `alex` a
target the response gate will try to dispatch to.

Now post the planning question:

```bash
./bin/persatrix channel send planning \
    "We have one engineer-month before the v1 release. Should we spend it on a pricing page or on cutting p99 latency?" \
    --as alex
```

Watch the second terminal. Within ~10–30 seconds you should see:

- **Iron Fox** (always-respond, reliability voice) argue that a slow
  product loses customers regardless of pricing.
- **Nova Sparrow** (always-respond, product voice) argue that pricing-page
  conversions are what fund the next engineer-month and pay for that
  latency work.
- The two **may exchange another round** — `iron-fox` reading
  `nova-sparrow`'s reply triggers another response, and vice versa.
- The chain stops when the cascade-depth backstop hits 5 or one of the
  personas writes a closing-style message.

This is the headline v0.3.0 capability: **agents reading each other and
forming opinions across multiple turns, in real time, with persistent
memory of what was said.**

## 6. Demo Part C — Bring in the advisor with `@`-mention

Ember Owl is set to `when_mentioned`, so they have stayed quiet so far.
Pull them in:

```bash
./bin/persatrix channel send planning \
    "ember-owl, you have the call. Pricing page or latency?" \
    --as alex --mention ember-owl
```

The watcher terminal now shows:

- **Ember Owl** weighing in directly (`when_mentioned` policy admits the
  reply because their id is in `mentions[]`).
- Iron Fox + Nova Sparrow **react to Ember Owl's reply** because they are
  `always`-respond.

You have just demonstrated **mixed-policy channels** — the canonical
"two collaborators + advisor" pattern from RFC 0011 §H.

## 7. Demo Part D — Read the transcript and per-persona context

Read the full ordered transcript at any time:

```bash
./bin/persatrix channel history planning --limit 50
```

For automation-friendly output:

```bash
./bin/persatrix channel history planning --limit 50 --json
```

Now talk to Iron Fox alone and ask what they took away from the channel:

```bash
./bin/persatrix chat iron-fox
```

Try:
`What did we just decide in the planning channel?`

Iron Fox should reference the exchange — **per-channel scoped memory
recall** is working. Each persona ingested every channel message into its
own memory tier, so each has a personal recollection of the same
conversation.

## 8. Demo Part E — Restart and verify catch-up replay

This proves the v0.3.0 missed-message recovery contract.

Stop one persona while leaving the channel active:

```bash
docker compose stop agent-iron-fox
```

From your first terminal, post **two new messages** while Iron Fox is
down:

```bash
./bin/persatrix channel send planning \
    "On reflection — let's split the engineer-month: 2 weeks pricing, 2 weeks latency." \
    --as alex
./bin/persatrix channel send planning \
    "Anyone disagree?" \
    --as alex
```

Nova Sparrow will reply (always-respond). Iron Fox is down, so misses
both. Now bring Iron Fox back:

```bash
docker compose start agent-iron-fox
docker compose logs -f agent-iron-fox
```

In Iron Fox's startup logs you should see:

```
channel.messages.replayed channel_id=group:planning count=...
```

Iron Fox **fetched the last 50 messages** in the channel, ingested them
into memory, but **suppressed any outbound replies** — so they did not
spam the channel with stale responses. Stop tailing logs (`Ctrl-C`).

Verify Iron Fox's recall is now up to date:

```bash
./bin/persatrix chat iron-fox
```

Try: `What's our current plan for the engineer-month?`

Iron Fox should describe the 2-week split correctly, even though they were
offline when you announced it.

## 9. Troubleshooting

**`channel list` returns a connection error.**
The orchestrator hasn't finished starting yet. Wait 10 seconds and retry.
If it persists, check `docker compose logs orchestrator`.

**One of the personas never replies.**
Check `docker compose logs agent-<id>`. The two most common causes:

- `ANTHROPIC_API_KEY` is missing or invalid → look for `401`/`403` from
  the API.
- Per-day cost budget hit → look for `cost budget exceeded` in the
  orchestrator logs.

**`channel send … --as alex` returns `403 Forbidden: sender is not a
member of the channel`.**
You skipped the join step at the top of Section 5. The orchestrator
enforces sender-must-be-member on group channels — `alex` is not in
`config/channels.yaml`, so they have to join at runtime. Run
`./bin/persatrix channel join planning --as alex --respond never` once,
then re-run the send.

**The personas are talking, but the watcher shows nothing.**
The watcher polls — make sure you ran `channel watch planning` (not
`channel watch group:planning`; both work but spelling matters). Run
`channel history planning` to confirm messages are landing.

**Iron Fox's restart did not show `channel.messages.replayed`.**
The catch-up is best-effort — if the channel is empty when the agent
restarts, the line is omitted. Post a message before restarting next time.

**The cascade is too chatty / costing too much.**
Edit [`config/channels.yaml`](../../config/channels.yaml) and change the
two `always` members to `when_mentioned`. Re-up the orchestrator
(`docker compose up -d --force-recreate orchestrator`) — channel config
divergence is loud failure, so the orchestrator picks up the new policy on
restart.

---

## 10. Stopping cleanly

When you are done, **explicitly stop the agents** so they do not keep
ticking and consuming budget:

```bash
docker compose down
```

If you want to also wipe persona memory for a fresh-start re-demo:

```bash
docker compose down -v   # -v removes named volumes incl. memory stores
```

## 11. What this demo shows about v0.3.0

- **Persistent personas with memory** — Ember Owl recognised you across
  restart (Part A).
- **Multi-agent channels with per-member response policies** — Iron Fox
  + Nova Sparrow debate, Ember Owl advises on demand (Parts B + C).
- **Per-channel scoped recall** — each persona has its own slice of the
  conversation in memory (Part D).
- **At-most-once delivery + on-startup catch-up** — a persona that misses
  messages while down replays them on restart but does not blast stale
  responses (Part E).
- **The chat-as-DM unification** — the `chat` and `channel` surfaces ride
  the same channels publish-and-await loop (RFC 0011 amendment).
