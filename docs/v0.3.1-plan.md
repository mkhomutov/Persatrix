## Why this plan exists

Two reasons v0.3.1 deserves an umbrella rather than two parallel RFC PR plans:

1. **Load-bearing cross-RFC sequencing.** [RFC 0031 OQ #4](rfcs/0031-per-session-namespacing-channels.md#open-questions): Phase 1 must land *before* RFC 0029 Phase 1 freezes the `MemoryStore` facade. RFC 0026's storage runs through that facade. The three-way ordering (0031 P1 columns → 0026 read path → 0029 P1 facade freeze in v0.3.2) is implicit otherwise.
2. **Public v0.3.1 commitment.** [Release checklist §6](v0.3.0-release-checklist.md#6-known-gaps-to-document-in-release-notes) links [MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md) Leg 1 at RFC 0026 as the fix. Promoting that to a plan makes the acceptance bar (Legs 1/2/5 flip green) visible at implementation level.

Owns "what order, in what step, by what gate."

## Acceptance for v0.3.1

The user-facing promise — *"the persona remembers stated facts about you across interactions, follows the conversation it is currently having, and every test/CI run is auto-isolated from prior runs by default"* — is met when:

- The persona references a stated fact about a named entity in a later interaction without keyword-overlap seeding ([MT-MEMORY-005](manual-tests/MT-MEMORY-005-dementia-test.md) Legs 1, 2, 5 flip green per [RFC 0026 §Phase 3](rfcs/0026-declarative-facts-tier.md#phase-3-reinforcement--retraction)).
- The persona answers `"what did you just ask?"` correctly within one DM session and resolves referential follow-ups (`"I like it"`) — [ISSUE-0052](issues/ISSUE-0052-persona-conversational-working-memory-gap.md) repro per [RFC 0034 §Goals](rfcs/0034-persona-conversational-working-memory.md#goals); new `MT-PERSONA-CONVERSATION-001` ships green.
- A second test run with the same channel name and same `--user` under a different `PERSATRIX_SESSION_ID` shows **no** prior-run carryover at the storage layer — every new row tagged with the new session id. (Recall filtering lands in RFC 0031 Phase 2, uncommitted v0.3.x.)
- `make reset` operator-guide subsections in [channels.md](guides/channels.md) and [persona-agents.md](guides/persona-agents.md) carry a forward-pointer at RFC 0031's planned CLI (Phase 3).

Out of acceptance: cross-session recall, `persatrix session …` CLI, OTEL `persatrix.session_id` attribute (RFC 0031 Phases 2–4); RFC 0034 Phases 2–3 (group channels, instrumentation).

## Dependency Graph (RFC-level)

Source of truth lives in [v0.3.x-sequencing.md §New dependency chain](v0.3.x-sequencing.md#new-dependency-chain). This is the v0.3.1-slice:

```
v0.3.0 complete (✅ released 2026-05-12)
    │
    ├── RFC 0031 Phase 1 (sessions table + four session_id columns + env-var plumbing)
    │       ├── depends on RFC 0011 (closed) — channels schema
    │       ├── hard gate: RFC 0031 OQ #1 + OQ #8 resolved
    │       └── soft-blocks RFC 0029 Phase 1 (v0.3.2) — facade must carry session_id
    │
    ├── RFC 0026 (Declarative Facts Tier — full, Phases 1–3)
    │       ├── depends on RFC 0020 (closed) for interaction-close hook
    │       └── facts table includes session_id from day one (consumes 0031 P1 migration)
    │
    └── RFC 0034 Phase 1 (Persona Conversational Working Memory — DM channels)
            ├── depends on RFC 0011 (closed) — channel store + history endpoint
            └── hard gate: RFC 0034 OQ #1 (per-session vs. per-channel transcript window) resolved
                 │
                 →  v0.3.1 — Memory Quality + Session Plumbing + Conversational Working Memory
```

**Ordering**: RFC 0031 Phase 1's column-add migration merges *before* RFC 0026's storage PR; the `facts` table is created with `session_id TEXT NOT NULL DEFAULT 'legacy'` from day one. RFC 0034 Phase 1 is independent and merges in parallel.

> **Maintenance**: if you edit dependency direction here, update [v0.3.x-sequencing.md §New dependency chain](v0.3.x-sequencing.md#new-dependency-chain) in the same commit.

## Risk and mitigations

| Risk | Mitigation |
|------|------------|
| [RFC 0031 OQ #1](rfcs/0031-per-session-namespacing-channels.md#open-questions) (dementia-test continuity / default-recall) can invalidate the v0.3.1 demo if shipped wrong — Phase 2 (recall filtering) is not in v0.3.1, but the v0.3.1 facade signature implicitly commits the Phase 2 default. | Hard gate on this PR ([Phase 0 acceptance](#phase-0--this-pr)). The MT-MEMORY-005 demo for v0.3.1 runs end-to-end under one session id; cross-session-recall stays a Phase 2 acceptance gate. |
| [RFC 0031 OQ #8](rfcs/0031-per-session-namespacing-channels.md#open-questions) (`session_id` wire-name collision against RFC 0016 `ChatRequest.session_id`) — Phase 1 lands the column name in four tables + the env-var suffix; reversing is non-additive. | Same hard gate as OQ #1; resolution comments linked in this PR's description before review exits. |
| [RFC 0034 OQ #1](rfcs/0034-persona-conversational-working-memory.md#open-questions) (per-session vs. per-channel transcript window) — the wire format implicitly commits the default once Phase 1 PR 1 merges. | Hard gate on the RFC 0034 PR plan PR (row 1b) before its first implementation PR opens. The proposed default (per-channel) is recorded in the RFC and must be ratified in review. |
| RFC 0026 needs `session_id` on the new `facts` table from day one, but the PR plan is authored before RFC 0031's migration framework is final. | Phase 1 lands both PR plans in one PR; the RFC 0026 storage PR cites the RFC 0031 P1 migration step by name. If the migration framework shifts during implementation, the RFC 0026 plan is amended in the same PR that lands the shift. |
| RFC 0034 absorbs late into the v0.3.1 scope (amendment 2026-05-15) and risks pushing the v0.3.1 cut. | RFC 0034 Phase 1 is DM-only with no cross-RFC dependency on RFC 0026; merges in parallel. Phases 2–3 are explicitly [Out of scope](#out-of-scope). |
| Dropping RFC 0029 Phase 1 from v0.3.1 delays the v0.4.0 RFC 0028 implementation start by one patch. | RFC 0028 is v0.4.0 per [RFC Master Index](../ROADMAP.md#rfc-master-index); v0.4.0 does not open until v0.3.3 cuts. One patch of slippage makes zero difference. |
| Three-RFC scope might feel small enough to bundle with v0.3.2 into a single patch. | Each patch carries one user-facing story per [§Version Map](../ROADMAP.md#version-map). v0.3.1 story is "memory works — long-term *and* in-conversation"; v0.3.2 story is "cost is bounded." Bundling violates the contract. |
| Master plan rots as Phase 2 progresses. | Status updates are part of every step PR's checklist (see [ROADMAP hygiene](#roadmap-hygiene)). Reviewers reject step PRs that flip RFC implementation status without touching the per-RFC plan's progress table. |
| RFC 0030 Phase 1 surfaces during implementation and pressure builds to absorb it. | [Out of scope](#out-of-scope) is the single arbiter. RFC 0030 Layer 1 is hard-gated on RFC 0023 Phase 1; shipping in v0.3.1 means Layer 1 is wire-reserved/inert — the half-deliverable pattern this plan exists to prevent. |
