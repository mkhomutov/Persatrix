# v0.3.0 Channel Test Findings — PR Plan

**Source**: Manual end-to-end testing of the v0.3.0 channels stack — three persona agents in a shared `group:planning` channel with mixed `respond_policy` (one `when_mentioned`, two `always`).
**Branch prefix**: `fix/v030-channel-`
**Target**: `main`
**Merge strategy**: Squash merge per [BRANCHING.md](BRANCHING.md)

> **Status**: ✅ Complete — all 6 PRs merged before the v0.3.0 tag. PR 1 [#318](https://github.com/mkhomutov/Persatrix/pull/318), PR 2 [#319](https://github.com/mkhomutov/Persatrix/pull/319), PR 3 [#321](https://github.com/mkhomutov/Persatrix/pull/321), PR 4 [#322](https://github.com/mkhomutov/Persatrix/pull/322), PR 5 [#323](https://github.com/mkhomutov/Persatrix/pull/323), PR 6 [#324](https://github.com/mkhomutov/Persatrix/pull/324). ---

## Findings being fixed

| ID | Finding | Severity |
|----|---------|----------|
| F-1 | **Cascade-depth backstop not enforced across the publish→fanout boundary.** RFC 0011 §D claims `max_cascade_depth=5` caps cross-agent fanout. In practice, `cascade_depth` is dropped at the REST publish hop and reset to `0` on every gRPC dispatch back to agents. With two `always`-respond personas in one channel, a single user prompt produced ~60 persona replies in ~10 minutes and was still firing when halted manually. Bounding the loop closes the runaway path but does **not** close the cost-ceiling story: even at cap=5 a fully populated channel still pays `members × depth` LLM calls per publish; that gate is its own follow-up (see Future PRs §"Cost-ceiling enforcement"). | **Blocker** |
| F-2 | **Persona impersonation.** A persona responded to a user prompt with `"Hey! I'm Alex, Staff Engineer and Reliability Lead here…"` — adopting the user's name as a first-person role. System-prompt grounding gap. | **High** |
| F-3 | **Cross-run state bleed.** Persona memory and channel history persist across stack restarts via named Docker volumes. A second test run with the same channel name and same user identity inherits prior content unless volumes are explicitly purged. The personas surface old participants and topics from prior runs, which steers the next conversation off-topic within ~2 turns. | **Medium** |

F-1 is a contract violation against an already-specified design ([0011-channels-bridges.md §D](rfcs/0011-channels-bridges.md#d-agent-integration)), not a design gap — **no new RFC is required**. An amendment doc captures the wire-boundary oversight in the original PR plan.

## PR sequence

### PR 1: `fix/v030-channel-cascade-depth-wire-amendment` — Amendment + Schemas

**Depends on**: nothing.
**Fixes**: F-1 (schema groundwork).

#### Scope

- New `docs/rfcs/0011-amendment-cascade-depth-wire-propagation.md`. Quote the wrong claim from [0011-channels-bridges.md §D](rfcs/0011-channels-bridges.md#d-agent-integration) (*"No change to the cascade mechanism is required"*), name the oversight (publish payload + gRPC dispatch event both omit the field), specify the contract:
  - **REST**: use the existing `metadata` seat on [publishMessageRequest](../internal/server/channel_types.go#L36), key `metadata.cascade_depth` (integer). The seat already round-trips into [ChannelMessage.Metadata](../internal/channels/channels.go#L89) — no struct-field change.
  - **gRPC**: `ChannelMessageEvent` has no metadata map (fields 1–10 all typed), so add `int32 cascade_depth = 11`.
  - The REST/proto asymmetry is deliberate — mirrors the `timestamp` divergence at [proto/task.proto:141-148](../proto/task.proto#L141-L148).
  - State that **primary enforcement moves to the orchestrator** (Go); the Python `EventDispatcher` check is retained as defense-in-depth.
- Update `schemas/channel.schema.json` to document `metadata.cascade_depth` as an optional integer, range `[0, 64]` (server clamps `> max_cascade_depth` down rather than rejecting).
- Update `proto/task.proto` to add `int32 cascade_depth = 11` on `ChannelMessageEvent`; regenerate via `make proto` and commit the artifacts.

#### Key implementation details

- Amendment doc lands first because both PR 2 and PR 3 cite it from their commit messages, and the schema/proto change is the load-bearing contract change reviewers need to evaluate against the design.
- `cascade_depth` is **partially untrusted** — the orchestrator clamps `[0, max_cascade_depth]` on inbound to prevent over-cap poisoning. The clamp does **not** defend against reset-to-0: a misbehaving publisher can emit depth 0 every time and there is no orchestrator-side signal to detect that without parent-message correlation. The amendment doc states both the clamp's scope and its limit; closing the reset-to-0 hole is deferred to Future PRs §"Authoritative depth derivation" (orchestrator looks up the parent message, uses `parent.depth + 1`, ignores the publisher's claim).
- No behavior change in this PR — Go still ignores the field, Python still doesn't emit it. Wire compatibility only.

#### Tests

- JSON schema validation: `cascade_depth: 0`, `cascade_depth: 5`, `cascade_depth: -1` (rejected), `cascade_depth: 9999` (accepted, will be clamped server-side in PR 2).
- Proto round-trip test: marshal/unmarshal with and without `cascade_depth` set.

#### PR checklist

- [ ] Amendment doc cross-linked from [0011-channels-bridges.md §D](rfcs/0011-channels-bridges.md#d-agent-integration) and the [0011-pr-plan.md](rfcs/0011-pr-plan.md) "Amendments" section (or equivalent index).
- [ ] `make validate` green.
- [ ] Generated proto artifacts committed and reproducible (`make proto` is a no-op after merge).

### PR 2: `fix/v030-channel-cascade-depth-go-enforcement` — Orchestrator Propagates + Caps

**Depends on**: PR 1 (schema + proto).
**Fixes**: F-1 (primary enforcement).

#### Scope

- `internal/server/channel_handlers.go` — publish handler reads `cascade_depth` from `req.Metadata["cascade_depth"]`, clamps to `[0, max_cascade_depth]`, threads it onto `ChannelMessage.Metadata["cascade_depth"]` (no struct-field change required).
- `internal/channels/router.go` — `Publish` reads the inbound depth from `msg.Metadata["cascade_depth"]`, drops fanout when `depth >= max_cascade_depth`, otherwise emits child events with `cascade_depth = inbound` (no further increment). **Increment site is the agent on outbound**, not the orchestrator: [dispatch.py:162](../agents/dispatch.py#L162) already passes `cascade_depth=depth+1` to the executor, so a publish at depth D arrives at the orchestrator already representing "this event lives at depth D." Orchestrator double-incrementing would fire the cap one hop earlier than RFC §D's "5" — the amendment doc pins this so a future reviewer doesn't restore the double-increment.
- `internal/channels/grpc_dispatcher.go` — outbound gRPC event sets `event.CascadeDepth` from `msg.Metadata["cascade_depth"]` (typed field from PR 1).
- `internal/defaults/defaults.go` — surface `max_cascade_depth` (default `5`) as a config knob. The Python dispatcher's [`max_cascade_depth=5`](../agents/dispatch.py#L43) stays aligned (one conceptual cap, two enforcement points) so the backstop fires only on a genuine primary-enforcement failure.
- Structured-log line on drop: `channels: cascade limit reached channel_id=… sender_id=… depth=…`.

#### Key implementation details

- The orchestrator is the **primary** enforcement point because it sits on the trust boundary — agents are downstream consumers and can't be relied on to honor the cap themselves. Move the conceptual "primary" status here; demote the Python check in PR 3 to "defense-in-depth."
- Drop, don't error. A capped fanout should not return a 4xx to the publisher (the publish itself succeeded — only the cascade is capped). Log + metric increment is enough.
- New counter: `channel.messages.cascade_capped{channel_type}`. Label on `channel_type` (not `channel_id`) to match the existing low-cardinality discipline at [internal/channels/fanout.go:103-106](../internal/channels/fanout.go#L103-L106) — `channel_id` is unbounded and would explode the metric's time-series count. The full `channel_id` is available on the structured log line for incident-driven pivots.

#### Tests

- `router_test.go`: publish with `cascade_depth=0,1,4,5,6`; assert fanout fires for ≤4 and is dropped at ≥5 (child events carry inbound depth unchanged — increment lives upstream of the publish).
- `router_test.go`: publish with `cascade_depth=99`; assert it is clamped to `max_cascade_depth` before the drop check. Explicitly **not asserted**: reset-to-0 detection (out of scope per PR 1 amendment doc).
- `channel_handlers_test.go`: POST without `metadata.cascade_depth` → defaults to `0`; POST with `-1` → 400; POST with `metadata.cascade_depth=99` → 200, clamped at the router boundary so the clamp covers REST and any future ingress.
- `grpc_dispatcher_test.go`: outbound dispatch event carries the depth on the proto's typed `cascade_depth` field.
- Counter assertion: `channel.messages.cascade_capped{channel_type=...}` increments by the number of suppressed fanouts.

#### PR checklist

- [ ] `make test` Go suite green; new tests named so they cannot be silently dropped.
- [ ] `channel.messages.cascade_capped` metric documented in [docs/guides/channels.md](guides/channels.md) operator section.
- [ ] Manual smoke: re-run a two-`always`-member channel scenario against this build; assert the cascade terminates by depth 5 and the new log line fires.

### PR 3: `fix/v030-channel-cascade-depth-python-roundtrip` — Publisher Emits + Servicer Ingests

**Depends on**: PR 2 (orchestrator must already handle the field correctly so a depth-emitting Python build does not desync against an older orchestrator on a partial deploy).
**Fixes**: F-1 (close the round-trip).

#### Scope

- `agents/channel_publisher.py` — `HTTPChannelPublisher.publish` accepts `cascade_depth: int` and threads it into the POST body's `metadata` map under the key `cascade_depth`.
- `agents/action_executor.py` — the REST-publish branch forwards its `cascade_depth=` kwarg (already received at [action_executor.py#L90](../agents/action_executor.py#L90)) into the publisher call. The executor does not read event metadata — the *dispatcher* does that; the executor receives the value as a kwarg already incremented at [dispatch.py:162](../agents/dispatch.py#L162). The +1 stays agent-side per PR 2's "orchestrator forwards as-is."
- `agents/server_servicers.py` — gRPC receive path reads `request.cascade_depth` (typed proto field from PR 1) and seeds inbound `AgentEvent.metadata["cascade_depth"]` so [dispatch.py:108](../agents/dispatch.py#L108) sees the wire value instead of defaulting to `0`.
- The Python `EventDispatcher.max_cascade_depth=5` check at [dispatch.py:108-114](../agents/dispatch.py#L108-L114) stays. The [response_gate.py:43-49](../agents/response_gate.py#L43-L49) docstring already labels it "backstop" — the doc edit here clarifies that the *cross-agent* primary cascade-depth enforcement now lives in the Go orchestrator's fanout cap (PR 2); the Python dispatcher cap remains the defense-in-depth backstop for the legacy in-process mention cascade and any wire-side regression.

#### Key implementation details

- The publisher does not invent a depth — it forwards what the executor was given. If the executor was invoked from a context with no event metadata (tick-originated, chat surface, etc.) the value is `0` and the orchestrator's cap takes over from there.
- Adversarial-publisher concern is handled by PR 2's clamp; this PR is purely correctness on the cooperative path.

#### Tests

- `tests/unit/python/test_action_executor.py`: given `cascade_depth=3` on the executor kwarg, the publish call gets `cascade_depth=3` (executor forwards as-is; `+1` already happened at the dispatcher).
- New `tests/unit/python/test_channel_publisher_cascade_depth.py`: publish stub asserts `cascade_depth` is present in the POST body's `metadata` map when set, and the entire `metadata` map is omitted when not set (no `metadata: {}` on every publish).
- Extend `tests/unit/python/test_event_dispatcher.py`: inbound `cascade_depth=4` increments to `5` on child metadata; executor receives `cascade_depth=5` via kwarg; cap-drop fires on the *next* inbound event for that agent.
- Existing `tests/unit/python/test_response_gate_cascade_backstop.py` continues to pass without modification.

#### PR checklist

- [ ] `make test` Python suite green; new tests named so they cannot be silently dropped.
- [ ] [agents/response_gate.py:43-49](../agents/response_gate.py#L43-L49) docstring updated to call the Python dispatcher check "defense-in-depth" and the Go orchestrator cap "primary."

### PR 4: `fix/v030-channel-cascade-depth-cross-process-test` — Integration Pin

**Depends on**: PR 3.
**Fixes**: F-1 (regression pin).

#### Scope

- New `tests/integration/test_channel_cascade_backstop_cross_process.py`: spin up the full Docker stack (or the existing integration harness), declare a two-`always`-member group channel, publish one user message, wait for cascade to terminate, assert the channel contains **at most 8** reply messages. Derivation: cap=5 with `depth >= 5 → drop` means only depths 1–4 deliver, and two `always` members each reply once per depth = `2 × 4 = 8`. The bound is `<= 8` (not `== 8`) to tolerate per-recipient timeout variations; tightening to `== 8` is a follow-up once CI determinism is shown.
- Update [docs/manual-tests/v0.3.0-execution-report.md](manual-tests/v0.3.0-execution-report.md) with a new row for the cascade-backstop manual check, citing this PR's commit.

#### Key implementation details

- The integration test is the contract-pin that catches a future regression where someone restores the old "publish doesn't carry depth" behavior. PRs 2 and 3's unit tests would still pass in that case (each is correct in isolation); only this PR can fail.
- Test must include a generous wall-clock timeout (~2 min) and assert the count *stabilizes* — a hung test that never sees a cascade would otherwise pass by waiting forever.

#### Tests

- The PR is the test. No further tests required.

#### PR checklist

- [ ] Test runs in CI under the existing integration job.
- [ ] Manual test report row added.

### PR 5: `fix/v030-channel-persona-impersonation` — Grounding the Persona System Prompt

**Depends on**: nothing.
**Fixes**: F-2.

#### Scope

- The shared persona system prompt (in `config/agents.yaml` or wherever the system-prompt prefix is assembled — likely [agents/persona_runtime/prompt_assembly.py](../agents/persona_runtime/prompt_assembly.py) or an equivalent template).
- Add a grounding clause near the top: *"You are not the user. If the user addresses you by a name, treat that as the user's name, not a role you adopt. Never open a reply with `I'm <user-name>` or otherwise speak as the user."*
- Optional: add the persona's own name and id as an explicit invariant block (*"You are <Persona Name> (`<persona-id>`). When you reply, you are speaking as that persona."*) — already partly present, may need strengthening.

#### Key implementation details

- The prompt change should be **shared across all personas**, not duplicated into each `agents.yaml` entry. House style is to keep persona-specific prose (voice, backstory) in the YAML and grounding invariants in the runtime/template.
- Regression risk: a too-restrictive grounding clause could make personas refuse to introduce themselves or use first-person at all. Keep the clause narrow: *don't impersonate the user*, not *don't speak in first person*.

#### Tests

- **Primary (deterministic, unit-level)** — new `tests/unit/python/test_persona_grounding.py`: assemble the system prompt for each persona in `config/agents.yaml` and assert the grounding clause appears verbatim in the assembled output. This is the load-bearing assertion: prompt-assembly is the deterministic invariant; whether the model honors the clause is downstream.
- **Optional (probabilistic, integration-level)** — gated behind `@pytest.mark.integration` and a real model call: feed a persona a prompt that starts with *"Hi, I'm Alex…"*, run one turn, assert no reply opens with `I'm Alex` / `I am Alex` (case-insensitive, leading-whitespace-tolerant). Treat failures as a signal to strengthen the grounding clause, not as a primary regression gate.

#### PR checklist

- [ ] Grounding clause visible in `make agent-prompt-dump <persona-id>` (or equivalent debug path).
- [ ] All persona agents in `config/agents.yaml` re-tested manually for the chat-as-DM intro flow: each persona introduces themselves *as themselves*, and recognises the user by name without adopting it. Manual-test record lands as a new row in [docs/manual-tests/MT-PERSONA-002.md](manual-tests/MT-PERSONA-002.md) (or the closest existing MT-PERSONA-* doc — the PR must explicitly name which one, not leave it as "operator's choice").

## Future PRs

Further test rounds against the v0.3.0 channels stack are expected to surface additional defects. New PRs will be appended to this plan as findings land, with the same `fix/v030-channel-*` branch prefix. Likely areas worth probing next:

- **Authoritative depth derivation** — PRs 1–4 bound runaway cascades on the cooperative path but do not defend against a publisher resetting `cascade_depth=0`. Complete fix: extend the publish surface with `published_in_reply_to: message_id`, look up the parent message in `ChannelStore`, use `parent.depth + 1` regardless of publisher claim. Same lookup shape as `thread_parent_sender_id` at [router.go:222-236](../internal/channels/router.go#L222-L236). Split from PRs 1–4 to keep immediate F-1 scope reviewable; the trust model is documented in PR 1's amendment doc.
- **Mention routing** — does the orchestrator-side `mentions[]` field reach the response gate as the structured signal, or does it ride only in the message body? Mixed-policy channels depend on this being precise.
- **Per-persona channel recall accuracy** — when a persona is queried via DM about a channel exchange it participated in, does its recap match the channel transcript, or paraphrase off-target? Tied to RFC 0008 / 0020 memory-scoping contracts.
- **On-startup catch-up replay** — does the documented `channel.messages.replayed count=…` log line actually fire on agent restart, and is the suppress-outbound-replies invariant honored (no stale responses blasted into the channel)?
- **Cost-ceiling enforcement** — F-1 above demonstrates that a single prompt can drive ~160 Anthropic API calls before any backstop fires. Even after F-1 is fixed, the cooperative-path cost still scales as `members × depth` per publish (8 in the two-persona test, 250 in a full 50-member channel at cap=5). The per-channel / per-day cost budget path warrants its own focused test pass with deliberate cap-trigger.
