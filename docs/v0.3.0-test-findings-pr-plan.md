# v0.3.0 Channel Test Findings — PR Plan

**Source**: Manual end-to-end testing of the v0.3.0 channels stack — three persona agents in a shared `group:planning` channel with mixed `respond_policy` (one `when_mentioned`, two `always`).
**Branch prefix**: `fix/v030-channel-`
**Target**: `main`
**Merge strategy**: Squash merge per [BRANCHING.md](BRANCHING.md)

> **Status**: Draft. Further PRs may be appended as testing continues to surface additional defects.

---

## Findings being fixed

| ID | Finding | Severity |
|----|---------|----------|
| F-1 | **Cascade-depth backstop not enforced across the publish→fanout boundary.** RFC 0011 §D claims `max_cascade_depth=5` caps cross-agent fanout. In practice, `cascade_depth` is dropped at the REST publish hop and reset to `0` on every gRPC dispatch back to agents. With two `always`-respond personas in one channel, a single user prompt produced ~60 persona replies in ~10 minutes and was still firing when halted manually. | **Blocker** |
| F-2 | **Persona impersonation.** A persona responded to a user prompt with `"Hey! I'm Alex, Staff Engineer and Reliability Lead here…"` — adopting the user's name as a first-person role. System-prompt grounding gap. | **High** |
| F-3 | **Cross-run state bleed.** Persona memory and channel history persist across stack restarts via named Docker volumes. A second test run with the same channel name and same user identity inherits prior content unless volumes are explicitly purged. The personas surface old participants and topics from prior runs, which steers the next conversation off-topic within ~2 turns. | **Medium** |

F-1 is a contract violation against an already-specified design ([0011-channels-bridges.md §D](rfcs/0011-channels-bridges.md#d-response-policy-and-the-gate)), not a design gap — **no new RFC is required**. An amendment doc captures the wire-boundary oversight in the original PR plan.

## PR sequence

### PR 1: `fix/v030-channel-cascade-depth-wire-amendment` — Amendment + Schemas

**Depends on**: nothing.
**Fixes**: F-1 (schema groundwork).

#### Scope

- New `docs/rfcs/0011-amendment-cascade-depth-wire-propagation.md`. Quote the wrong claim from [0011-channels-bridges.md §D](rfcs/0011-channels-bridges.md#d-response-policy-and-the-gate) (*"No change to the cascade mechanism is required"*), name the oversight (publish payload + gRPC dispatch event both omit the field), specify the contract: `cascade_depth: int32` on the publish request body and on the dispatch event metadata. State that **primary enforcement moves to the orchestrator** (Go) and the Python `EventDispatcher` check is retained as defense-in-depth.
- Update `schemas/channel.schema.json` (or whichever JSON schema covers the publish request body) to add an optional `cascade_depth` integer field, default `0`, range `[0, 64]`. Server clamps anything above `max_cascade_depth` down to the cap rather than rejecting — keeps the surface forward-compatible.
- Update the relevant proto (likely the channel-dispatch event proto under `proto/`) to carry `cascade_depth` alongside the existing event metadata. If the proto already has a generic metadata map, route it through that and document the key; if not, add a typed field.
- Regenerate generated code (`make proto` / equivalent), commit the regen artifacts.

#### Key implementation details

- Amendment doc lands first because both PR 2 and PR 3 cite it from their commit messages, and the schema/proto change is the load-bearing contract change reviewers need to evaluate against the design.
- `cascade_depth` is **untrusted from the publisher** — the orchestrator must clamp to `[0, max_cascade_depth]` on inbound to prevent a hostile or buggy agent from resetting it to `0`. The amendment doc must state this invariant.
- No behavior change in this PR — Go still ignores the field, Python still doesn't emit it. Wire compatibility only.

#### Tests

- JSON schema validation: `cascade_depth: 0`, `cascade_depth: 5`, `cascade_depth: -1` (rejected), `cascade_depth: 9999` (accepted, will be clamped server-side in PR 2).
- Proto round-trip test: marshal/unmarshal with and without `cascade_depth` set.

#### PR checklist

- [ ] Amendment doc cross-linked from [0011-channels-bridges.md §D](rfcs/0011-channels-bridges.md#d-response-policy-and-the-gate) and the [0011-pr-plan.md](rfcs/0011-pr-plan.md) "Amendments" section (or equivalent index).
- [ ] `make validate` green.
- [ ] Generated proto artifacts committed and reproducible (`make proto` is a no-op after merge).

### PR 2: `fix/v030-channel-cascade-depth-go-enforcement` — Orchestrator Propagates + Caps

**Depends on**: PR 1 (schema + proto).
**Fixes**: F-1 (primary enforcement).

#### Scope

- `internal/server/channel_handlers.go` — the publish handler reads `cascade_depth` from the request body, clamps to `[0, max_cascade_depth]`, and threads it to the router.
- `internal/channels/router.go` — `Publish` (or the equivalent fanout entry point) reads the inbound depth, drops fanout when `depth >= max_cascade_depth`, otherwise emits child events with `cascade_depth = inbound + 1`.
- `internal/channels/grpc_dispatcher.go` — the outbound gRPC dispatch event carries the depth in the appropriate metadata slot defined in PR 1.
- `internal/defaults/defaults.go` (or wherever channel defaults live) — surface `max_cascade_depth` (default `5`) as a config knob.
- Structured-log line on drop: `channels: cascade limit reached channel_id=… sender_id=… depth=…` so an operator can detect the case in logs.

#### Key implementation details

- The orchestrator is the **primary** enforcement point because it sits on the trust boundary — agents are downstream consumers and can't be relied on to honor the cap themselves. Move the conceptual "primary" status here; demote the Python check in PR 3 to "defense-in-depth."
- Drop, don't error. A capped fanout should not return a 4xx to the publisher (the publish itself succeeded — only the cascade is capped). Log + metric increment is enough.
- New counter (or new label on the existing `channel.messages.gated` counter): `channel.messages.cascade_capped{channel_id,depth}`.

#### Tests

- `router_test.go`: publish with `cascade_depth=0,1,4,5,6`; assert fanout fires for ≤4 and is dropped at ≥5.
- `router_test.go`: publish with `cascade_depth=99` (above clamp); assert it is clamped to `max_cascade_depth` before the drop check, so a hostile publisher submitting a sky-high depth doesn't poison downstream events with garbage metadata.
- `channel_handlers_test.go`: POST without the field → handler defaults to `0`; POST with `-1` → 400.
- `grpc_dispatcher_test.go`: outbound dispatch event carries the depth on the wire.
- Counter assertion: `channel.messages.cascade_capped` increments by exactly the number of suppressed fanouts.

#### PR checklist

- [ ] `make test` Go suite green; new tests named so they cannot be silently dropped.
- [ ] `channel.messages.cascade_capped` metric documented in [docs/guides/channels.md](guides/channels.md) operator section.
- [ ] Manual smoke: re-run a two-`always`-member channel scenario against this build; assert the cascade terminates by depth 5 and the new log line fires.

### PR 3: `fix/v030-channel-cascade-depth-python-roundtrip` — Publisher Emits + Servicer Ingests

**Depends on**: PR 2 (orchestrator must already handle the field correctly so a depth-emitting Python build does not desync against an older orchestrator on a partial deploy).
**Fixes**: F-1 (close the round-trip).

#### Scope

- `agents/channel_publisher.py` — `HTTPChannelPublisher.publish` accepts `cascade_depth: int` and includes it in the POST body.
- `agents/action_executor.py` — the `SEND_CHANNEL_MESSAGE` path sources `cascade_depth` from the originating event metadata (the executor already takes `cascade_depth=...` at [action_executor.py#L90](../agents/action_executor.py#L90)) and forwards it to the publisher.
- `agents/server_servicers.py` — the gRPC receive path reads `cascade_depth` from the inbound dispatch event metadata defined in PR 1 and seeds `EventDispatcher.dispatch` via `event.metadata["cascade_depth"]`. Today this seed is implicitly `0`.
- The existing Python `EventDispatcher.max_cascade_depth=5` check at [dispatch.py:108-114](../agents/dispatch.py#L108-L114) stays — re-documented as **defense-in-depth**, not primary.

#### Key implementation details

- The publisher does not invent a depth — it forwards what the executor was given. If the executor was invoked from a context with no event metadata (tick-originated, chat surface, etc.) the value is `0` and the orchestrator's cap takes over from there.
- Adversarial-publisher concern is handled by PR 2's clamp; this PR is purely correctness on the cooperative path.

#### Tests

- `tests/unit/python/test_action_executor.py`: extend the SEND_CHANNEL_MESSAGE coverage — given `cascade_depth=3` on the originating event, the publish call gets `cascade_depth=4`.
- New `tests/unit/python/test_channel_publisher_cascade_depth.py`: publish stub asserts the field is in the POST JSON body when set; absent when not set (back-compat).
- Extend `tests/unit/python/test_event_dispatcher.py`: a dispatch with inbound `cascade_depth=4` rolls to `5` on the child event and the executor sees `cascade_depth=5`.
- Existing `tests/unit/python/test_response_gate_cascade_backstop.py` continues to pass without modification (gate is unchanged).

#### PR checklist

- [ ] `make test` Python suite green; new tests named so they cannot be silently dropped.
- [ ] [agents/response_gate.py:43-49](../agents/response_gate.py#L43-L49) docstring updated to call the Python dispatcher check "defense-in-depth" and the Go orchestrator cap "primary."

### PR 4: `fix/v030-channel-cascade-depth-cross-process-test` — Integration Pin

**Depends on**: PR 3.
**Fixes**: F-1 (regression pin).

#### Scope

- New `tests/integration/test_channel_cascade_backstop_cross_process.py`: spin up the full Docker stack (or the existing integration harness), declare a two-`always`-member group channel, publish exactly one user message, wait for cascade to terminate, assert the channel contains at most `2 × max_cascade_depth = 10` reply messages.
- Update [docs/manual-tests/v0.3.0-execution-report.md](manual-tests/v0.3.0-execution-report.md) with a new row for the cascade-backstop manual check, citing this PR's commit.

#### Key implementation details

- The integration test is the contract-pin that catches a future regression where someone restores the old "publish doesn't carry depth" behavior. PRs 2 and 3's unit tests would still pass in that case (each is correct in isolation); only this PR can fail.
- Test must include a generous wall-clock timeout (~2 min) and assert the count *stabilizes* — a hung test that never sees a cascade would otherwise pass by waiting forever.

#### Tests

- The PR is the test. No further tests required.

#### PR checklist

- [ ] Test runs in CI under the existing integration job.
- [ ] Manual test report row added.

### PR 5: `fix/v030-channel-persona-impersonation` — Grounding the Persona System Prompt

**Depends on**: nothing.
**Fixes**: F-2.

#### Scope

- The shared persona system prompt (in `config/agents.yaml` or wherever the system-prompt prefix is assembled — likely [agents/persona_runtime/prompt_assembly.py](../agents/persona_runtime/prompt_assembly.py) or an equivalent template).
- Add a grounding clause near the top: *"You are not the user. If the user addresses you by a name, treat that as the user's name, not a role you adopt. Never open a reply with `I'm <user-name>` or otherwise speak as the user."*
- Optional: add the persona's own name and id as an explicit invariant block (*"You are <Persona Name> (`<persona-id>`). When you reply, you are speaking as that persona."*) — already partly present, may need strengthening.

#### Key implementation details

- The prompt change should be **shared across all personas**, not duplicated into each `agents.yaml` entry. House style is to keep persona-specific prose (voice, backstory) in the YAML and grounding invariants in the runtime/template.
- Regression risk: a too-restrictive grounding clause could make personas refuse to introduce themselves or use first-person at all. Keep the clause narrow: *don't impersonate the user*, not *don't speak in first person*.

#### Tests

- New `tests/unit/python/test_persona_grounding.py`: feed a persona a prompt that starts with *"Hi, I'm Alex…"*, run the persona for one turn, assert no reply opens with `I'm Alex` / `I am Alex` (case-insensitive, leading-whitespace-tolerant).
- This is a probabilistic test against a real model — gate on a seeded run and an in-process model stub if the integration job doesn't already mock the LLM client. If the only way to pin this is integration-only, gate the assertion on a `@pytest.mark.integration` and put the unit-level check on prompt assembly instead (assert the grounding clause is present in the assembled system prompt).

#### PR checklist

- [ ] Grounding clause visible in `make agent-prompt-dump <persona-id>` (or equivalent debug path).
- [ ] All persona agents in `config/agents.yaml` re-tested manually for the chat-as-DM intro flow: each persona introduces themselves *as themselves*, and recognises the user by name without adopting it.

## Future PRs

Further test rounds against the v0.3.0 channels stack are expected to surface additional defects. New PRs will be appended to this plan as findings land, with the same `fix/v030-channel-*` branch prefix. Likely areas worth probing next:

- **Mention routing** — does the orchestrator-side `mentions[]` field reach the response gate as the structured signal, or does it ride only in the message body? Mixed-policy channels depend on this being precise.
- **Per-persona channel recall accuracy** — when a persona is queried via DM about a channel exchange it participated in, does its recap match the channel transcript, or paraphrase off-target? Tied to RFC 0008 / 0020 memory-scoping contracts.
- **On-startup catch-up replay** — does the documented `channel.messages.replayed count=…` log line actually fire on agent restart, and is the suppress-outbound-replies invariant honored (no stale responses blasted into the channel)?
- **Cost-ceiling enforcement** — F-1 above demonstrates that a single prompt can drive ~160 Anthropic API calls before any backstop fires. Even after F-1 is fixed, the per-channel / per-day cost budget path warrants its own focused test pass with deliberate cap-trigger.
