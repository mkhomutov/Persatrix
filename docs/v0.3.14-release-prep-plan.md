### Version state

All version-carrying components are at `0.3.13` — bump to `0.3.14` via [`bump_version.py`](../scripts/bump_version.py): `agents/pyproject.toml`, `agents/observability/{metrics,tracing}.py` (`_DEFAULT_SERVICE_VERSION` + the tracing docstring restatement), `cli/Cargo.toml` (+ `cargo update --workspace` for the lock), `internal/server/ui_handlers.go` (`defaultServiceVersion`). `web/package.json` stays `0.0.0` by design.

### Schema / migration state

**None — the migration gate is empty this cycle.** Channel store at v11, persona-memory at migration 17, both shipped by the v0.3.13 tag; PR 1's `principal_id` columns landed in migration v11 back at ISSUE-0081. The checklist replaces the migration gates with the explicit no-migration statement — **and immediately qualifies it**, because this is the one release where drop-in schema compatibility does not imply drop-in behaviour:

> **The activation-day reset.** Migration v11 backfilled every pre-existing row to `'local'` and the recall predicate is strict equality with no carve-out. A deployment already running `auth.mode: enabled` finds each person's accumulated memory unreachable the moment emission lands — indistinguishable from "the persona forgot everything." This is the boundary working, not a bug; bridging it would *be* the cross-tenant bridge the release forbids. Locked at plan opening, observed live at Leg 5, stated in the release notes with the operator remedy.

The only schema-adjacent change is **payload contract, not storage**: three new definitions in `schemas/channel.schema.json` (RFC 0040 Phase 1).

### Wire-compatibility state

**No protobuf changes this cycle** (`make proto && git diff --exit-code` re-verified at PR 4). The new `persatrix-principal` gRPC metadata header is additive on a rail the persona has bound since ISSUE-0081 PR 3 — a v0.3.13 persona under a v0.3.14 orchestrator isolates correctly, and a v0.3.14 persona under a v0.3.13 orchestrator sees no header and resolves `'local'`, i.e. today's behaviour. The REST surface is unchanged.

One deliberate **behaviour** change rides the release and must be read at the right scope: under `auth.mode: enabled`, memory written by one authenticated caller is no longer recallable by another. Under `disabled` — and for any unauthenticated caller on a public route, which is the whole persona fleet — the middleware emits nothing and behaviour is byte-identical.

**Container note**: `Dockerfile.agent` now copies `schemas/` into site-packages (PR 4) because the send-side validator resolves the schema off `Path(__file__).parent.parent`. A stale agent image leaves the validator a no-op, so the checklist gates a rebuilt image, not just a rebuilt tree.

### Manual test state

[MT-MEMORY-MULTIUSER-001](manual-tests/MT-MEMORY-MULTIUSER-001.md) is at **v1.0**, authored at #820 and **never run live** — that debt is the release gate. Six legs: Alice's private disclosure; Alice's own continuity; Bob's absence bar; Alice unchanged after Bob; the activation-day reset; the `disabled`-mode no-delta. [MT-AUTH-001](manual-tests/MT-AUTH-001.md) re-runs as the auth-substrate regression.

**Live-run guidance** (carry-forward + this cycle): machine-pace the whole arc in one script — governance windows race idle operators; **restart agents after the orchestrator** (the registry is in-memory and never re-registers — [ISSUE-0125](issues/ISSUE-0125-agents-never-reregister-after-orchestrator-restart.md); the MT carries the note, the eight others do not — [ISSUE-0126](issues/ISSUE-0126-mt-orchestrator-restart-registry-note-missing.md)); run with `PERSATRIX_MEMORY_PROVENANCE=1`, but read it knowing the `relationship` tier emits no admission line ([ISSUE-0122](issues/ISSUE-0122-relationship-tier-emits-no-provenance.md)) — for *this* MT the authoritative evidence is the `principal_id` column read off `memory.db`, not provenance; leg-verification sqlite queries ride the agent runtime's `python3` (the image ships no `sqlite3` CLI).
