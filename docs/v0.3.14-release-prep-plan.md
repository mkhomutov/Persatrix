**The release gate is the live arc.** A green run counts as the ISSUE-0082 proof **only with the two distinct emitted principal values read off storage and recorded verbatim** — the MT's own "Record the values" rule, made release-blocking here rather than invented here. The risk is not that a broken emission slips past Leg 3: it would fail that bar loudly, both people writing to one `'local'` tenant. It is that **an absence bar is satisfied by any empty recall**, whatever caused it — a write that never landed, a capture miss, an interaction that never closed, a restart that discarded it. Every one is green on Leg 3 with every row still reading `'local'`, for a reason that has nothing to do with the boundary. Leg 1's stop-and-diagnose check (`principal_id` must read `alice-person`, not `local`) and the group-by output separate the two, so the report carries them for `episodes`, `facts` **and** `relationships`. Leg 5 (the activation-day reset) is a **required observation**, not an optional extra: the release notes state it, so the run must show it.

**Out of scope**: new feature work. The v0.4.0 on-ramp (RFC 0039 Phase 3, RFC 0040 Phases 2–4, RFC 0038 §C–§E, RFC 0049 Phases 2–4, RFC 0041 Phase 1) stays parked per the master plan. The ISSUE-0082 residuals R-1 and R-2 (re-slotted **v0.3.15**, so interaction functionality is complete before v0.4.0 organizations) and the per-principal capacity sweeps are **Known Gaps to state**, not work to do. **R-3 is the exception**: [ISSUE-0130](issues/ISSUE-0130-catchup-replay-rederives-memory-under-default-principal.md)'s leak-stopper is work to do, in PR 1a.

### Schema / migration state

**None — the migration gate is empty this cycle.** Channel store at `channelStoreSchemaVersion = 11`, persona-memory at migration 17, both shipped by the v0.3.13 tag. The `principal_id` columns this release activates are **not** new: they landed in **persona-memory migration 11** at ISSUE-0081 (`agents/memory/_migration_registry.py` — *"ISSUE-0081: principal_id on all five persona-memory tiers"*), long before v0.3.14. The two stores are separately versioned and both happen to read 11 — the channel store's v11 is the RFC 0037 classification backfill, nothing to do with principals. PR 1 ([#819](https://github.com/mkhomutov/Persatrix/pull/819)) was wire-only and touched no storage. The checklist replaces the migration gates with the explicit no-migration statement — **and immediately qualifies it**, because this is the one release where drop-in schema compatibility does not imply drop-in behaviour:

> **The activation-day reset.** Persona-memory migration 11 backfilled every pre-existing row to `'local'` and the recall predicate is strict equality with no carve-out. A deployment already running `auth.mode: enabled` finds each person's accumulated memory unreachable the moment emission lands — indistinguishable from "the persona forgot everything." This is the boundary working, not a bug; bridging it would *be* the cross-tenant bridge the release forbids. Locked at plan opening, observed live at Leg 5, stated in the release notes with the operator remedy.

The only schema-adjacent change is **payload contract, not storage**: three new definitions in `schemas/channel.schema.json` (RFC 0040 Phase 1).

### Wire-compatibility state

**No protobuf changes this cycle** (`make proto && git diff --exit-code` re-verified at PR 4). The new `persatrix-principal` gRPC metadata header is additive on a rail the persona has bound since ISSUE-0081 PR 3 — a v0.3.13 persona under a v0.3.14 orchestrator isolates correctly, and a v0.3.14 persona under a v0.3.13 orchestrator sees no header and resolves `'local'`, i.e. today's behaviour. The REST surface is unchanged.

One deliberate **behaviour** change rides the release: under `enabled`, memory written by one authenticated caller is no longer recallable by another. Under `disabled` — and for any unauthenticated caller, which is the whole persona fleet — the middleware emits nothing and behaviour is byte-identical.

**Container note**: `Dockerfile.agent` now copies `schemas/` into site-packages (PR 4) because the send-side validator resolves the schema off `Path(__file__).parent.parent`. A stale agent image leaves the validator a no-op, so the checklist gates a rebuilt image, not just a rebuilt tree.

### Manual test state

Six legs: Alice's disclosure; Alice's continuity; Bob's absence bar; Alice unchanged; the activation-day reset; the `disabled`-mode no-delta. [MT-AUTH-001](manual-tests/MT-AUTH-001.md) re-runs as the auth-substrate regression.

**Live-run guidance**: machine-pace the whole arc in one script — governance windows race idle operators; **restart agents after the orchestrator** ([ISSUE-0125](issues/ISSUE-0125-agents-never-reregister-after-orchestrator-restart.md) — the registry is in-memory and never re-registers); run with `PERSATRIX_MEMORY_PROVENANCE=1` but do not treat it as the evidence — the `relationship` tier emits no admission line ([ISSUE-0122](issues/ISSUE-0122-relationship-tier-emits-no-provenance.md)), so the `principal_id` column read off `memory.db` is authoritative; sqlite queries ride the agent runtime's `python3` (the image ships no `sqlite3` CLI).
