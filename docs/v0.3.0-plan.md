## Why this plan exists

v0.3.0 is the first multi-RFC milestone. v0.1.0 shipped four sequential RFCs; v0.2.0–v0.2.3 each shipped one or two. v0.3.0 originally scoped **six RFC scopes** with non-trivial inter-RFC dependencies (now five — RFC 0007 retargeted to v0.4.0 on 2026-05-06). Without an umbrella, three things go wrong:

1. **Cross-RFC sequencing rots.** RFC 0020 P1 must land first; RFC 0011 P3 pairs with RFC 0020 P3. That ordering lives only in [ROADMAP.md](../ROADMAP.md) prose today.
2. **Reviewers can't tell where they are.** v0.2.3's paired delivery of RFCs 0018 + 0019 already needed a "joint merge order" block duplicated across both PR plans ([RFC 0019 §Joint Merge Order](rfcs/0019-pr-plan.md#joint-merge-order-rfcs-0018--0019)). Five RFCs would each need such blocks. One umbrella replaces them.
3. **Release prep gets pushed late.** v0.2.x release prep was authored *after* all RFCs landed; that worked at 1–2 RFCs per release. With five, the release-prep plan needs a placeholder now (Phase 3) and authoring time before the last implementation PR merges.

This document is light on RFC-internal detail — it owns "what order, in what step, by what gate."

## Acceptance for v0.3.0

The user-facing promise ([ROADMAP.md L420](../ROADMAP.md)) — *"give agents a shared channel and watch them talk, negotiate, and form opinions about each other over time"* — is met when the user can:

- Create an internal channel via `persatrix channel` and have two persona agents converse in it.
- Read coherent per-interaction recall from each agent (one episode per dialogue, not one per message — RFC 0020).
- See agents reason about *when* something happened ("we last talked 3 days ago" — RFC 0021 Phase 1).
- See per-step memory injection bounded by an agent-level context budget (RFC 0008).
- See rate-limited REST endpoints and audit-logged tool calls (RFC 0009 P1–2).

## Phase 1 — Author the six RFC PR plans

**Goal**: produce one PR plan per v0.3.0 RFC, modeled on [RFC 0017 PR plan](rfcs/0017-pr-plan.md). Each plan splits its RFC into ≤8 PRs that fit under the [BRANCHING.md](BRANCHING.md) 500-line soft cap and leave the repo in a passing-tests, lint-clean state.

#### Delivery shape

Phase 1 ships as **one combined PR** (`feature/v030-rfc-pr-plans-scaffold`) containing all six per-RFC plan files, with [RFC 0020](rfcs/0020-pr-plan.md) and [RFC 0021](rfcs/0021-pr-plan.md) fully fleshed out and the other four ([0008](rfcs/0008-pr-plan.md), [0009](rfcs/0009-pr-plan.md), [0011](rfcs/0011-pr-plan.md), [0007](rfcs/0007-pr-plan.md)) shipped as scaffolds. Each scaffold has every PR row pinned (branch, depends-on, scope) but defers the per-PR "Key implementation details" + "Tests" sections to be filled in immediately before that RFC's first implementation PR opens. Each scaffold ends with a `## Scaffold TODOs` checklist enumerating what must be added.

The combined-PR shape was chosen over six separate plan PRs because:
1. Scaffolds carry no code risk — review fatigue is the only cost, and one focused review is cheaper than six.
2. Cross-RFC anchors (`[RFC 0020 PR plan](0020-pr-plan.md) PR 5`) all resolve at land time instead of being TBD until the next plan PR opens.
3. The dep-chain root (RFC 0020) is fully detailed, so the first implementation PR (`feature/v030-rfc0020-tracker-schema`) can open immediately after this PR merges.

#### Acceptance

- Each new PR-plan file follows the [RFC 0017 PR plan](rfcs/0017-pr-plan.md) structure: Overview, Dependency Graph, PR Sequence, Risk and Mitigations, ROADMAP Hygiene.
- Every PR row has: branch name, depends-on, estimated size (with the [1.7× calibration factor](rfcs/0017-pr-plan.md#overview)), scope (table or bullets).
- RFC 0020 + RFC 0021 P1 plans additionally carry per-PR Key Implementation Details, Tests, and PR checklists.
- Scaffolds carry a `## Scaffold TODOs` block listing what must be filled in before the first implementation PR opens.
- Cross-RFC sequencing is called out explicitly in each plan's Overview, citing the [Dependency Graph above](#dependency-graph-rfc-level) as source of truth.

## Phase 2 — Implement the six RFCs

**Goal**: execute each RFC's PR plan from Phase 1. Each row in the [Master Progress Overview](#master-progress-overview) for rows 2–7 stands for the entire sequence in its PR plan — 3 to 8 PRs per RFC depending on scope (RFC 0021 P1 is the smallest at 3, RFC 0011 the largest at 8).

#### Workstream sequencing

Three observations matter for week-to-week planning:

- **RFC 0020 P1 must merge before any other Phase 2 work begins.** Every other v0.3.0 RFC consumes its schema columns (RFC 0021 P1, RFC 0008 §D) or its `add_turn` API (RFC 0011 P3). Fan-out begins after RFC 0020 P1 ships.
- **RFC 0008 is the second hub.** Once it merges, RFC 0011 P1–P2 develops without further RFC dependencies; RFC 0011 P3 + RFC 0020 P3 land jointly per the [paired-delivery rationale](../ROADMAP.md#why-rfc-0020-p3-is-jointly-delivered-with-rfc-0011-p3). (Originally RFC 0007 was a third concurrent workstream here; it was retargeted to v0.4.0 on 2026-05-06.)
- **RFC 0009 P1–2 runs throughout.** It integrates progressively at RFC 0011 P1 (rate limiting on REST endpoints) and RFC 0011 P3 (input sanitization on stored channel content).

#### Status tracking

Each per-RFC PR plan owns a "Progress Overview" sub-table the same shape as v0.2.3's, listing each PR in that RFC's sequence. Roll-up to this document happens at the workstream-row granularity only.

#### Acceptance per workstream

- All PRs in the corresponding PR plan are merged.
- The RFC's own status row in [ROADMAP.md](../ROADMAP.md) flips to `✅ Implemented`.
- The RFC's own closeout PR has merged (per [RFC 0017 PR 7](rfcs/0017-pr-plan.md#pr-7-featurev022-rfc0017-close--rfc-close) precedent).

#### Cross-cutting acceptance for Phase 2

- All six v0.3.0 RFC scopes show `✅ Implemented` in [ROADMAP.md RFC Master Index](../ROADMAP.md#rfc-master-index).
- `make test` passes on `main` with the six RFCs merged.
- The new manual tests authored across each RFC (channel routing E2E, interaction-summarization E2E, control-flow E2E, recency-rendering E2E, audit-log E2E) exist as `MT-*` documents in `docs/manual-tests/` and are ready for Phase 4 execution.

## ROADMAP hygiene

Per [.github/copilot-instructions.md](../.github/copilot-instructions.md) "Status Hygiene" and the [RFC 0019 PR plan §ROADMAP Hygiene](rfcs/0019-pr-plan.md#roadmap-hygiene) precedent:

- **Phase 1 PR opens** (this combined PR plans the six RFCs at once) → leave each RFC's status at `📋 Proposed` (or `👍 Accepted` for RFC 0008). Authoring PR plans does not start implementation.
- **First Phase 2 PR opens** for an RFC → flip the RFC's row to `🚧 Implementing`.
- **Each implementation PR merges** → update the merged-PR table inside the RFC's PR plan; tick the corresponding checklist line.
- **RFC closeout PR merges** → flip the RFC's row to `✅ Implemented`. Update this document's Master Progress Overview workstream row to ✅.
- **Phase 4 PR 4 merges (final pre-tag)** → flip v0.3.0 in [Version Map](../ROADMAP.md#version-map) to `✅ Released`.
- **`Last updated` header** → refresh on every step that materially changes ROADMAP content.

## Risk and mitigations

| Risk | Mitigation |
|------|------------|
| RFC 0020 P1 schema disagrees with RFC 0008 §D's compression contract once implementation begins | Phase 1 ordering puts the RFC 0008 plan immediately after the RFC 0020 plan; contract gaps surface during plan authoring, not implementation. RFC 0020 §I (Backfill and Migration) absorbs additive schema patches without churn. |
| RFC 0011 P3 + RFC 0020 P3 paired delivery slips and forces serial landing | The RFC 0011 plan explicitly carves out the joint-delivery PR with both RFCs cross-referenced — same pattern as the [RFC 0018/0019 paired closeout](rfcs/0019-pr-plan.md#joint-merge-order-rfcs-0018--0019). If pairing fails, RFC 0011 P3 ships with per-event episodic writes and RFC 0020 P3 backfills in a v0.3.x patch — documented as accepted divergence. |
| Five concurrent RFC PR plans drift on shared types (`InteractionTracker`, `MemoryFacade.retrieve_relevant`) | Phase 1 ordering forces the upstream type-definers (RFC 0020, RFC 0008) to land their plans first. Downstream plans cite concrete PR numbers and class signatures rather than re-defining them. |
| RFC 0009 P1–2 integration into RFC 0011 P1 (rate limiting) lands out of sync, leaving the publish endpoint unrate-limited | RFC 0011 §Phase 1 — Dependencies already pins this as a hard production-deployment dependency with explicit startup `WARN` and opt-out gate. The RFC 0011 plan's Phase 1 PR(s) cite the RFC 0009 middleware PR by number; if RFC 0009 slips, RFC 0011 ships the WARN path and a tracked-issue link. |
| Master plan rots as Phase 2 progresses; the [Master Progress Overview](#master-progress-overview) becomes inaccurate | Status updates are part of every step PR's checklist (see [ROADMAP hygiene](#roadmap-hygiene)). Reviewers reject step PRs that flip an RFC implementation status without also touching the per-RFC plan's progress table. |
| Release-prep plan (Phase 3) is authored too late, after the last implementation PR merges | Phase 3 sequences *before* Phase 4 with explicit gates. As soon as the final Phase 2 workstream's PR plan shows ≥75% PRs merged, open the Phase 3 PR — do not wait for the last implementation merge. |
| v0.3.0 surface grows beyond the five scoped RFCs during implementation | New RFC-tier work surfaced mid-flight files as a tracked issue and a v0.3.x or v0.4.0 follow-up; this plan does not absorb it. The "Out of scope" line at the top is the single arbiter — review challenges go there, not into the master overview. |
