> v0.3.9 — "Conversations you can mine" — ships the **mine rung**: the recall cluster that lets a persona **quote the verbatim record of what was said, scoped to the channels it was actually present for**. **[RFC 0036 verbatim message recall](rfcs/0036-persona-message-recall.md) — the user-facing win** — a new `recall_channel_messages` persona tool searches the exact words of past conversations **server-side in SQL** ([`agents/tools/recall.py`](../agents/tools/recall.py) → `POST …/recall` → an FTS5 `messages_fts` index over `messages` joined against the membership ledger), so a persona added → removed → re-added recalls messages from *both* of its stints and from neither the pre-join period nor the removal gap. Recall is `epoch_id`-hard-filtered (run isolation), spans sessions within the epoch, is audited server-side (count, not content), gated behind the opt-in `channels:recall` permission, and delimiter-escaped inside the RFC 0009 `<external_data>` envelope against prompt injection. **[RFC 0035 membership-interval ledger](rfcs/0035-channel-membership-interval-ledger.md) — the substrate** — an append-only `membership_intervals` ledger (one row per join/leave stint) written transactionally by the membership mutators, backfilled to one open interval per current member, guarded by a partial unique index (≤1 open stint per pair). It ships **no user-visible behaviour of its own** — the ledger is the scope recall joins against, plus a read-only operator membership-history inspection endpoint. Folded in: the same membership filter is retrofitted onto the **live RFC 0034 conversation window + boot-time catch-up** (`?as_participant`), so a re-added persona's *live* prompt also stops at its membership boundary. The user-facing promise: *a persona can quote the verbatim record of what was said, scoped to where it was present, and a human can search that record.*

### 3.1 Required Upgrade Notes in Changelog

This is the canonical source for Upgrade Notes text (PR 3 reconciles it with the five-row table already in `[0.3.9] - Unreleased`). All five rows below stand as the shipped notes; plus the behaviour-active-by-default caveat and the version-skew / upgrade-ordering caution.

| Notable change | Detail |
|----------------|--------|
| **[Permission — opt-in, deny-by-default]** New `channels:recall` permission | The `recall_channel_messages` tool is **unavailable** until a persona is granted `channels:recall` in its `permissions:` block (`channels: { recall: true }`). Existing configs without the block load unchanged and the tool is simply denied (a failed `ToolResult`) — verbatim cross-channel recall is materially more sensitive than reading the persona's own episodic summaries (`memory:read`), so it is a **distinct** grant an operator enables deliberately. See [RFC 0036 §E](rfcs/0036-persona-message-recall.md). |
| **[Migration — forward-only, upgrades on open]** Two channel-store migrations (v9 ledger, v10 FTS) | On first open after upgrade the channel store (`channels.db`, [`internal/channels/sqlite_schema.go`](../internal/channels/sqlite_schema.go)) migrates **v8 → v9 → v10**: **v9** ([`sqlite_membership_intervals_migration.go`](../internal/channels/sqlite_membership_intervals_migration.go)) adds the append-only `membership_intervals` ledger ([RFC 0035](rfcs/0035-channel-membership-interval-ledger.md), backfilled with one open interval per current member, guarded by the partial unique `ux_membership_intervals_open`); **v10** ([`sqlite_messages_fts_migration.go`](../internal/channels/sqlite_messages_fts_migration.go)) adds the `messages_fts` FTS5 index over `messages` (backfilled via `('rebuild')`). Both are additive, idempotent, and `user_version`-stamped in-transaction; **no operator action is required**, no data loss. On a SQLite build **without FTS5**, v10 records the unavailable flag and recall transparently falls back to a `LIKE` scan under the **identical** membership scope. The **persona-memory store is unchanged at v15** this release. **There is no rollback path — forward-only.** |
| **[Behaviour — active by default for personas]** Conversation-window / catch-up membership filter | Persona-runtime history fetches now pass `?as_participant=<agent_id>`, so a re-added persona's live conversation window and boot-time episodic seeding exclude pre-join and removal-gap messages ([RFC 0036 §G](rfcs/0036-persona-message-recall.md#g-conversation-window-membership-filter)). **No-op for a current single-stint member** (recent messages are unaffected); **human/CLI callers omit the param and are unchanged**. |
| **[Known limitation — accepted]** Pre-upgrade closed stints are unrecallable | The RFC 0035 §D backfill recovers **one open interval per *currently present* participant**; membership stints that *closed* (a remove, or a remove-then-rejoin) **before** migration v9 shipped are permanently absent from the ledger, so messages inside them cannot be recalled and are not surfaced by the window filter. This is an [accepted gap](rfcs/0035-channel-membership-interval-ledger.md#d-backfill) ([RFC 0035 OQ #1](rfcs/0035-channel-membership-interval-ledger.md#open-questions)), not a bug — recall and membership history are exact from v9 forward. |
| **[Known limitation — by design]** Recall honours the retention horizon | Recall reads the **live** `messages` table, so a cap-pruned or user-deleted message is gone from results (removed from `messages_fts` by the delete trigger). The tool description does not promise total recall; a durable, retention-immune recall store is explicitly [out of scope](rfcs/0036-persona-message-recall.md#h-retention-horizon-and-deletions) for this RFC. |

**Behaviour-active-by-default caveat (must appear in the release body).** The `?as_participant` conversation-window / catch-up membership filter runs **live by default for personas** — a re-added persona's live prompt and episodic seeding now stop at its membership boundary out of the box. It is a **no-op for a current single-stint member** (the common case — recent messages are unaffected), and human/CLI callers omit the param and are unchanged, so the practical change is confined to removed-and-re-added personas. The **recall tool itself stays opt-in** (gated behind `channels:recall`): a persona without the grant behaves exactly as in v0.3.8.

**Version-skew / upgrade-ordering caution.** The orchestrator owns the channel-store migrations **and** the new REST surface (`POST …/recall`, `?as_participant` on the history endpoint). **Upgrade the orchestrator first** (or together with the agents): a v0.3.9 agent talking to a **pre-v0.3.9** orchestrator gets a graceful failure from the recall tool (no endpoint) and its `?as_participant` filter is silently ignored (the old orchestrator returns unfiltered history — removal-gap messages would reappear in the live window until it is upgraded). The reverse skew is safe (a v0.3.9 orchestrator simply offers the tool to agents that may not request it). Note it in the release notes.

## 6. Known Gaps to Document in Release Notes

These items remain intentionally incomplete and should be described as deferred scope, not regressions. Seeded from [v0.3.9-release-prep-plan §Out of scope](v0.3.9-release-prep-plan.md) and [§Known follow-up issues](v0.3.9-release-prep-plan.md#known-follow-up-issues).

### v0.3.9-scope gaps

| Area | Description | Deferred to |
|------|-------------|-------------|
| **Durable, retention-immune recall store** deferred | Recall reads the **live** `messages` table; cap-pruned or user-deleted messages are gone from results (removed from `messages_fts` by the delete trigger). Copying messages into a separate retention-immune index was considered and **rejected** for this RFC — it re-opens the retention/privacy question. The tool description does not promise total recall ([RFC 0036 §H](rfcs/0036-persona-message-recall.md#h-retention-horizon-and-deletions)). | future RFC |
| **Pre-upgrade closed membership stints are unrecallable** | The RFC 0035 §D backfill recovers **one open interval per *currently present* participant**; stints that *closed* before migration v9 shipped are permanently absent from the ledger, so messages inside them cannot be recalled or surfaced by the window filter. An [accepted gap](rfcs/0035-channel-membership-interval-ledger.md#d-backfill) ([RFC 0035 OQ #1](rfcs/0035-channel-membership-interval-ledger.md#open-questions)), not a bug — recall and membership history are exact from v9 forward. | accepted (exact from v9 forward) |
| **Epoch isolation is deterministic-only by design** | The production channel store is single-epoch (`live`); the publish path never stamps a non-`live` epoch on a persisted message, so a cross-epoch message cannot be produced through the real publish path. The `epoch_id` hard filter is a forward-looking defensive guard pinned by the deterministic suite (`TestRecallEndpoint_RealPublishPath_ExplicitEpochUnreachable` + `TestRecallMessages_Epoch_HardFilter`), **not** a live MT lever. | n/a (forward-looking guard) |
| **Semantic / vector recall** deferred | Search is FTS5 lexical (BM25), the same technology the episodic summary tier uses; embedding-based semantic recall is a separate concern ([RFC 0036 Non-Goals](rfcs/0036-persona-message-recall.md#non-goals)). | later (RFC 0005 §5 pattern) |
| **Multi-tenant recall- / inspection-endpoint auth** deferred | The endpoints scope by a caller-supplied participant id on a channel REST surface that is currently unauthenticated (single-tenant trust level); they ship **no more permissively than their neighbours** and audit every recall call. The scope join is correct regardless of caller; this gates *treating recall as safe on a multi-tenant deployment*, not the cut ([RFC 0036 §OQ-1](rfcs/0036-persona-message-recall.md#open-questions) / [RFC 0035 §OQ-2](rfcs/0035-channel-membership-interval-ledger.md#open-questions)). | RFC 0009 / RFC 0039 |
| **`messages` retention / TTL policy + closed-interval pruning** deferred | Negligible at the foreseeable workload; revisited only when observed table size matters ([RFC 0035 §OQ-3](rfcs/0035-channel-membership-interval-ledger.md#open-questions)). | post-soak |
| **Recall ↔ episodic summary cross-referencing** deferred | Cross-referencing verbatim recall against the episodic summary tier is a follow-up once both surfaces are in real use ([RFC 0036 §OQ-5](rfcs/0036-persona-message-recall.md#open-questions)). | follow-up |
| **BM25 / recency ranking blend not yet calibrated** | A reasonable default ships (BM25-dominant, recency a mild tiebreak); retune when recall-usage data exists, not on a schedule ([RFC 0036 §OQ-3](rfcs/0036-persona-message-recall.md#open-questions)). | post-soak |
| **Rebroadcast residual risk** | Within scope, a persona can lift user A's exact words from channel X into channel Y. Cannot be fully prevented (recall *is* read access); mitigated by origin-tagging each row + system-prompt guidance that recalled content is reference material. Documented and accepted ([RFC 0036 §Security](rfcs/0036-persona-message-recall.md#security-considerations)). | accepted |
| RFC 0030 **Layer 5 — moderator / bid-and-select** deferred | Carried forward from v0.3.8; not a v0.3.9 dependency. The `chair` stays a low-threshold facilitator with the [`chair_moderation.py`](../agents/chair_moderation.py) seam inert. | v0.4.0 |
