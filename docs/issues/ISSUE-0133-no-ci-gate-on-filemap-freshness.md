## Summary

`FILEMAP.md` has no CI freshness gate. The only thing that regenerates it
is a hook that is not version-controlled and that not every contributor
has installed.

## Context

`scripts/generate_filemap.py` supports `--check`, documented in its own
module docstring as "exit 1 if FILEMAP.md is stale". Grepping
`.github/workflows/` and the `Makefile` for `filemap` or
`generate_filemap` returns nothing — the flag has no caller.

Regeneration happens in exactly one place: check 0 of
`scripts/pre_commit.py`, run by `.git/hooks/pre-commit`. That hook is
generated by `scripts/install_hooks.py` into `.git/`, so it is absent for
anyone who has not run the installer and stale for anyone who ran it
before the last change to it (see [[ISSUE-0134]]).

Found during the [PR #840](https://github.com/mkhomutov/Persatrix/pull/840)
review. That PR fixes a bug where committing from a linked worktree wrote
one tree's file map into the other tree's working copy. The PR body notes
that "the committed content happened to be correct, which is why this
went unnoticed" — the damage was confined to the working trees. That is
luck, not a property of the system: the same bug with the trees swapped
commits a wrong file map, and no gate would have caught it.

## Impact

`FILEMAP.md` is a navigation aid for AI assistants working in this repo —
its whole value is being an accurate index. A wrong one is worse than an
absent one, because it is trusted.

The failure is silent by construction. There is no assertion anywhere
that the committed map matches `git ls-files`, so the only detection
mechanism is a human noticing the header count looks off. During the #840
review the branch's map claimed 1978 tracked files when the post-merge
truth was 1980; that was caught by hand, in a review that happened to be
looking.

## Proposed fix / investigation path

A CI step in the Python job, adjacent to the other doc-freshness gates
(`scripts/rfcs.py --check` and the doc-links check already run there):

```yaml
- name: Check FILEMAP.md is up to date
  run: python scripts/generate_filemap.py --check
```

Two things to confirm before landing it:

* **Full history.** `git ls-files` needs the checkout to be complete;
  confirm the job's `actions/checkout` does not use a filter that hides
  paths. Depth does not matter here, since `ls-files` reads the index.
* **Merge-commit skew.** The gate compares against the *merged* tree, so
  a PR that is behind main can fail on files it never touched. That is
  arguably correct — it is the same staleness a merge would introduce —
  but it makes the failure message important. Have it print the diff, or
  at least say "run `python scripts/generate_filemap.py` and commit".

Worth pairing with the hook-staleness warning added in #840
(`scripts/pre_commit.py::_stale_hook_warning`), which addresses the other
half: CI catches the wrong map, the warning catches the cause.

## Notes

> 2026-08-22 — captured during the #840 review. The `--check` flag was
> verified present and functional on `main`; it simply has no caller.

> 2026-09-06 — RESOLVED in #858. New `Docs hygiene` CI job runs
> `python scripts/generate_filemap.py --check` on every PR alongside the
> doc-links, leaked-markup, and status-marker checks. Both caveats above
> were addressed: the default `actions/checkout` is a full index so
> `git ls-files` sees every tracked path, and the failure message now says
> what changed and what to run. One more caveat surfaced on the way: the
> header carries the generation date, so a byte comparison would have gone
> red on any PR older than a day — `--check` now compares everything except
> that date (`_comparable`, pinned by test_generate_filemap_check.py).
